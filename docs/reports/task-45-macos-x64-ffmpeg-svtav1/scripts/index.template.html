macOS x64 FFmpeg with SVT-AV1

2026-11-16 · task #45 · deps 1.17.0-rc2 · evermeet.cx 9.0.1 (shipped up to rc1) against martin-riedl.de 9.0.2 amd64 build 1789931006, both run under Rosetta 2 on an Apple Silicon Mac (macOS 27.2)

Outcome: shipped. The macOS x64 deps bundle now takes martin-riedl.de's static amd64 FFmpeg instead of evermeet's. The new build has SVT-AV1, so AV1 output (task #40) works on Intel Macs. It targets macOS 12.0, links only system frameworks, and is the same 9.0.2 build run as the Apple Silicon binary. Nothing VapourBox writes changes except the encoder's version text: native encoders are byte-identical, and x264, x265 and MP3 decode to identical pictures and samples (F3). Every one of the 30 test fixtures decodes identically (F4). The components it drops are ones nothing in VapourBox calls (F2).

F1. The candidates, and the checks the task asked for

  • evermeet.cx: no libsvtav1 in any release (libaom only). This was the gap.
  • Homebrew: dynamically linked to Homebrew's dylibs, and its bottles target the runner's macOS. Rejected for arm64 long ago for the same reason.
  • A source build: possible, but unnecessary once a static build that passes every check exists.
  • martin-riedl.de amd64 release build (chosen). The site publishes static macOS builds for both architectures from one build run. Its release history lists every build back to 5.0 (2022), and 2022 build-ID URLs still download, so an exact pin is durable. The deps script pins the build ID and each zip's SHA-256.

F3. Encoder output

A 2-second 720x576 test pattern and a 440 Hz tone, encoded single-threaded with +bitexact, at the settings the worker uses. Each output is then hashed as packets and as decoded frames (always decoded by the same binary).

EncoderPacketsDecoded

encoder_bitstreams in results.json. "Packets" hashes the coded packets only, not the stream header. That is why x265 matches here although the files are not byte-identical: x265 writes its version (4.2+37-b81f650e2 against 4.0+1-6318f22) into the header (2,415 against 2,412 bytes of extradata). x264 and LAME write theirs into the packets, so they show as different, but decode identically.

On real footage: the first 100 frames of three fixtures, encoded by each build and scored against a lossless copy by the same binary.

The size difference is the encoder's version text: x264 writes its full version, including evermeet's r3223 0480cb0, into an SEI message, and x265 reports 4.2+37-b81f650e2 (evermeet) against 4.0+1-6318f22 (martin-riedl; the site's own version list says 4.2, so its x265 version string looks stale). These fixtures are three clips at one setting each, not a population, and x264/x265 dispatch SIMD at run time, so a different CPU could in principle take a different path. Both encoders are designed to give the same output on every SIMD level.

MP3: 20 s of small_clip.mp4's sound at 192 kbit/s. The packets differ in the LAME header's version tag (LAME3.100 against LAME4.0).

Limits

  • Not run on an Intel Mac here. Everything above ran under Rosetta 2. CI's macos-15-intel runner runs the push gate and the heavy suite against the new bundle (both CPU tiers in the nightly), which is the real-hardware check.
  • Pre-AVX Intel Macs (the v2 tier). FFmpeg is one binary for both tiers. There is no Intel SDE on macOS, and the static check can only show that the initializers themselves contain no AVX. Beyond that, FFmpeg, x264, x265, dav1d and SVT-AV1 select their SIMD at run time, which is what evermeet's build relied on too. macOS 12's oldest supported Mac (Mac Pro, late 2013) has AVX; older Macs run it only through patchers.
  • Download size: +15.3 MB zipped for the macOS x64 bundle.
  • The source may thin out. martin-riedl.de's amd64 snapshot channel was last built in January 2026, though release builds continue (9.0.2 in September 2026). The build-ID pin keeps working whatever happens next; a future FFmpeg series may need a source build or another host.
  • Not tested: hardware encoders (VideoToolbox is in both builds and unchanged), and an AV1 source (dav1d) on x64.

Decisions

  • martin-riedl over a source build: it passes every check, matches the arm64 bundle's build, and needs no toolchain in CI.
  • Pinned by build ID and SHA-256, not latest: the host keeps build-ID URLs, so a rebuilt deps bundle gets the same binary, and a changed file fails the build. (arm64 still takes latest with the series check; pinning it too is a separate change.)
  • The build fails without libsvtav1 on either arch (assert_ffmpeg_encoder in download-deps-macos.sh), and the push gate's libsvtav1 is compiled in test checks every bundle with no exception.
  • The app keeps its availability check (HardwareEncoderDetector, missing_encoder_problem): cheap, and still right for any FFmpeg without SVT-AV1.
  • A new deps version, 1.17.0-rc2: no released app references 1.17.0 yet.
