graphengine f6211289: get_tmp_size() leaves out an error-diffusion node's context

2026-11-22 · task #109 (added by task #103) · measured on macOS arm64 (M1 Pro) and x86_64 under Rosetta, locally, and on GitHub Actions ubuntu-24.04 (x64) and ubuntu-24.04-arm runners · every number below comes from scripts/, and the tables are in data/.

Outcome: cause found and bisected; reported upstream as sekrit-twc/zimg#245 with a one-line fix. Our bundles are unaffected (task #103's pin). zimg master's e2e43d09 moved graphengine from cb5b2ce1 to 91c6af4c. From graphengine f6211289 ("Exclude fused nodes from buffer sizing calculation", 2026-07-30), zimg_filter_graph_get_tmp_size() leaves out the context of any node with no live rows. The error-diffusion dither node is such a node, and its context holds two float error rows, 2 × (width + 2) × 4 bytes. So every graph that dithers with error diffusion writes about that much past the end of the buffer: 792 bytes at width 96, 5784 at 720. VapourSynth's resize allocates exactly get_tmp_size() bytes in vszimg::real_get_frame, and glibc's heap checks caught the overrun there. It reproduces through zimg's C API alone, on every platform and compiler tried. A one-line change (skip only the cache sizing, not the context) makes every case clean. graphengine HEAD (e9b10267) still has the bug.

Added 2026-11-27 (task #126): fixed upstream. sekrit-twc closed #245 on 2026-11-22 with graphengine 308d3735, which moves the context sizing above if (!live_rows) continue;, the same effect as this report's patch. zimg master was rewritten to 9806db42, which is 67e06032 (our pin) with that graphengine: e2e43d09 is no longer on master. The text below is as written on 2026-11-22. Task #126 measures the fixed commit against our pin with these scripts: task-126-zimg-9806db42.

Symptom

From task #103: 1.18.0-rc3's Linux bundles, with VapourSynth R78 statically linked to zimg e2e43d09 through R78's subprojects/zimg.wrap, aborted in VapourSynth's own resize on every job that resized: double free or corruption (!prev) at free() ← vszimg::real_get_frame. That was 617 of 6861 sweep rows (Deband, BM3D, Descale, Crop & Resize's BT.709, Face Restoration, Colourisation, QTGMC high precision), and zimg_colorspace_test. VapourBox's template dithers its depth reductions with dither_type="error_diffusion": ten calls in pipeline_template.vpy (BM3D, the AI upscale, the fade fix, the working-format and depth restores), plus colorize.py and ai_runtime.py. The failing passes are ones that reach such a call. That was not traced pass by pass.

Where the buffer comes from

R78's src/core/vsresize.cpp, real_get_frame, uses zimg's C API through zimg++.hpp. It allocates vsh_aligned_malloc(graph.get_tmp_size(), 64) (the larger of the two field graphs when interlaced), runs graph.process(src, dst, tmp), and frees the buffer. A write past tmp_size lands in the next heap chunk's header, and glibc notices on that free() (the !prev check) or on a later malloc. So a plain C program can do exactly what VapourSynth does.

The repro

scripts/tmp_overrun.c builds a graph per case, as VapourSynth does (cpu_type AUTO_64B, the luma filter for chroma too, approximate gamma, full-frame buffers with 64-byte strides, interlaced cases as two field graphs processed bottom then top). It then measures in two ways:

  • canary: 64 KiB guard bytes on each side of the buffer, filled with 0xA5 and then 0x5A, and every guard byte that changed is counted. This works on any allocator or CPU.
  • exact (--exact): exactly tmp_size bytes, for AddressSanitizer.

scripts/cases.tsv (from make_cases.py) has 158 graphs: the conversions in zimg_colorspace_test.rs and the kinds of call the failing sweep rows make (Deband's depth round trip, BM3D's GRAY planes, Descale's luma resample, the 601→709 matrix change, Colourisation's float YUV444 to the source format, an SD→HD resize). Each is at 96x64, 98x64 and 720x480, progressive and interlaced. zimg is built by scripts/build.sh the way R78 builds its subproject: R78's own subprojects/packagefiles/zimg/meson.build is overlaid on zimg, so the file list, -DZIMG_GRAPHENGINE_API, c++17 and the AVX2/AVX-512 kernel libraries are all R78's. There are three build modes:

  • vs: as R78 ships it (b_ndebug=if-release, so NDEBUG is set);
  • guard: NDEBUG unset, so graphengine puts guard pages between the regions of the buffer and asserts on them (state.h);
  • asan: vs plus -fsanitize=address, run with --exact.

scripts/upstream_repro.c is the one-case version for the upstream report: GRAY16 → GRAY8 at 96x64 with error diffusion.

Cause

f6211289 added an early continue to GraphImpl::impl::compile_simulation_result, for nodes whose simulation found no live rows (fused nodes, which need no cache):

unsigned live_rows = sim.live_range(id);
if (!live_rows)
    continue;

for (unsigned p = 0; p < node->num_planes(); ++p) { /* cache sizing */ }

node_result.context_size = (sim.context_size(id) + ALIGNMENT_MASK) & ~ALIGNMENT_MASK;
node_result.initial_cursor = sim.cursor_min(id);
sat_add(result.tmp_size, node_result.context_size);

The continue skips the last three lines too. So a fused node's context is never counted in tmp_size, and its context_size stays 0, but begin_frame still hands the filter a context pointer and init_context fills it. Error diffusion is the filter in these graphs with a real context (its error rows), so it writes them past the buffer, or over whatever region follows. The patch (scripts/graphengine-fused-node-context.patch, against 91c6af4c and HEAD alike) skips only the plane loop:

-			unsigned live_rows = sim.live_range(id);
-			if (!live_rows)
-				continue;
-
-			for (unsigned p = 0; p < node->num_planes(); ++p) {
+			// A fused node (no live rows) has no cache, but its filter context
+			// is still allocated from tmp and initialised in begin_frame.
+			unsigned live_rows = sim.live_range(id);
+
+			for (unsigned p = 0; live_rows && p < node->num_planes(); ++p) {

With it, f6211289's saving stays (1216 bytes against cb5b2ce1's 1344 in the minimal repro), and every case is clean in all three modes on every platform above. It is offered to upstream as a suggestion only. VapourBox ships cb5b2ce1 and never this patch.

Who is exposed

  • VapourBox: nobody, since task #103. Linux pins the wrap to 67e06032 / cb5b2ce1. macOS ships zimg releases (arm64 Homebrew's 3.0.6, x64 3.0.5), which predate the range. The Windows R78 wheel was uploaded to PyPI on 2026-07-24, six days before f6211289 existed.
  • The bug itself is not platform-specific. It reproduces on macOS arm64 and x86_64 and on Linux x64 and arm64, with Apple clang, gcc 13 and clang 18. glibc is only what made it loud.
  • Anyone building VapourSynth from source with its wrap (R78 through R82 still say revision = HEAD) since 2026-11-21. That is left to zimg's maintainer, who also maintains VapourSynth's resize; we are not reporting it to VapourSynth.
  • Added 2026-11-27 (task #126): a VapourSynth build from its wrap made after 2026-11-22 clones master 9806db42 (graphengine 308d3735), which has the fix.

Limits

  • The canary sees only writes past either end of the buffer. Writes that land inside it, in another region, are seen only by the guard-page build. The guard counts are the full extent; the vs counts are a lower bound.
  • Only zimg's own filters were tried. Another graphengine user with a context-carrying fused node would hit the same thing.
  • The patch was checked against these 158 graphs and the minimal repro, not against graphengine's own test suite. Whether initial_cursor matters for a fused node was not examined; the patch keeps setting it as before f6211289.
  • Only cpu_type AUTO_64B (VapourSynth's default) was run. The fault is in the size calculation, not in a kernel, and it reproduced with NEON, with AVX2 under Rosetta, and on the runners' CPUs (each job's log names the CPU and whether it has AVX-512). The number of graphs that overrun past the end differs by arch (18 against 24), presumably because the buffer's layout follows each arch's kernels. That was not examined. The guard counts (36) are the same on both.
  • Windows was not run. Its exposure is ruled out by date (wheel built before the bad commit), not measured.
