Core ML aborts vspipe on Intel Macs; the CPU is faster there anyway

Task #94, 2026-11-21. Measured on GitHub's macos-15-intel runners (Intel Core i7-8700B, 4 vCPUs, 14 GB, macOS 15.7, Apple Paravirtualized Graphics Device, Metal 2) with deps 1.18.0-rc2 (both x64 CPU tiers) and the ai-runtime add-on's onnxruntime 1.23.2. No real Intel Mac was measured (see Limits).

Outcome

  • The fault: on macOS x64, Core ML runs the ai-runtime models on the GPU through Metal Performance Shaders. MPS compiles its kernels at the first prediction; when a compile fails it asserts (MTLReportFailure in MPSLibrary::MPSKey_Compile, "Compilation failed: (null)") and the whole vspipe process dies with SIGABRT. No Python exception is raised, so ai_runtime.Runner's CPU retry and session()'s creation fallback never run.
  • How often: 8 nightly jobs in four days (2026-11-17 to 2026-11-20): 6 of the 12 x64 heavy jobs that ran since the nightly split into heavy and sweep legs, and 2 of the 12 x64 sweep jobs; both CPU tiers; DDColor (heavy) and DeOldify (sweep previews); two different kernels; never arm64. It is intermittent on one machine: in the probe below, 12 cold first-compiles on fresh runners all passed.
  • Fix: Intel Macs are no longer offered Core ML. ai_runtime.preferred_providers() leaves it out on darwin/x86_64 and every ai-runtime model (Colourisation, Face Restoration) runs on ONNX Runtime's CPU provider there; cpu_reason() says why in the probe (cpuReason) and in the passes' log lines. VAPOURBOX_AI_COREML_ON_INTEL=1 offers Core ML again, for measuring only. Apple Silicon is unchanged.
  • Cost on the runner: none; it is faster. On four fresh runners, a 16-frame encode on the CPU took a median 35 s for DDColor against 179 s on warm Core ML (5×), 64 s against 102 s for DeOldify (1.6×) and 98 s against 188 s for RestoreFormer++ (1.9×). Core ML's start-up (its compile, every process) is 34–134 s on these VMs; the CPU's 2–10 s. At 120 frames (two more runners) the CPU was still ahead, 1.6–1.8× for DDColor and 1.05–1.4× for the others: per frame the two providers are equal within noise, and Core ML never earns its start-up back. The CPU was not slower in any of the 108 runs' comparisons.
  • The picture is the same: Colourisation's output on the CPU is identical to Core ML's, sample for sample, for both models (the providers differ by less than one 8-bit level, and the conversion rounds both to the same samples). Face Restoration's differs in 0.4% of luma samples, by 0.004 levels on average.
  • Rejected: a probe before the job (the failure is intermittent, and the self-test model uses neither failing kernel), a canary prediction in a child process (doubles the compile and the job's own compile can still fail), re-running the job on the CPU after the abort (more machinery for a slower provider on a frozen runtime: 1.23.2 is the last Intel wheel), and a retry in the test.

Limits

  • A real Intel Mac's GPU was not measured. The runners' GPU is Apple's paravirtualized device (64 MB VRAM), not Intel UHD/Iris or an AMD Radeon Pro. On a real Intel Mac, Core ML might be faster than the CPU, and the MPS compile might never fail. What such a machine loses by running on the CPU is unknown. The choice can be revisited if a user with real hardware reports it, by measuring with VAPOURBOX_AI_COREML_ON_INTEL=1 and this script.
  • Four vCPUs. A Mac with more cores runs the CPU provider faster; Core ML would not scale the same way.
  • The probe never reproduced the abort (0 of 12 cold runs, 0 of 108 runs), so it does not confirm that the cold compile is the trigger; the nightlies are the evidence for the fault, the probe for the cost of the fix.
  • One clip per pass, at 640×480. DDColor's render size is fixed (512) whatever the source size; DeOldify's and the faces' work grow with it.

Reproduce

  • The nightly evidence: scripts/nightly_aborts.sh > data/nightly_aborts.tsv and CACHE=<the same log directory> scripts/nightly_timings.sh > data/nightly_timings.tsv (need gh).
  • The probe: copy scripts/probe-coreml-intel.yml to .github/workflows/ on a branch and push it (PROBE_NAME picks the short runs, (cold, warm), or the long ones, 120 frames); or on any Mac with the add-ons installed, copy scripts/coreml_vs_cpu_test.dart to app/test/ and run it with flutter test --plain-name ….
  • The tables: python3 scripts/summarise.py.
