Task #68: vspipe's teardown race, backported to R78

2026-11-19 · macOS arm64 (M1 Pro), deps 1.17.0-rc3 · scripts in scripts/, raw counts in data/

Outcome

  • The fault (task #65): R78's vspipe increments completedFrames at the top of frameDoneCallback, without the mutex, and only then writes the frame. outputNode's condition.wait(lock, pred) checks the predicate before it first sleeps, so main can see "every frame done", free the script and the core, and leave the callback writing into freed memory: SIGSEGV after the last frame, intermittently. Task #66's gdb cores (QTGMC Draft at 96x66, Linux x64) show exactly this: the crashing thread in frameDoneCallback, main in freeScript.
  • Upstream fixed it in 4ff3f8a0, first released in R80, but the bundle cannot move to R80. R80 dropped API 3; 12 of the bundle's 40 plugins are API 3 only (section 2), most with no API 4 release. Filed as task #74.
  • So the fix is backported to R78 on every platform: Scripts/patches/vapoursynth-r78-vspipe-frame-done-count.patch is 4ff3f8a0's vspipe.cpp change byte for byte (only line offsets differ), plus a vspipe --version line that marks the build. macOS and Linux apply it in their source build; Windows replaces the wheel's vspipe.exe with one Zig builds from patched R78.
  • With the race window widened, unpatched R78 crashed 400 of 400 runs and the patch 0 of 400 (section 3).

1. The change

The counters move to the end of the callback, inside the block that already takes the mutex to notify. A counter reaching the total now means the frame was written and released, and because outputNode holds the same mutex from its first request until it waits, the increment cannot land between its predicate check and its sleep. The progress line adds the current frame to the (unchanged) counter instead of reading the incremented one.

The --version marker, VapourBox patch: vspipe frame-done count (task #68), is how a bundle is checked: each download-deps-* script refuses to finish without it (and rebuilds a vspipe that lacks it), and vapoursynth_integration_test.dart requires it from deps 1.18.0. The race itself is too rare to test for on every push.

Windows: the wheel's vspipe.exe is four C++ files (vspipe.cpp, vsjson.cpp, printgraph.cpp, wave.cpp) that reach VapourSynth only through vsscript.dll's getVSScriptAPI and getVSScriptAPILastError. Zig builds them against an import library for those two exports, with R78's meson defines and upstream's manifest embedded (it sets longPathAware), at -mcpu=x86_64 so one build serves both CPU tiers. The build-deps run's smoke test reports Core R78 and the marker.

scan_plugin_api.py on the deps 1.17.0-rc3 macOS arm64 bundle (data/plugin-api-macos-arm64-1.17.0-rc3.txt) finds 12 plugins that export VapourSynthPluginInit but not VapourSynthPluginInit2, which R80+ refuses ("uses API 3, which is no longer supported"):

Only FillBorders has an API 4 release. R79–R82's ChangeLog otherwise changes nothing CLAUDE.md's R78 notes rely on.

Limit: the scan was run on one bundle (macOS arm64). Windows and Linux ship the same plugins at the same versions except where a platform takes a different build; the follow-up (task #74) should scan each.

3. Measurements

Widened (widened_race_ab.sh): both binaries built from R78 with widen_race.py's test-only sleeps, 20 ms before outputFrame writes and 5 ms between outputNode's requests and its wait check, so the interleaving that crashes is the likely one. trigger.vpy, 4 concurrent loops, data/summary-widened-macos-arm64.txt:

vspipeRunsCrashed
R78, widened400400 (all exit 139, SIGSEGV)
R78 + patch, widened4000

Unwidened (compare_vspipe.sh, 8 loops × 150 beside 4 busy-loop CPU hogs, data/summary-unwidened-macos-arm64.txt): 0 of 1200 for either binary. arm64 does not reproduce the race at its natural width, as in task #65, so this row shows the patched build runs, not that it fixes anything.

The widened test proves the patch closes the interleaving the sleeps force; it does not measure how often the unwidened race fires. Task #65 measured that on x86 (2–3% of IVTC previews with its old template, 2 in 1200 Bwdif previews on macOS x64).

4. Not yet measured: the x86 A/B on the built bundles

The plan was to swap each built 1.18.0 x86 bundle's vspipe for R78's own and run task #65's loops (IVTC with the pre-#65 template, which crashed 2–3%) on Linux x64, macOS x64 and Windows x64. That workflow (.github/workflows/repro-vspipe-teardown.yml, temporary) had not run when this report was written; its counts belong here when it has.
