BtbN's rolling FFmpeg moved within 9.0: the D1 fixture, and a pin by build

2026-11-27 · task #123 (found by task #116) · measured on minimal local builds of FFmpeg at the two commits BtbN built (macOS arm64), and on GitHub's release listings · the scripts are in scripts/, their output in data/.

Outcome: only a test fixture was broken. The fixture is fixed, and Windows and Linux FFmpeg are now pinned to one exact build.

BtbN's rolling n9.0-latest asset went from n9.0.2-61 (deps 1.18.0-rc3) to n9.0.2-963 (rc4). Between them, release/9.0 gained ff65bd5417, a heap-overflow fix. It makes swscale refuse a field-by-field 4:2:0 conversion when the height is 2 mod 4. The field-order test's 720x486 fixture asked for exactly that, so three heavy tests failed on Windows and Linux.

No worker or app path asks for one. Every encoder format pin, the preview's scale and a pad/format/crop chain pass on the new code at 720x486 (68 of 68 rows); only the interl=-1 control fails.

The fixture now converts at 488 lines and crops to 486. That gives the same file from both builds, and the 4:2:2 fixture is byte-identical to before.

Windows and Linux now pin n9.0.2-963-g4d831360c9 (what rc4 shipped, so the binaries don't change) by SHA-256. It is fetched from our ffmpeg-mirror-v1 release first, then from BtbN's dated tag.

1. What failed

Nightly 45796959369 (deps 1.18.0-rc4, 2026-11-26), heavy legs on Windows x64, Windows x64-v2, Linux x64 and Linux x64-v2. These tests failed in integration_field_order_test.dart, group 720x486 (task #92):

  • H.264 at 4:2:0 is coded progressive, and the job log says why
  • H.264 cropped to 484 lines is MBAFF again
  • ProRes keeps the fields; x265 is not told to use H.264

The fixture command, crop=720:486:0:44,scale=interl=1,format=yuv420p, failed with:

[swscaler] The bottom field has fewer chroma rows than its height requires (Invalid argument): fmt:yuv422p ... -> fmt:yuv420p
Error while filtering: Invalid argument

The other two tests then read the empty file it left ("EBML header parsing failed"). Every failing job's log reports ffmpeg version n9.0.2-963-g4d831360c9-20261125. macOS (martin-riedl 9.0.2, pinned by build) passed.

Each of those jobs also had one failure unrelated to FFmpeg:

  • CTMF in task #98's stress test, fixed on main by task #112; the run's branch predated it.
  • The Windows v2 DCTFilter timeout, task #124.

2. The cause: ff65bd5417

git log d59078794d..4d831360c9 -- libswscale on FFmpeg's release/9.0 lists about 40 swscale fixes. The refusal is ff65bd5417, "swscale: reject interlaced frames whose bottom field lacks a chroma row", cherry-picked from f93d46898b ("Fixes: heap-buffer-overflow (read and write)"). It adds this check to sws_frame_setup(), for the bottom field:

2 * AV_CEIL_RSHIFT(field->height, vsub) <= AV_CEIL_RSHIFT(frame->height, vsub)

At 486 lines, each field is 243 lines, which needs 122 chroma rows, so two fields need 244. The frame has 243. The older code converted the bottom field anyway, reading and writing one chroma row past the plane. So the fixture rc3 produced was made through an out-of-bounds access.

swscale only splits a frame into fields when it carries AV_FRAME_FLAG_INTERLACED (ff_fmt_from_frame). vf_scale sets or clears that flag from its interl option, which defaults to 0 and clears it. So only interl=1, or interl=-1 on a flagged frame, can reach the check. The scaler ffmpeg inserts for -pix_fmt uses the defaults.

3. Users: no path reaches it

Static: grep -rnE "interl=" over worker/, app/lib, app/test, Scripts, .github and Tests finds only the fixture. The worker's interlaced chroma conversions run in VapourSynth (zimg honours _FieldBased). HDR tone mapping is zscale, not swscale.

Measured: scripts/exposure_matrix.sh runs every way the worker lets FFmpeg convert a still-interlaced picture, at 720x486:

  • a Y4M pipe as vspipe writes it (Ip), with -top 1 or -top 0 on the input (field_order_args) and -flags +ildct;
  • through every format an encoder is pinned to: forced_pix_fmt's yuv420p / nv12 / p010le, ProRes's and v210's yuv422p10le / yuv444p10le, and rgb24;
  • the preview's scale=out_range=pc:flags=accurate_rnd+full_chroma_int to rgb48be;
  • a pad / format / crop chain like the grid crop;
  • a control, scale=interl=-1, which keeps the frame's flag.

4. The fixture

The fixture now converts at 488 lines, where each field has its own 122 chroma rows, and crops the result to 486. Cropping 2 lines off the bottom of a 4:2:0 frame keeps its first 243 chroma rows as they were interleaved, so the field order and each field's chroma are kept:

setpts=PTS-STARTPTS,fps=25,crop=720:488:0:44,scale=interl=1,format=$pixFmt,crop=720:486:0:0

5. The pin

A series pin against a rolling tag still moves within the series. The 2026-08-31 decision ("pin the series, never an exact old build") rested on BtbN dropping old builds. The releases listing (data/btbn_releases_2026-11-27.txt) shows how long BtbN actually keeps them:

  • daily autobuild-* releases for about 14 days (2026-11-13 to 2026-11-26 present);
  • month-end ones for at least two years (back to 2024-12-31).

rc4's autobuild-2026-11-25-12-41 would therefore disappear around 2026-12-09. The listing also shows latest moving again: the 2026-11-26 build's Linux tarballs are 62 MB, against 154 MB a day earlier.

Decision.

  • Pin n9.0.2-963-g4d831360c9 on Windows and Linux. It is the build rc4 shipped, so a rebuild changes no FFmpeg binary, and it keeps the swscale overflow fixes.
  • Copy its three assets, unmodified, with BtbN's LICENSE.txt, to ffmpeg-mirror-v1 on this repository (a prerelease, never Latest). GitHub's digests match the pins:

How the scripts use it:

  • download-deps-linux.sh and download-deps-windows.ps1 try the mirror, then BtbN's dated tag. Either copy must match the hash.
  • Each asserts the installed build from ffmpeg -version, and replaces an ffmpeg that is another build.
  • ffmpeg_version_pin_test.dart checks that both scripts pin the same build, inside the series, with a dated fallback tag and a hash per asset, and that neither fetches latest.
  • source_pin_test.dart refuses any releases/download/latest/ URL.

Not done

  • A deps rebuild just for this. The binaries are rc4's; the pin ships with the next deps build (1.18.0-rc5).
  • FFmpeg 9.1 (task #107), which will pin and mirror a dated 9.1 build the same way.
