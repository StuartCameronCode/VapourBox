Task #73: matrices FFmpeg 9's scale can't name

2026-11-19 · macOS arm64 (M1 Pro) · deps 1.17.0-rc3 (FFmpeg 9.0.2, martin-riedl build) · branch stuart/73-sdr-preview-fails-for-sources-tagged-ycg

Summary

The preview converts its untagged Y4M frame to RGB with scale=in_color_matrix=<m>, where <m> was the source's matrix tag as written (only rgb was dropped). FFmpeg 9's scale has no conversion for six of the H.273 matrices the worker accepts as tags. An SDR source tagged with any of them got no preview (ffmpeg exit 234). Fixed: ColorMetadata::swscale_matrix maps each one to the nearest matrix scale has, or leaves it out so auto (BT.601) applies.

Wider finding, not fixed here: FFmpeg 9 can't convert a frame tagged with these matrices at all. The app's before frame, its thumbnails, the detectors' converting decodes and an encode whose encoder converts all fail on such a source. Filed as task #76.

1. What scale accepts

ffmpeg -h filter=scale lists in_color_matrix as an integer (−1…17) with these named constants: auto, bt601, bt470, smpte170m, bt470bg (all 5), bt709 (1), fcc (4), smpte240m (7), bt2020, bt2020nc (both 9). The table shows the preview's own filter (in_range=tv:out_range=pc:flags=accurate_rnd+full_chroma_int) on a 96x64 testsrc2 Y4M, untagged like the preview's pipe.

in_color_matrixResult
auto, bt601, bt470bg, smpte170mok (identical output)
bt709 / fcc / smpte240mok (each different)
bt2020, bt2020ncok (identical output)
ycgco, bt2020c, smpte2085, chroma-derived-nc, chroma-derived-c, ictcpUndefined constant or missing '(' in '<m>'
8, 10, 11, 12, 13, 14 (their AVCOL_SPC numbers)Unsupported input color matrix '<m>'

The numeric values fail as well, so the scaler has no conversion for these matrices; there is no other spelling to fall back on. Raw output: data/probe-macos-arm64.txt.

2. Decision, per tag

TagPreview reads it asWhy
bt709, fcc, bt470bg, smpte170m, smpte240m, bt2020ncitselfAccepted as written. Every existing preview keeps its arguments byte for byte.
rgbleft outIdentity matrix; scale has no entry for it (unchanged).
bt2020cbt2020Same Kr/Kb as the non-constant-luminance form. Reading constant-luminance samples with those coefficients is the nearest swscale can do, and is how FFmpeg's swscale treated it before 9.
chroma-derived-nc / -cbt709 or bt2020 when the primaries are those; else left outH.273 derives Kr/Kb from the primaries. From BT.709 or BT.2020 primaries they are exactly those matrices' coefficients. For other or missing primaries, scale has nothing closer than auto.
ictcpbt2020ICtCp exists only with BT.2100 (BT.2020 primaries). An SDR picture carrying it is most likely BT.2020 YCbCr with a wrong or missing transfer tag. display_tonemap_filter reads an unusable HDR matrix as BT.2020 for the same reason.
ycgcoleft out (auto)YCgCo is not a Kr/Kb matrix (Cg and Co are not B−Y and R−Y), so every choice shows wrong hues. Auto is what an untagged picture gets.
smpte2085left out (auto)Y′D′zD′x is for XYZ-coded content and has no YCbCr equivalent. zimg doesn't implement it either.

The preview of a ycgco or smpte2085 source therefore shows wrong colours; the encode keeps the samples and the tag. An exact preview would need zscale, which knows ycgco, 2020_cl, chroma-derived and ictcp. That was rejected for now: it would be a third conversion path, for tags no real source has been seen with, and the before frame and the test twin would need it too.

3. Verification

  • Rust (color_metadata.rs): every MATRICES × PRIMARIES (and none) combination names only constants on the pinned list. Each MATRICES entry has a decided reading, so adding a tag fails the test until its reading is chosen.
  • Shared table Tests/TestResources/preview_scale_cases.json (28 rows): the Rust preview_scale_filter and the test twin WorkerHarness.previewScaleFilter both reproduce every row. preview_scale_filter_test.dart also reads swscale_matrix's arms from the Rust source and checks the twin against them.
  • Bundled ffmpeg (preview_scale_ffmpeg_test.dart, push gate): every row's filter is run on an untagged Y4M frame, on each CI platform's own FFmpeg build.
  • Heavy (integration_colour_tag_pixels_test.dart): small_clip.mp4 retagged ycgco, bt2020c (bt2020 primaries), smpte2085, ictcp and chroma-derived-nc (bt709 primaries) with setparams, so no sample is converted.
    • Each preview succeeds and is identical (0.000/255) to the preview of a twin tagged as it is read.
    • Each also matches the source decoded as the preview converts it (0.000/255).
    • With main's worker the ycgco case fails: "ffmpeg encoder exited with exit code 234".
    • A lossless FFV1 encode of the ycgco fixture keeps color_space=ycgco and every sample.

4. Wider finding: tagged frames can't be converted (task #76)

Each row is a yuv420p FFV1 file tagged with the matrix through setparams, then decoded one frame to each target.

Tag→ yuv420p→ JPEG→ rgb24→ gray16le→ yuv422ptag cleared first → rgb24
bt709okokokokokok
each of the sixokfailfailfailfailok

Every failure says "Impossible to convert between the formats…". The negotiation lists the matrices the scaler accepts: unknown gbr bt709 fcc bt470bg smpte170m smpte240m bt2020nc. This is the class decode_tag_neutraliser handles for reserved. Task #76 is to clear or map these tags the same way before converting decodes. Until then, WorkerHarness._frameRgb24 clears them itself before the preview's scale. That changes no pixel: the scale names its matrix explicitly, and with the tag cleared the output matches the untagged Y4M through the same scale, md5 for md5.

Limits and what wasn't tested

  • The probe ran on the macOS arm64 FFmpeg only. The other platforms' builds (BtbN on Windows and Linux, martin-riedl x64) are covered by the push-gate test rather than by this report.
  • The heavy fixtures are a real 8-bit 4:2:0 picture whose samples were never encoded in these matrices. The test shows how the preview reads the tag, not that the picture looks right. No real ycgco, bt2020c or ictcp SDR source was available.
  • Deeper formats were not run; the preview's scale is the same filter at every depth.
