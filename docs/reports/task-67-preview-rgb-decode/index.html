Task #67: heavy preview tests decode as the preview converts

2026-11-18 · macOS arm64 (M1 Pro) · deps 1.17.0-rc3 (FFmpeg 9.0.2) · main at 7df4630 · scripts in scripts/, numbers in data/

Decision

Task #56 F8 changed the preview's YUV → RGB step to scale=[in_color_matrix=<tag>:]in_range=tv|pc:out_range=pc:flags=accurate_rnd+full_chroma_int (preview_scale_filter). The heavy tests compared the preview with a decode of the encode or the source that used ffmpeg's default conversion (WorkerHarness.frameRgb24), so one frame no longer read 0.00 against itself. Of 105 heavy test cases that failed on main in the set run here, all but two (an add-on install race and task #64's Unblend fault) failed because of it (table 2).

  • One helper, WorkerHarness.previewFrameRgb24 (and previewScaleFilterFor for a test's own -vf), decodes a frame as the preview converts it: the same scale built from the tags the file carries, the same PNG stage, the same imageToRgb24. Every comparison of a preview with a decode now uses it; comparisons that don't involve the preview keep frameRgb24.
  • No bound was loosened. Lossless preview = encode and preview = source checks now read 0.000 (they read up to 5.1 before), so a 0.5 bound measures the frame again, not the conversion.
  • preview_scale_filter_test.dart (push gate) pins the helper to the Rust source: the appended options, the matrix rule, the range rule and the worker's own test cases.
  • Found on the way and filed as task #73: swscale_input_opts passes ycgco, bt2020c, smpte2085, chroma-derived-* and ictcp to scale=in_color_matrix, which FFmpeg 9.0.2 refuses ("Undefined constant or missing '(' in 'ycgco'"), so an SDR preview of such a source fails.

4. How the helper decides the conversion

  • It reads the tags the decoded file carries. An encode carries the tags the worker stamped, which are output_color_metadata(), the same decision the preview's conversion reads. A source carries the job's input tags, which an every-pass-off preview reads. So no test holds a copy of the worker's output-tag logic, and a wrongly stamped tag still fails the comparison.
  • The matrix is stated unless it is missing, unknown to FFmpeg or rgb; the range is pc for pc/jpeg/full, else tv; then out_range=pc:flags=accurate_rnd+full_chroma_int. That is swscale_input_opts and preview_scale_filter rule for rule.
  • A PQ/HLG file throws: the preview tone-maps those (display_tonemap_filter), and the HDR tests compare the preview with the app's before frame, which uses the same chain.
  • A reserved tag is cleared first with ColorTags.decodeNeutraliser, as the worker's decoders clear it.

Limits

  • One platform. Windows, Linux and macOS x64 have the same FFmpeg 9.0 series, but only the nightly run shows they convert identically; it has not run on this branch yet.
  • Table 1 is one frame per fixture; the difference depends on chroma detail, so other content lands elsewhere.
  • The before values for colourisation, AV1, upscale/resize, frame mapping and VFR were not collected (setup race, or not in the before set). Those tests pass after.

Not tested

  • The format sweep (preview against preview, so unaffected; only its comment changed).
  • HDR tests (they compare preview with before frame through the tone map, unaffected).
