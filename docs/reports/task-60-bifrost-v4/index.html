Task #60: Bifrost v3.0 → v4.0

2026-11-17 · macOS arm64 (M1 Pro) · deps 1.16.0 / 1.17.0-rc2 bundles · scripts in scripts/

Decision

Every platform takes Bifrost 4.0 from its PyPI wheels, installed under the old file names (libbifrost.dylib, libbifrost.so, bifrost.dll). Before, macOS and Linux built bifrost.c from the v3.0 tag and Windows took v3.0's GitHub 7z. v4.0 publishes no GitHub release asset, so the wheel is the one source every platform can share.

  • v3.0 left the chroma past the last whole 4×4 luma block uninitialised (upstream issue #1, "green line at the bottom"): different output run to run at width 98, 718 and at 720×486. v4.0 starts chroma as a copy of altclip (default: the clip), so that strip is the input, unfiltered, every time.
  • v4.0 runs at 8–16 bits, scaling luma_thresh and variation (8-bit units) itself. The template's 8-bit detour (run_within on an 8-bit copy, task #37/#48) is gone: the contract now accepts every depth, so run_within converts nothing.
  • One refusal remains: with interlaced=True (the default) v4.0 calls SeparateFields itself, so 4:2:0 at a height ≡ 2 mod 4 (720×486) is refused, as with v3.0. The contract pads such a frame to whole field chroma rows (height_step=CHROMA, task #57's step) and crops back.
  • Task #56's padding to whole blocks (width mod 4, height mod 8), a guard against the v3.0 fault, is not needed with v4.0 and was dropped when this branch was rebased onto #56 and #57; only the height step above remains.

1. Arguments

Identical signature and defaults (luma_thresh 10.0, variation 5, interlaced True, 4×4 blocks):

clip:vnode; altclip:vnode:opt; luma_thresh:float:opt; variation:int:opt;
conservative_mask:int:opt; interlaced:int:opt; blockx:int:opt; blocky:int:opt

The template's call is unchanged.

4. Parity at depth

probe.py dump + parity.py: 720×480, frames 2–9, interlaced=True. The change at depth (out − in, in 8-bit levels) against the 8-bit run's change on the same picture rounded to 8 bits.

InputLuma bit-exactChroma changedDecisions differing from 8-bit|Δ − Δ8| mean / max (levels)
16-bit, low bits zero (8-bit content)yes79.5%0.00%0.101 / 0.8
16-bit, real low bitsyes79.5%0.10%0.142 / 19.0
10-bit, real low bitsyes79.5%0.11%0.130 / 19.0

The same for 4:2:0 and 4:2:2. On 8-bit content at 16 bits the decisions are identical; the 0.1 level is the half-level rounding of Bifrost's averages, which 16 bits keeps and 8 bits rounds. With real low bits, 0.1% of chroma samples belong to blocks whose luma difference sits on the threshold and tips the other way: that is the max of 19. The old run_within path decided on an 8-bit copy, so it differed from native processing in exactly these blocks. Chroma Bifrost leaves alone is the altclip copy, so it is bit-exact natively, which is what run_within's delta was for.

The heavy test Bifrost runs at the source depth (task #60) (integration_high_bit_depth_filters_test.dart, the crawl fixture at 352×288, 10-bit = 8-bit × 4 + 0 or 1) measures the same through the worker: luma unchanged; U/V decisions differing from the 8-bit run in 171–188 of 1,267,200 samples (4:2:2) and 421–433 of 633,600 (4:2:0); mean |10-bit/4 − 8-bit| 0.127–0.130 (0.125 of it is the fixture's own low bits); 5,000–5,800 changes per plane not a multiple of 4 (it ran at 10 bits); preview = encode (0.000). The 8 vs 10-bit parity pass reads 0.174 (tolerance 2.0).

Limits: one real capture with a synthetic shimmer, not a population of rainbowed tapes; the threshold flips depend on how much content sits near luma_thresh.

7. Licence and credit

Still WTFPL. v4.0 adds a LICENSE file (the WTFPL text, no holder) and license = "WTFPL" in pyproject.toml; v3.0 had none. Authorship, as upstream states it: the readme says Bifrost was created by Fredrik Mellbin; the 2016 VapourSynth port is cantabile's (dubhater's handle); the API 4 conversion (2024) and every v4.0 commit (2026) are Fredrik Mellbin's, who is the wheel's listed author.
