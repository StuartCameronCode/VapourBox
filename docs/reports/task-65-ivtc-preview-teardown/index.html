Task #65: the IVTC preview's vspipe crash, and IVTC parity

2026-11-18 · GitHub-hosted runners (ubuntu-24.04, macos-15-intel) and macOS arm64 (M1 Pro) · deps 1.17.0-rc3 · scripts in scripts/, raw counts and a backtrace in data/

Outcome

  • vspipe R78 counts a frame done before it writes it. A one-frame run whose frame is ready almost immediately can have its main thread tear the script down while the frame callback is still writing: SIGSEGV in outputFrame / frameDoneCallback. Fixed upstream in 4ff3f8a0, first released in R80.
  • Task #46's IVTC preview made its frame ready at once: it read VDecimate's drop with get_frame() while the script was evaluated, which computed the target's graph in advance. Under load, 2–3% of x86 IVTC previews crashed. The read is now made inside the graph (a FrameEval with prop_src), giving 0 crashes in 3960 IVTC previews. It picks the same frame: 120 of 120 previews were byte-identical to the old template's on macOS arm64.
  • Not gone for every preview: Bwdif, which doesn't decimate, crashed 2 times in 1200 runs on macOS x64, once with each template. Only a VapourSynth upgrade to R80+ removes it (filed as a follow-up).
  • The 8 vs 10-bit IVTC parity case had no pulldown to remove. Its master is progressive, so IVTC keeps frame 12 unchanged (0.000 levels from the passthrough). It passed only while the preview showed the wrong frame (the bug #46 fixed). It now runs on the master telecined 3:2.

3. Where it crashes

Of the 44 Linux cores, 40 show the crashing thread in outputFrame (23) or frameDoneCallback (17) while the main thread is in freeScript → vpy4_freeScript → Python's garbage collector. The remaining 4 are unsymbolised: the process was already unmapping its libraries. Example: data/backtrace-example.txt.

vspipe R78's frameDoneCallback (abridged):

if (rnode == data->node) data->completedFrames++;   // no lock, first thing
...
outputFrame(frame, data);                             // writes the frame
...
if (data->totalFrames == data->completedFrames ...) {
    std::lock_guard<std::mutex> lock(data->mutex);
    data->condition.notify_one();
}

and outputNode:

std::unique_lock<std::mutex> lock(data->mutex);
for (n ...) getFrameAsync(n, node, frameDoneCallback, data);
data->condition.wait(lock, [&]() { return data->totalFrames == data->completedFrames ...; });
// ... then output closes and the script is freed

wait evaluates its predicate before it first sleeps. If the one frame completes between getFrameAsync and that check, the predicate is already true while the callback is still inside outputFrame, and main goes on to free what the callback is using. Upstream's 4ff3f8a0 ("Fix many rare issues found by AI", 2026-09-06, in R80) moved the increment to the end of the callback, under the mutex, with the comment "Counting at entry, as this used to, let the waiter return while the last frame was still being written."

The race needs the frame to finish within the main thread's few instructions between request and check, or while it is descheduled. Task #46's evaluation-time get_frame() made that likely: the target's frames were already in the cache, so the output frame came back at once. CPU load, which deschedules main, raised the rate from 0 to 2–3%.

4. The change

  • _preview_decimate_out keeps the frame where the target would be (c[_j], still tagged) instead of reading it, and _preview_decimate_pick at the end of the script returns FrameEval(c[keep], pick, prop_src=probe). The pick chooses c[keep] or c[after_drop] from the tag and prints PREVIEW_DECIMATE:corr=N, which the worker's stderr reader already collects. The constant cases (the cycle's last frame, past the clip's end) still decide when the script is evaluated, without a frame.
  • Same picks: on macOS arm64 the old and new templates gave byte-identical PNGs and the same drop report for all 30 ProRes and 90 AVI frames.
  • test_259: no get_frame( in the template outside the border colour's one-frame BlankClip swatch. A heavy smoke test repeats the ProRes preview 36 times, three at a time. At a 2% rate it would miss the fault about half the time, so test_259 is the guard.

Limits

  • The rates are for four previews at a time with CPUs held at 60% on hosted runners; they say the fault is real and which template triggers it, not how often a user sees it.
  • No Windows run: its vspipe is the same R78 source, in the wheel.
  • Apple Silicon was not run under load natively. arm64 never failed in the nightly.
