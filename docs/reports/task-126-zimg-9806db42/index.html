What changes

Linux VapourSynth links R78's subprojects/zimg.wrap statically, pinned since task #103 to zimg 67e06032, whose graphengine submodule is cb5b2ce1 (ZIMG_COMMIT / ZIMG_GRAPHENGINE_COMMIT in Scripts/download-deps-linux.sh).

  • zimg 9806db42 ("Update graphengine", 2026-11-22) is one commit on top of 67e06032, and that commit changes only the submodule pointer. zimg's own code is the same. Master was rewritten to it: e2e43d09, the commit that broke rc3 (task #103), is no longer on master.
  • graphengine 308d3735 is cb5b2ce1 plus 15 commits: the 13 that task #109 bisected (7014d9f2 … 91c6af4c, among them the faulty f6211289), a test-app fix (e9b10267) and the fix. Library files changed: graph.cpp, node.cpp, state.h, include/graphengine/graph.h and types.h; none added, so R78's overlay meson.build, which lists the sources, still builds it.
  • The fix ("Fix uninitialized simulation parameters for fused nodes") moves three lines of compile_simulation_result above if (!live_rows) continue;:
+			node_result.context_size = (sim.context_size(id) + ALIGNMENT_MASK) & ~static_cast<size_t>(ALIGNMENT_MASK);
+			node_result.initial_cursor = sim.cursor_min(id);
+			sat_add(result.tmp_size, node_result.context_size);
+
 			unsigned live_rows = sim.live_range(id);
 			if (!live_rows)
 				continue;

So a fused node's context counts in tmp_size again, as task #109's patch did by a different route (it skipped only the cache loop). The minimal repro asks for 1216 bytes with either.

How it was measured

scripts/compare.sh WORK OUT builds two zimgs with task #109's build.sh (R78's overlay meson.build on the zimg tree, a static release library) and runs task #109's cases.tsv through each with its run_cases.sh, one process per graph:

  • A: zimg 67e06032, graphengine cb5b2ce1 (shipped); B: zimg 9806db42, graphengine 308d3735 (candidate). The script first checks each zimg commit's submodule pointer, which is what the wrap's recursive clone checks out.
  • vs build (NDEBUG, as R78 ships it): the canary, guard bytes around the buffer; once with --cpu auto64 (VapourSynth's default) and once with --cpu none (zimg's C kernels).
  • guard build (NDEBUG off): graphengine's own guard pages between the buffer's regions, which caught all 36 error-diffusion graphs at 91c6af4c in task #109.
  • asan build: AddressSanitizer on a buffer of exactly tmp_size (--exact).
  • Pictures: tmp_overrun.c's new --digest option prints a 64-bit FNV-1a hash of every destination plane's visible samples (stride padding left out). Each graph converts the same seeded random source frame, so A and B are compared graph by graph. The hash is not trivially constant: on macOS arm64 the 158 graphs give 125 distinct hashes, and 64 of them differ between auto64 and none (NEON against C).
  • upstream_repro.c, task #109's minimal repro (GRAY16 → GRAY8 at 96x64, error diffusion), linked against each build.

The 158 graphs: format, depth and subsampling conversions, colour-space changes, resizes and every dither type, progressive and interlaced (two field graphs, as VapourSynth runs them), at 96x64, 98x64 and 720x480; 36 of them dither with error diffusion (task #109, "The repro").

The arm64 gcc ASan reports (task #115)

Linux arm64 with gcc 13 reports a heap-buffer-overflow on 32 graphs, at A and at B alike, and they are the same 32 (data/linux/…/compare-arm64-gcc-13/A-asan.tsv, B-asan.tsv): the 4:2:0 graphs that convert the matrix from an integer format, rgb24 → 4:2:0 at 8 and 10 bits (14), 4:2:0 → rgbs (12) and 4:2:0 470bg → 709 (6 of 8), at every size, progressive and interlaced. The same conversions from rgbs, the depth-only 4:2:0 graphs and the error-diffusion ones (20 graphs in all) are not flagged. Task #109 saw the same 32 at every graphengine commit. New here: clang 18 on the same arm64 runner image reports none, nor does any other platform or compiler, and the canary and guard pages see nothing on any graph. So it follows the compiler, not the architecture or graphengine. Whether it is a real read past a buffer that only gcc's code makes, or an ASan false positive, is task #115's question; it does not separate A from B.

Temporary buffer size

B asks for less on every graph (158 of 158, every platform): from 0.04× (cs-to-rgbs-yuv444p16-720x480i, 17984 → 704 bytes, everywhere) to 0.998× on Linux x64 and 0.992× on arm64 (cs-from-rgbs-yuv420p8-720x480p), median 0.89× on Linux x64 (bm3d-down-720x480i, 6976 → 6208) and 0.86× on arm64, Linux and macOS; the 158 together 5.09 MB → 4.61 MB on macOS arm64. That is graphengine's range doing what it set out to (fused nodes no longer get cache buffers), now with the contexts counted.

Decision

Bump, in deps 1.18.0-rc5 (the user's choice of release, 2026-11-27). For: the candidate passes everything #109 measured, draws identical pictures, uses less memory, and is what upstream master and any VapourSynth built from its wrap now get. Against: our pin is good and nothing is broken today, and it changes libvapoursynth.so.4 on Linux, so it needs a deps release. The arm64 gcc ASan reports are the same at both commits, so they don't weigh either way.

Done in task #127, after task #111 merged: the two pins and their comment in download-deps-linux.sh, a guard in zimg_pin_test.dart that refuses task #109's bad graphengine range (f6211289 … e9b10267), and the bundle A/B below.

Limits

  • The pictures are compared through zimg's C API, built as R78 builds it. The same library goes into libvapoursynth.so.4. The bundle A/B (task #127) checks that the bundle runs and passes the test suites; it does not compare pictures byte for byte.
  • Each graph converts one seeded random frame. A difference that only some content would show is not ruled out, but zimg's own code is unchanged and graphengine's changes are to buffer planning, which the 158 graphs exercise.
  • The canary sees writes past either end of the buffer, and the guard pages writes between its regions; neither sees a write inside the region that should hold it. ASan covers reads and writes past the buffer's ends only.
  • Correction, during the work: the first macOS x86_64 attempt reported all 158 graphs as aborts at A and B. They were not zimg's: the x86_64 binaries could not run at all (no Rosetta, "Bad CPU type"). compare.sh now runs each binary once first and stops if it can't.
  • Not run: macOS x86_64 (Rosetta is not installed on the machine used; Linux x64 covers x86, and macOS ships zimg releases, not this commit), and Windows (ships the R78 wheel's zimg). --cpu auto (128-bit) was not run; auto64 is VapourSynth's default.
  • The arm64 runners' CPU model is not printed by /proc/cpuinfo.
