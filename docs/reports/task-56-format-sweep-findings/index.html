Format sweep findings: nine faults, fixed

2026-11-17 · task #56 (findings of task #47's generated format sweep) · deps 1.17.0-rc2 · measured on an Apple Silicon Mac (M1 Pro): the macOS arm64 bundle natively and the macOS x64 bundle under Rosetta 2. CI's push gate runs the sweep natively on Linux x64, macOS x64 and Windows.

Outcome: all fixed; every knownFailures entry the sweep held is gone.

  • F9, the one that mattered most, was not an x86 bug. MVTools divides by zero when a picture is exactly two motion blocks tall. x86 traps (vspipe dies, SIGFPE). On arm64 the division returns 0 and the bottom block row is blended with the wrong window, up to 127 levels off, with no error. One block row or column is just as wrong on every CPU. Every MVTools caller now pads a picture under 64x96 (plugin_formats.mvtools_blocks).
  • F1, F2, F6 are frame-size refusals, now Contract steps that run_within() pads to. They use task #57's pad_around, taken verbatim.
  • F3/F3b, F4, F5 and F8 were fixed in an earlier commit; their numbers are here.
  • F7: CLAHE now decides on an 8-bit copy at every depth. Its parity went from 3–22 levels to about 1. It comes with a trade-off on smooth ramps, stated in F7.

F9 — MVTools on a picture one or two block rows tall

Seen: on every x86 push gate (Linux x64, macOS x64, Windows), QTGMC Very Fast, Super Fast, Ultra Fast and Draft failed every 96x64 / 98x64 row with "vspipe failed: Warning: Plugin … already loaded". arm64 passed. Those four presets alone use 32-pixel blocks with an overlap of 8.

Cause (vapoursynth-mvtools master 17250aa, unchanged since v24): Compensate, Degrain and BlockFPS choose each block row's overlap window with

int wby = ((by + nBlkY - 3) / (nBlkY - 2)) * 3;   // src/MVCompensate.cpp:269, MVDegrains.cpp:255, MVBlockFPS.cpp:541

where nBlkY = (H − overlap) / (blksize − overlap). Upstream already replaced the horizontal twin. With nBlkY == 2 the division is by zero, and with nBlkY == 1 the only row gets the bottom edge's window.

Measured: flat grey clip, Compensate and Degrain1, every vector zero

A correct result returns the input exactly. "max diff" is the largest luma difference from the input in 8-bit levels. Exit −8 is SIGFPE. Data: data/mvtools_two_rows_{x64,arm64}.tsv; script scripts/mvtools_two_rows.py.

Across all 41 failing cells of each table, the guard brings every one to exit 0 and difference 0. Bare QTGMC under Rosetta: Very Fast and Draft at 96x64 SIGFPE; through the template's guard they run, at 4:2:0 8-bit, 4:2:2 10-bit, 4:4:4 and 4:2:0 16-bit.

Fix

  • Two block rows means 2b − o ≤ H < 3b − 2o, and one column W < 2b − o. Blocks go up to 32 (QTGMC's maximum; every other pass picks smaller) and overlap is at least 2. So 94 rows and 62 columns are always safe. MVTOOLS_MIN_ROWS = 96 and MVTOOLS_MIN_COLS = 64, rounded up to whole field chroma samples.
  • mvtools_blocks(clip, fn) pads with pad_around (rows repeat with period 2, so fields stay fields) and crops back. A clip at least that big gets no node, so no real source's script changes.
  • Wrapped: QTGMC (inside its run_within), MCTemporalDenoise, SMDegrain, MCDegrainSharp, SpotLess, mClean and TemporalDegrain2.
  • test_256 fails on any MVTools overlap caller in the template outside the helper, and on any template module that calls Compensate, Degrain or BlockFPS without being one of the wrapped ones.

Limits: real sources are never this small, so this mattered for the sweep's tiny fixtures and for a thumbnail-sized clip, not for a capture. Rosetta runs x86 code but is not a native x86 run: CI's push gate is the native proof on three x86 platforms. Not done: reporting the one-line fix upstream (wby = by == 0 ? 0 : by == nBlkY - 1 ? 6 : 3, with one row needing its own window), or patching the from-source deps builds. Either is the owner's call.

F9b — the preview hid the crash

When vspipe failed, the preview reported every line vspipe had printed to stderr, which starts with plugin warnings, and dropped the exit status. The encode path already reported it properly (task #28). The preview now uses the same vspipe_failure_message. A native crash reads "vspipe exited with signal 8 (SIGFPE) — a native crash inside vspipe or a plugin; no Python error was printed". A Python error keeps its exception and traceback. The macOS "already loaded" warnings themselves come from the worker setting VAPOURSYNTH_EXTRA_PLUGIN_PATH on macOS/Linux; that is task #61.

F1, F2 — a 4:2:x picture whose width is 2 mod 4

  • F1, MCTemporalDenoise. It pads to its mod with xf = ceil(w/mod)·mod − w + mod and crops xf/2 each side. At a width that is 2 mod 4, xf/2 is odd, and std.Crop refuses an odd chroma offset ("cropped area needs to have mod 2 width offset"). An 854x480 source does this.
  • F2, QTGMC Super / Ultra Fast. With SrchClipPP == 1, havsfunc does resize.Bilinear(w // 2, h // 2) for the motion search. 98 // 2 = 49 is an odd chroma width ("Resize error 1027").

Fix: Contract width_step=CHROMA, which run_within pads to. MCTemporalDenoise always gets it. QTGMC gets it only when SrchClipPP is 1 (QTGMCParameters::effective_srch_clip_pp, the havsfunc.QTGMC[SrchClipPP=1] contract; test_257), because padding the width moves other presets' pictures well inside the frame:

F6 — Bifrost reads uninitialised chroma

Bifrost v3.0 (bifrost.c) creates its output frame with only the luma plane copied, and writes chroma one whole 4x4 luma block at a time (per field when interlaced=True). Chroma past the last whole block is never written, so it holds whatever memory the frame got (upstream issue #1, "green line at the bottom"). The contract now pads to width_step=4, height_step=8. Data: data/bifrost_repeat.tsv; script scripts/bifrost_repeat.py, distinct MD5s over 3 fresh vspipe runs.

At 98x64, this synthetic clip happened to repeat; the sweep's fixture did not (thousands of samples apart run to run). Uninitialised memory can repeat by chance, so a "1" is evidence, not proof; the source is the proof. 720x486 4:2:2 is NTSC D1, i.e. v210 and ProRes captures, which got garbage in their bottom chroma rows and a preview that differed from the encode. Task #60 (Bifrost v4.0, which initialises chroma) can drop the steps.

F3, F3b — Rotate / Flip on a still-interlaced picture

A quarter turn kept _FieldBased. The turned picture's "fields" were columns, and the geometry block's format restore resampled them per field: 98x64 TFF 4:2:2 became 64x98 4:4:0, and a 49-line field has no whole chroma height, so "Resize error 1027". A vertical flip or half turn of an even-height TFF frame is BFF, but the encoder was told TFF. ScriptGenerator::field_order_at_framing is now the one decision: a quarter turn clears the flag, one vertical mirror swaps it. The geometry block stamps it before its format restore, and every reader after Rotate / Flip uses it (output_field_order, the border alignment, the crop and resize steps). Tests: test_253, test_221; the sweep's rotation rows pass.

F5 — resizing still-interlaced 4:2:0 to a height ≡ 2 mod 4

The resize rounded both axes to 2. A still-interlaced 4:2:0 picture needs a height that is a multiple of 4 (each field a whole chroma height): 720x480 TFF resized to width 160 asked for height 106 and failed. ScriptGenerator::framing_steps (shared with the crop detector) gives the step, and the template and CropResizeParameters::output_size_stepped round to it. Test: test_254.

F4 — Deband turned an 8-bit source 16-bit

f3kdb's output_depth defaults to 16, and Color Format "original" kept it, so an 8-bit 4:2:0 job encoded as yuv420p16le while encoder_input_pix_fmt still said 8-bit. Now "original" dithers back to the source's depth after the passes ({{#DEPTH_RESTORE}}; depth only, never family or subsampling). Deband's setting is relabelled "Working Depth": the passes after Deband still work at 16 bits. Test: test_255; the sweep's Deband rows pass the PNG-depth check. Decided this way rather than changing the default because every saved preset stores outputDepth: 16, which can't be told apart from a choice.

F7 — CLAHE on genuinely deep content

vszip's clip limit is a whole count per histogram bin, max(1, limit × tile pixels / bins). With 65536 bins, the per-bin limit that would match the 8-bit picture's is a fraction it can't hold. The old template scaled limit << (16 − content depth), which assumes each 8-bit level's samples fill its sub-bins evenly. Genuine deep content doesn't, so it was barely clipped. Now CLAHE runs on an 8-bit copy and only its change is added at the clip's depth (plugin_formats.change_at, the same conversions as run_within). Data: data/clahe_parity_*.txt; script scripts/clahe_parity.py.

The trade-off: samples of one 8-bit level now all get the same change, so a smooth deep ramp steps about as the 8-bit result does. Largest step between neighbours on a noiseless 40-level ramp: 8-bit CLAHE 3.0 levels; 16-bit, before 0.14, now 2.06. After a 13-pixel blur: 8-bit 0.23; 16-bit before 0.11, now 0.21. A dithered 8-bit copy was tried and is worse (2.95 / 0.36). The deep result is never banded worse than the 8-bit output would be, but on a clean deep gradient it is no longer smoother. The old method's smoothness came with a picture 4–22 levels from what the same setting does at 8 bits.

At 96x64 (12x8-pixel tiles) the same picture is still about 5 levels from 8-bit (was 22–35). The sweep's own fixtures pass its parity check at its 4.0 tolerance.

F8 — the preview's RGB conversion by depth

swscale converted 8-bit 4:2:0 to RGB on its fast path with nearest-neighbour chroma, and deeper formats with interpolation. The worker's preview now passes flags=accurate_rnd+full_chroma_int for every SDR source (preview_scale_filter).
