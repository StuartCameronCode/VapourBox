Sources stored off the chroma grid

2026-11-22 · task #97 (found by task #86) · measured on an Apple M1 Pro, macOS arm64 deps 1.16.0 (FFmpeg 9.0.2) and 1.17.0-rc1 · every number below comes from a script in scripts/.

Outcome: such sources are processed, and kept at their stored size wherever the encoder can store it. A subsampled picture whose size is not a whole number of chroma samples (4:2:0 with an odd width or height, 4:2:2 with an odd width, 4:1:1 with a width off a multiple of 4) is stored and decoded by FFmpeg, but VapourSynth refuses a clip of that format and size, so every preview and encode of one failed. pipe_source now reads it at the stored size and pads it onto the grid, repeating the last column and row; the encoder's crop takes the pad off again. An FFV1 encode is the source sample for sample. An encoder that can't store the size (x264 and x265 in 4:2:0/4:2:2, HuffYUV, v210, VideoToolbox and the other hardware encoders) gets the next size up, with the repeated line, and the job log says which encoders keep the exact size.

4. The fix, and why it pads in the reader

  • FFmpeg's rawvideo rounds a chroma plane up (63x33 4:2:0 carries 32x17 chroma samples: 3,200 bytes for 64x33, 3,040 for 63x32, 4,064 for 63x32 4:2:2, 3,040 for 63x32 4:1:1), and that is exactly the chroma of the grid-padded frame. So pipe_source copies every plane as stored and only repeats the last luma column / row into the pad (each field's own last row on an interlaced clip). The decoder is unchanged: it decodes the stored frame and its size guard still holds it to the probed size.
  • Not the decoder's pad filter: FFmpeg's pad floors an odd input width and writes black into the last real column (measured on 63x32: column 62 became 16). It pads an odd height exactly.
  • Not refusing the source (the other option in the plan): VP9/AV1 screen recordings are ordinary inputs.
  • The sizes are the worker's: VideoJob::grid_output rounds the picture up to every grid it must sit on (the pipe's, the output format's, the encoder's step), the script pads to that before the output conversion and raises if the clip is any other size, and the encoder crops to the encoder's own step. A pipeline that reshapes the frame (Rotate / Flip, resize, upscale, borders) decides the size itself, as before.

6. A conversion trap: FFmpeg's RGB of an odd-height 4:2:0 frame

The first preview = encode check failed by 4–8 levels. The preview was right: scripts/before_frame_options.py shows that FFmpeg's own YUV → RGB conversion of a 64x33 4:2:0 frame differs from the same frame padded to 64x34, converted, and cropped by 3.4 levels on average (max 106), through the whole picture. Its scaler spreads the 17 chroma rows over 33 luma rows, a vertical stretch of the chroma, where the samples belong to 34. The worker's preview converts the padded frame, so it is the correct one; the heavy test now builds its reference from an on-grid twin padded in Dart, and the preview matches it within 0.5 levels. A player that converts an off-grid file with FFmpeg's scaler shows that stretch whatever produced the file; the file's samples are the source's.

Decisions

  • An encoder that can't store the size gets the next size up, never a dropped real line and never a refusal (the user's choice, option A). This changes one existing behaviour: an odd-sized 4:4:4 source into VideoToolbox was silently 1 px smaller in each direction and is now 1 px larger, with a repeated line.
  • Reshaping passes keep their own sizes: a right/bottom crop rounds outward by the repeated line, a resize reads the real picture, Rotate / Flip and borders leave the repeated line in the picture; each is logged.
  • No schema bump: the worker computes the pad at job time from the job's format and size, so a model probed before the field existed still processes correctly; only the app's HDR before frame needs a re-analysis.
  • No format-sweep row: every pass sees an ordinary on-grid padded frame, which the sweep already covers.

Not tested

  • NVENC, QSV and AMF with an off-grid size (no hardware); they are held to even sizes.
  • Windows and Linux: the push-gate and heavy tests run there in CI; everything above was measured on macOS arm64.
  • The AI upscalers and edge-directed upscaling on a padded frame: they enlarge the repeated line with the picture (logged), and a following resize reads the scaled real window.
  • A real VP9/AV1 screen recording (the fixtures are synthetic, made with the bundled encoders).
