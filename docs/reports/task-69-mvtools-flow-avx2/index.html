MVTools FlowFPS / FlowInter corrupt the heap below 8 block columns on x86

Task #69, 2026-11-19. Measured on GitHub's ubuntu-24.04 runners (Intel Xeon 6975P-C), deps 1.18.0-rc1 linux-x64 (MVTools master built from source, havsfunc r31), valgrind 3.22 memcheck, through .github/workflows/repro-native-crash.yml (inputs bisect, bisect_script, probe_calls). Source read from dubhater/vapoursynth-mvtools master. The guard was also run on macOS arm64 (where it is inert).

Outcome

  • Cause: MVTools' AVX2 vector upsizer, simpleResize_int16_t_avx2 (src/SimpleResize_AVX2.cpp, master and v24 alike), does each row's tail as one more 8-sample step ending at src_width, the number of block columns. With fewer than 8 columns the step starts before its malloc'd row buffer: it reads before the source rows and writes over malloc's chunk header. Its 8-bit twin (masks) does the same with 4 samples. On any x86 CPU with AVX2 and opt=1 (MVTools' default).
  • Fix: the template passes opt=_pf.mvtools_flow_opt(width, blksize, overlap) to the Frame Rate mv.FlowFPS and the VFR gap mv.FlowInter. It is False (MVTools' C upsizer, what arm64 runs) exactly when fewer than 8 block columns cover the picture, else True, MVTools' default. So every job that worked before generates the same picture; only the argument is new in the script.
  • Who could hit it: the probe (64x48 at 16/8, every cell, every run) and real jobs with a narrow picture and a large Frame Rate block: widths ≤ 64 at 16/8, ≤ 176 at 32/8 (QCIF, a real phone/3GP size), ≤ 224 at 32/0.
  • Not fixed here: QTGMC's internal mv.Mask (InputType 2/3, BlockSize 32) hits the 8-bit twin below 4 block columns (widths under 80 at 32/16 after mvtools_blocks()' padding). havsfunc makes that call, so the template can't pass opt. Filed as task #79.

The fault, in the source

int16_t *workp = (int16_t *)malloc(simple->src_width * sizeof(int16_t));
...
const int src_width_sse2 = simple->src_width & ~(pixels_per_iteration - 1);   // 8
for (int x = 0; x < src_width_sse2; x += pixels_per_iteration)
    simpleResize_int16_t_vertical_8px_avx2(workp, srcp1, srcp2, x, dwords_weights_v);
if (src_width_sse2 < simple->src_width)
    simpleResize_int16_t_vertical_8px_avx2(workp, srcp1, srcp2, simple->src_width - pixels_per_iteration, ...);
    //  _mm_loadu_si128(&srcp1[x]) ... _mm_storeu_si128(&workp[x], dst)   with x = src_width - 8 < 0
...
free(workp);

src_width is nBlkXP for FlowInter / FlowFPS (simpleInit(&d.upsizer, nWidthP, nHeightP, nBlkXP, nBlkYP, …)): Analyse's nBlkX = (W − o) / (b − o), grown while nBlkXP·(b − o) + o < W. At 64x48 with 16/8, nBlkXP = 7, so the tail step is at x = −1.

Task #66's core matches: _int_free_merge_chunk(size=0x3000000000020) ← free ← mvflowinterGetFrame (repro run 44089474128). 0x20 is the chunk of a 14-byte malloc (7 × int16), and the top 16 bits are the sample written at workp[−1]. free(workp) is the resizer's last statement, a tail call, which is why the caller shows as mvflowinterGetFrame. Whether the corrupted size makes glibc abort ("free(): invalid size") or crash later depends on the value, hence SIGABRT or SIGSEGV.

Widths that corrupt the heap

bad ⇔ nBlkXP < 8 ⇔ W ≤ 7·(b − o) + o. Only the width matters. The horizontal tail uses the picture's padded width (or its chroma width), never below 8 at a size MVTools accepts.

Correction, kept visible. The first matrix (run 44498321055) showed FlowInter and FlowFPS clean at 64x48 with opt=1, against the diagnosis. The script was at fault. Its clip moves 3 px a frame over a fine texture, and at MVTools' default thscd1=400 every frame counted as a scene change (mv.SCDetection sets _SceneChangeNext on every frame). FlowInter and FlowFPS then blend the two frames and never call the upsizer: FlowInter's output differs from a plain std.Merge blend by 0.0019 at 400 and by 0.049 at 16320 (macOS arm64). flow.vpy now defaults to thscd1=16320, MVTools' maximum, and the rows above are from that version. The probe's own clip keeps its vectors, which is why it crashed.

The committed table already said ok for these cells (measured on macOS arm64, which has no AVX2 path), so it is unchanged. --quick (the push gate) now measures 64x48 for both calls at 8 and 16 bits, so losing the guard fails every Linux x64 push, not only the nightly.

Decisions

  • A template argument, not a deps patch. Windows and macOS x64 ship MVTools v24 prebuilt, which has the same code, and Windows has no from-source path for MVTools, so a patch would reach only Linux and macOS arm64 (which doesn't need it), and only with a deps release. opt=False adds no node and changes only the SIMD choice, only where the AVX2 path is broken.
  • Not padding the width (as mvtools_blocks() does for Degrain/Compensate): it would need up to 225 columns at 32/0 and would move the motion search at the edge.
  • opt=False also selects MVTools' C blend functions for that call. At the affected widths, x86 output changes from heap-corrupting to the C result (what arm64 already gives). Every other width keeps opt=True and its output.
  • Guarded by tests: test_260 (Rust) fails on any Flow / FlowFPS / FlowInter / FlowBlur / Mask / BlockFPS call in worker/templates/ without the guard, and checks the generated FlowFPS and VFR-gap scripts. plugin_format_contracts_test.dart checks the helper against MVTools' arithmetic and runs both calls through it at 64x48 and 176x144. On an AVX2 x86 runner, a lost guard would crash that process.

Not tested

  • arm64 under valgrind: clean by construction (meson builds SimpleResize_AVX2.cpp on x86 only, and the C simpleResize<> stays within [0, src_width) by reading), not by measurement.
  • Windows and macOS x64 (MVTools v24): same source, not run under a memory checker. macOS x64 crashed once in mvflowinterGetFrame in task #66's runs.
  • Valgrind sees only the paths a run takes: one clip, 5 frames, the formats listed.
  • FlowBlur and BlockFPS are not called by any template; the guard rule covers them if one ever is.

Upstream issue (draft, not filed)

simpleResize_int16_t_avx2 / simpleResize_uint8_t_avx2 write before workp when src_width < 8 / < 4

The vertical pass handles the row's tail with one more step at src_width - pixels_per_iteration.
When src_width (the block-column count) is below pixels_per_iteration, x is negative: the
step reads srcp1[x], srcp2[x] before the row and stores to workp[x] before the malloc'd
buffer, corrupting the heap (glibc: "free(): invalid size", or a later SIGSEGV). Reproduce:
FlowInter or FlowFPS on a 64x48 clip with Analyse(blksize=16, overlap=8) (nBlkXP = 7), opt=1,
on an AVX2 CPU; valgrind reports invalid reads and writes in simpleResize_int16_t_avx2.
mv.Mask with nBlkX < 4 hits the uint8 version. Suggested fix: fall back to the C
simpleResize<> when src_width < pixels_per_iteration (in simpleInit, or per call).
