14-bit sources: QTGMC failed at every preset

2026-11-15 · task #23 · deps 1.16.0 · measured on an Apple Silicon Mac (macOS arm64 bundle); macOS x64 measured by task #19 (fmtconv report); Windows and Linux are covered by the nightly heavy run, not measured here

Outcome: built. fmtconv's fmtc.bitdepth has no 14-bit integer output, in r31 and git-18a9cecb alike. havsfunc goes back to the clip's own depth through it in Bob, Resize and Deblock_QED, so on a 14-bit clip QTGMC failed at every preset, as did the Anti-aliasing pass's santiag and the Deblock pass's QED method. A 14-bit source was piped natively (yuv4xxp14le), and a 13-bit depth rounded up to 14.

pixel_format::decode_pixel_format, the one place the worker picks the pipe format, now decodes 14-bit (and anything rounding to 13 or 14) as 16-bit. The conversion loses nothing and costs no speed (both depths use 2 bytes a sample). Every consumer follows: the encode and preview decoders, both templates, the encoder's input format and the three detectors. The one visible effect: with Output Colour Format original, a 14-bit source comes out 16-bit, which only FFV1 and FFVHuff store as such.

3. The decoder's 14 → 16-bit conversion loses nothing

scripts/shift_check.py decodes one frame of a 14-bit 4:4:4 FFV1 file twice, as yuv444p14le and as yuv444p16le, and compares each sample.

source rangesamplesexact x << 2y >> 2 == xmax distance from x·65535/16383
limited (tv)304,128304,128304,1283.00
full (pc)304,128222,348304,1283.00

Limited range is a pure shift. Full range is scaled toward 65535/16383, within 3/65535 of the ideal curve (less than one 14-bit step, which is 4). In both cases every 16-bit sample holds the source's 14-bit value in its top 14 bits, so nothing is lost and nothing downstream needs undoing. The detectors (native_res, noise_halo, crop_detect) take the depth from the pipe format, so their 8-bit-unit measurements are unchanged.

Correction. The plan described the full-range conversion as exactly round(x·65535/16383). That holds for only some samples; what does hold is y >> 2 == x for all of them, which is the property that matters.

4. What changes at the encoder

From scripts/reproduce.sh: the same 5 frames handed to each encoder as 14-bit and as 16-bit 4:2:0, with no -pix_fmt, as the worker does under original.

encoderfrom 14-bitfrom 16-bit
libx264yuv420p10leyuv420p10le
libx265yuv420p12leyuv420p12le
libsvtav1yuv420p10leyuv420p10le
FFV1yuv420p14leyuv420p16le
FFVHuffyuv420p14leyuv420p16le

ProRes and v210 have fixed formats from the script, and hardware encoders take forced_pix_fmt, which looks only at depth > 8. So only FFV1 and FFVHuff change. Stored at 16-bit, the 14-bit fixture's FFV1 file grows 7.8% (2,812,203 → 3,031,693 bytes). That is the worst case, an unfiltered source whose two lowest bits are zero; after any filtering the picture genuinely has 16-bit precision. The plan's figure (~11%, 2.14 → 2.38 MB) came from an earlier, uncommitted fixture with different content. This script's 7.8% supersedes it; the gap is a reminder that the overhead depends on the content.

5. Decisions

  • Decode 14-bit as 16-bit in decode_pixel_format (built). It is the single decision site and every consumer already calls it, so the decoders, the scripts and the encoder's input format cannot disagree. 14 is the only depth fmtconv refuses. NATIVE_FORMATS and pipe_source.py drop the three p14le entries, and a unit test fails if a 14-bit format comes back.
  • Rejected: a 14 → 16 guard around each havsfunc call. It would be needed around QTGMC, santiag and Deblock_QED in both templates, plus any future havsfunc function that calls fmtc.bitdepth or haf.Resize: a permanent special case spread across the templates, for no gain in picture.
  • Rejected: converting back to 14-bit for original. It would need a second decision (the probed depth beside the pipe depth) in the output conversion and in encoder_input_pix_fmt, and would round away real precision after filtering. The only effect of not doing it is FFV1/FFVHuff writing 16-bit, which is documented.

6. Tests

  • Rust: pixel_format unit tests (every 14-bit layout → 16, no native format at 14, 13 → 16) and test_241_14_bit_source_pipes_as_16 (the generated script and encoder_input_pix_fmt).
  • Heavy (integration_high_bit_depth_filters_test.dart): "preview runs on deeper formats" gains a yuv422p14le row, and every pass gains santiag, which the pass matrix lacked. A new group compares 14-bit with 16-bit previews for passthrough, default QTGMC, santiag and Deblock QED (mean abs diff 0.003–0.007 levels, fixtures alone 0.004). It also encodes the default pipeline to FFV1 from yuv420p14le (output yuv420p16le, 50 frames) and previews gray14le and gbrp14le. Before the change, 6 of that group's 7 tests failed.
  • The deeper-formats row is 4:2:2, not 4:2:0: on any 4:2:0 fixture, 8-bit included, the DeScratch pass fails with a resize error unrelated to depth (task #29).

7. Not tested

  • Windows and Linux bundles directly. Their fmtconv is the same r31, and the nightly heavy run covers them.
  • Which real-world files decode as 14-bit. FFV1 at 14-bit (yuv4xxp14, gray14, gbrp14/gbrap14) is confirmed, which plausibly includes archival film scans. H.264 High 4:4:4 Predictive at 14-bit is decodable by ffmpeg but could not be produced locally (libx264 has no 14-bit). The fix keys on the decoded format, so the codec does not matter.
