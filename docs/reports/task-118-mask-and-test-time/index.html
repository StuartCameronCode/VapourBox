The "havsfunc mask AND (patch 8)" test timed out on macOS x64

Task #118, 2026-11-27. CI durations from ci-test.yml's flutter jobs, 14 runs from 2026-11-22 to 2026-11-26 (deps 1.18.0-rc3/rc4). Profiles on an Apple M1 (macOS arm64), deps 1.18.0-rc4. The x64 bundle was not run locally (no Rosetta on that machine); the macOS x64 figure after the change is a projection until the PR's CI run.

Outcome

  • Slow, not hung. The push gate's check of havsfunc patch 8 (task #82) took 114–158 s on the macOS x64 runner and timed out at its 180 s limit in 4 of 14 runs. On the other platforms it took 14–75 s.
  • The cost was the test's reference, not the code under test. The reference ran each havsfunc call with upstream's own AND table, as a Lut2(lut=…) list built for every call. At 10 bits that is 220 entries, and handing them to VapourSynth costs ~0.3 s a call on an M1. The 48 such calls were 14.0 s of the script's 16.9 s. The patched calls took 0.12 s in all.
  • Fix (test only): above 8 bits the reference ANDs the top 8 bits and the low bits in two 8-bit tables and joins them in a third, all integer tables. Before the loop the script proves this equal to upstream's full 10-bit table on all 1,048,576 pairs, once. Whole script 16.9 s → 4.2 s on the M1; the same 36 comparisons, every one still exact. The 3-minute timeout stays.
  • Still caught: with _mask_and swapped for Expr 'x y max' the comparisons fail; with one entry of the join table broken the proof fails (PlaneStatsDiff 6.8e-7).

A 10-bit table costs the same passed as a list, a tuple or an array('q') (~0.29 s; the conversion of 220 Python ints), and 2.2 s as function=. A Lut2 node is bound to its two clips, so the table can't be built once and reused across calls; caching the list saves only the 1.1 s of building it. The bundle has no numpy.

The split reference, and why it is exact

AND works bit by bit, so for two N-bit values (N ≥ 8), with s = N − 8 and m = 2s − 1:

x & y = (((x >> s) & (y >> s)) << s) | ((x & m) & (y & m))

Each half is an 8-bit Lut2 with the 65,536-entry AND table, fed by std.Lut(…, bits=8) splits of each clip, and a third 8-bit Lut2 with bits=N joins them. At 8 bits the reference is upstream's own 256×256 table. Every step is an integer table, so the reference shares nothing with the code under test (Expr 'x y min'). It needs both clips at one depth, which every _mask_and call in havsfunc is (two GRAY planes of one clip); the test raises otherwise.

The proof, in every run of the test: one 1024×1024 GRAY10 frame where clip a is the column index and clip b the row index, so every (x, y) pair of 10-bit values meets once (R78's std.Expr has no X/Y, so the ramp is 1,024 one-pixel BlankClips stacked, and its transpose). Both ramps are checked to span 0..1023, then the split is compared with upstream's full Lut2(lut=[x & y …]). scripts/split_exhaustive.py; data/split_exhaustive_macos-arm64.txt:

What changed

  • app/test/vapoursynth_integration_test.dart, group havsfunc mask AND (patch 8): the split reference, the proof before the loop, and a TOTAL_EVAL line beside SLOWEST_EVAL so every run records the script's time on every platform. Coverage unchanged: outputs at every subsampling at 8 and 10 bits, masks at 4:2:0 for both depths and at 8-bit 4:2:2/4:4:4.
  • The 3-minute timeout and the 2 s slowest check are kept. A longer timeout alone would have left the test using ~2.5 minutes of the ~10-minute push gate (task #84) on the slowest runner.

Limits

The M1 numbers are one machine. The macOS x64 runner took ~7.7× the M1's script time before (130 s against 16.9 s); at that ratio the script now takes ~32 s there, plus vspipe's start. That is a projection: the PR's CI run records TOTAL_EVAL and the test's time on all four platforms, and one green run is not proof against a timeout that hit 4 runs in 14, so the recorded times (far under 180 s) are what to read. 16-bit isn't exercised by the test; the split is the same code there (s = 8).
