4:2:0 at a height 2 mod 4 (720x486), and RemoveDirt's race

Task #57, 2026-11-17. Measured on macOS arm64 (M1 Pro), deps 1.16.0 (the plugins are the same binaries as 1.17.0-rc2 on arm64). Found by task #48's plugin format probe.

Outcome

  • A 4:2:0 frame whose height is 2 mod 4 now runs through every pass that refused it. At 486 lines it has 243 chroma rows, so a field has no whole chroma height. SeparateFields refuses such a frame, and zimg refuses any resize of it while it is field-flagged, a pure depth change included (Resize error 1027). Every height 2 mod 4 does this (482, 486, 490, 270 and 1082 measured), not only 486.
  • Fix: pad, run, crop. plugin_formats.pad_around() adds two rows repeating each field's own last row (row h = h−2, h+1 = h−1; one chroma row = chroma row ch−2), runs the call, and crops back. read_padded() does the same for a resize, through src_height. A frame that already fits gets no node, so every other size keeps its script output byte for byte.
  • Only frames that refused are padded. Most of these plugins refused the size only when field-flagged, and ran on a progressive 486 frame before. Their contracts are field_based_only, and a progressive frame takes the old path, chosen per frame by _FieldBased. On progressive 720x486 their output is 0.000 levels from before (table 3). Correction, left in place: the first version padded every frame, and LSFmod then moved by up to 26 levels inside the frame, because it supersamples at a size that follows the height.
  • The case users meet most was not in the probe's list: a still-interlaced 4:2:2 D1 capture written out as 4:2:0 (Color Format 4:2:0, or AV1, which is always 4:2:0) refused at the script's last step. It now converts per field on a padded frame (heavy test integration_height_2_mod_4_test.dart).
  • RemoveDirt is deterministic again. removedirt.RestoreMotionBlocks v1.1 is registered fmParallel, but every frame of one instance writes the same block buffers. The bare chain gave 18 results in 20 runs at 8 threads, and 1 at 1 thread. removedirt.py now gives each frame an instance to itself, from a pool: 1 result in 20 runs, equal to the single-threaded one, 7% slower, memory flat. (A new instance per frame, the first fix, leaked about 0.6 MB per frame inside the plugin.) Upstream issue: pinterf/RemoveDirt#5; task #63 removes the pool once the bundle carries the fix.
  • Found on the way: TemporalDegrain2 differs run to run on its own (4 runs, 4 hashes, at 720x480 too). Filed as task #62.

3. What changes for jobs that ran before

Every height that is not 2 mod 4, and every 4:2:2 / 4:4:4 height: nothing. pad_around returns fn(clip) and adds no node. srestore and weave are bit-identical: stats_clip's per-frame measurements hash identically before and after at 352x240, 720x480 and 720x486, for 4:2:0, 4:2:2 and 4:4:4 at 8, 10 and 16-bit, progressive and TFF, wherever the old module ran. The cells it refused (720x486 TFF) now run. weave's 16-bit copy is identical in the same cells (scripts/module_identity.py, data/module_identity.json). weave's own output is not compared: Depan's estimate on a picture without global motion is a near-tie that varies with threading.

TemporalDegrain2's differences are its own run-to-run differences (task #62), not the padding's. The always-padded calls (QTGMC, MCTemporalDenoise) and the conversion sites refused every 2-mod-4 frame they were given, so they have no "before" to compare.

Why not pad every frame: the helper cannot read _FieldBased while the script is built (reading frame 0 would pull it through pipe_source). Padding every frame of such a height was the plan's first choice.

It moved LSFmod by a mean of 0.13 and up to 26 levels inside a progressive 720x486 frame, and DCTFilter / SangNom by up to 5 levels in the bottom rows. LSFmod supersamples at a size derived from the height, so 488 resamples the whole picture differently from 486.

Hence field_based_only: both paths are built, and one FrameEval with prop_src picks per frame, with no node created per frame. Only the chosen path's frames are requested.

remove_dirt() at 1 thread equals the bare chain at 1 thread, so the pool changes nothing but the race. At 1 thread with frames requested in 12 shuffled orders, SCSelect, RestoreMotionBlocks and the chain each give 1 result: it is a thread race, not an order dependence (removedirt.py order).

The cause, from the plugin source (v1.1, RemoveDirt.cpp):

  • restoreMotionBlocksCreate registers fmParallel;
  • d->rd->ProcessFrame() writes MotionDetection::blockproperties and Postprocessing's counters on the one RemoveDirt object each instance holds.

Upstream issue #5 (opened 2026-10-17, confirmed on Windows and Linux) proposes fmParallelRequests; on 2026-11-16 the maintainer said a fix is queued.

Each frame has an instance to itself, from a pool (_ExclusiveInstances in removedirt.py): a FrameEval takes a free instance (making one when none is free) and a ModifyFrame on that instance gives it back once its frame is made. The wrappers are uncached, so every request runs the hand-back. The pool grows only to the number of frames in flight.

Correction, left in place: the first fix made a new RestoreMotionBlocks per frame. The plugin leaks every instance it frees, so memory grew with the length of the job (table 5b). Found in review; the pool replaced it.

The push gate checks it: app/test/removedirt_determinism_test.dart runs remove_dirt() five times at 8 threads and wants one result, equal to the single-threaded one. It prints the bare plugin's spread (4 results in 5 runs on this machine) as a control, which drops to 1 when the bundle carries the fix.

6. The probe table

Tests/TestResources/plugin_format_table.json was re-measured for every call this task touches (the 17 calls in scripts/reproduce.sh: the eleven 720x486 refusals, Bifrost, Dedot, DeScratch, LUTDeCrawl, LUTDeRainbow and remove_dirt). A contracted call's cells are now also run through run_within(): the within result, summarised as within_refused. The push gate's plugin_format_contracts_test.dart now checks four things:

  • no reachable cell of a contracted call is refused through run_within();
  • a size the plugin refuses is accepted without a KNOWN entry when the contract's steps pad it;
  • a KNOWN entry whose contract pads every size it refuses is reported as stale;
  • the quick probe includes 720x486 4:2:0 for every contract with a step.

KNOWN is empty: task #56, merged first, fixed its two entries (Bifrost and MCTemporalDenoise's width 2 mod 4) with contract steps.

worker/tests/filter_integration_test.rs test_258 fails on a SeparateFields that no function handed to pad_around / run_within reaches.

Decisions

  • Pad, don't refuse. Padding fixed every refusal measured, at no cost to any other job. A readable refusal would have blocked a real (if uncommon) source and the common 4:2:2 → 4:2:0 output.
  • Period-2 rows, no field flag at build time. They are each field's own last row on an interlaced frame and a near-edge repeat on a progressive one, so one rule is right for both.
  • Pad per call, not once around the whole script. One pad at the top would reach the Crop and Resize geometry, Descale's exact inversion and the aspect fit. It would also change every pass's output on such a frame.
  • srestore and weave fixed in their modules. They only measure luma (weave: an undithered depth change), so the samples cannot change, and padding would only add work.
  • A pool of instances, each held by one frame at a time. Not a pool selected by n % k, which can hand two in-flight frames one instance, and not a new instance per frame, which leaks (5b). Its output equals the fixed plugin's (1 thread), so removing it later is purely a speed change.

Limits and what wasn't tested

  • macOS arm64 only. The other platforms run the same template, and CI's quick probe checks their bundles against the table, which now includes the 486 cells.
  • "1 result in N runs" is evidence, not proof: a race depends on timing. The plugin source is the proof that it was a race; an instance in the pool is never used by two frames at once.
  • The padded rows influence the bottom edge of a field-flagged 2-mod-4 frame. There was no "before" for those frames to compare with; they refused.
  • Width 2 mod 4 (854x480 and others), Bifrost's own blocks, and a resize's output at a height 2 mod 4 are task #56's.
  • TemporalDegrain2's nondeterminism is not investigated here (task #62).

Reproduce

SCRATCH=/some/scratch/dir scripts/reproduce.sh (optionally DEPS= a bundle, BASE= the commit whose templates are "before"). It needs the deps bundle; the decoded pictures it writes stay in SCRATCH. The 96x66 sweep rows run with the format sweep: flutter test test/integration_format_sweep_test.dart.
