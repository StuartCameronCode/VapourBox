FFT3DFilter's timed FFTW plans differ between processes: plan with FFTW_ESTIMATE

2026-11-20 · task #80 (found by task #73's merge, on the Windows push gate) · measured on GitHub's hosted runners (Windows x64, Linux x64, macOS x64 and arm64) and an Apple M1 Pro, with the deps bundles 1.18.0-rc1 and the 1.18.0-rc2 build of this task · pictures: the push gate's synthetic textured clip (352x288) and Tests/TestResources/interlaced_test.avi scaled to 720x480 and 1920x1080 · every number below is in data/, produced by scripts/.

Outcome: fixed, in deps 1.18.0-rc2. FFT3DFilter's default measure=1 makes FFTW time its candidate algorithms when the filter is created and keep the fastest. The winner depends on the machine's load at that moment, and different algorithms round floats differently, so two processes could filter the same frame differently. A preview and its encode are two vspipe processes, so this was the preview ≠ encode bug task #62 had just fixed, by another route. On x86 it happened on every platform: across 20 fresh processes, at least one argument class came out more than one way on every Windows, Linux and Intel-Mac runner probed. Apple Silicon agreed with itself every time, which is why task #62 (measured there) did not see it.

measure=0 (FFTW_ESTIMATE) picks the plan from heuristics, with no timing: one picture per machine on every runner, every key, 20 processes each. The template's three FFT3DFilter calls now pass measure=0, and the patch makes it the plugin's default, for havsfunc's calls (QTGMC, MCTemporalDenoise). Both are needed: FFTW reuses a measured plan made earlier in the same process for a later ESTIMATE request of the same problem, so one measured call undoes an explicit measure=0 (section 3).

Cost: only TemporalDegrain2's FFT post pass (postFFT 1 or 2, off by default) changes speed or picture. That call alone is 13–32% slower on x86 and a whole TD2 job with it about 5–23% slower; its picture moves by at most 1 level in under 0.1% of 8-bit samples. The FFT3D method, TD2's spatial pass and QTGMC's fft3dfilter denoiser are within run noise for speed; their 8-bit pictures came out identical to every measure=1 plan drawn, and at 16 bits two of them differed from some draws by one code value (1/257 of an 8-bit level) in under 0.25% of samples.

1. What the push gate saw

Task #62's push-gate test (vapoursynth_integration_test.dart, "fft3dfilter is deterministic") runs each argument class in six fresh graphs, then runs the whole script in a second process and compares hashes. The six graphs always agreed (FFTW caches a plan per process); the second process sometimes did not:

  • Run 44510129664 (PR #229, deps 1.18.0-rc1), Intel Family 6 Model 207: attempt 1 differed in td2_spat at 8 and 16 bits; attempt 2 in all 8 classes.
  • Run 44611343325, AMD Family 25 Model 17: 5 of 8 classes.
  • Six other Windows jobs on the same bundle passed, AMD Family 25 Model 17 among them: it is load, not the CPU model.

Hashes: data/ci-push-gate-windows.txt. gh returned the same log for both attempts' job IDs of run 44510129664; the attempt 1 figures are the ones quoted in the task.

2. Why: the planner, and the evidence for it

At tag R2, FFT3DFilterTransform and FFT3DFilterInvTransform plan with (measure ? FFTW_MEASURE : FFTW_ESTIMATE) | FFTW_DESTROY_INPUT, and Plugin.cpp defaults measure to 1. FFTW_MEASURE runs and times the candidate algorithms; ESTIMATE chooses by a cost model. Plans are made in the filter's constructor, so once per graph, and FFTW keeps them as process-wide "wisdom".

scripts/xproc.py hashes six calls (the classes below) on two pictures at 8 and 16 bits, 22 keys in all, in one process at one measure value; scripts/probe.py runs it in 20 fresh processes per value and counts distinct hashes per key. "default" is the call with no measure argument.

  • td2_spat: TemporalDegrain2's spatial pass at its defaults (sigma pattern, bt 3, 32 px blocks).
  • td2_post: TD2's post pass, postFFT 1 (sigma 1, bt 3, 48 px blocks).
  • nr_bt3, nr_bt5: the Noise Reduction FFT3D method at bt 3 (its default) and 5.
  • bt1: sigma 16, bt 1, as in the push gate.
  • qtgmc: havsfunc's QTGMC, Preset Fast, NoiseProcess 1, Denoiser fft3dfilter, NoiseTR 1 (FFT3DFilter at bt 3 inside); run at 0 or 1 by injecting measure into havsfunc's core (common._MeasureCore).

3. FFTW reuses a measured plan for an ESTIMATE request

scripts/wisdom.py plans every key at measure=1 in one process, then at measure=0, and compares the second hashes with a fresh measure=0 process (last column of the tables). On every runner and the M1 Pro, the in-process measure=0 differed from the fresh one wherever the two planners choose differently (always td2_post; on some x86 runs every class): FFTW's planner uses wisdom made at a more patient level for a less patient request. So an explicit measure=0 is only safe if nothing in the process measured the same problem first. A job runs QTGMC (havsfunc, no measure argument) and TemporalDegrain2 in one script, so the plugin's default had to change too, not only the template's calls.

Consistent across runners: td2_post alone is 13–22% slower on Linux, 24–32% on Windows, 11–15% on the M1 Pro; a whole TD2 job with the post pass is 12–23% slower on Windows, 5–17% on Linux, 6–15% on the M1 Pro. The macOS CI runners (3–4 shared cores) swing by tens of percent between neighbouring cells in both directions, so their cells say nothing either way; the M1 Pro is the macOS figure.

Limits: hosted runners, short clips, 8 threads. The post pass is off by default (td2PostFft 0), so a default TD2 job runs only the spatial pass, which costs nothing measurable.

Decisions

  • Plan with ESTIMATE everywhere, and make it the plugin's default. The template's calls pass measure=0 (so a bundle older than rc2 is fixed for them too, and the script says what it relies on); the patch's default covers havsfunc and closes the wisdom trap. test_261 fails on a template call without it.
  • Accept the cost on TD2's post pass. Preview = encode is the point of task #62; a 15–30% slower opt-in pass is the price. The alternative, shipping FFTW wisdom measured once per platform at build time, would be deterministic only on the CPU it was measured on and needs import code in the plugin; not worth it at this cost.
  • Correction to task #62. Its decision "Keep measure=1: processes agreed" rested on an Apple Silicon Mac, where they do. A note at the top of that report links here.

Not tested

  • Users' machines: only hosted runners and one M1 Pro. Linux arm64 (no runner in this probe) and the v2 CPU tier (the plugin is the same file in both tiers; FFTW's own SIMD dispatch differs by CPU, which ESTIMATE still uses).
  • Whether ESTIMATE agrees between machines: it need not, and nothing needs it to; preview and encode run on the same machine.
  • The heavy determinism test on CI against rc2 (run locally on the M1 Pro only); the push gate on all four platforms against the rc2 artifacts is CI run 44696475156.
