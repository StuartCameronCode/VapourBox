The DCTFilter stress test that timed out on Windows

Task #124, 2026-11-27. The failure: vapoursynth_integration_test.dart › dctfilter thread safety › DCTFilter and Deblock_QED survive many instances starting together (task #96), past its 5-minute timeout on the windows-x64-v2 heavy leg of nightly 45796959369 (deps 1.18.0-rc4, job 139829982138). The evidence is the nightly job logs (scripts/nightly_stress_lines.sh, data/nightly-stress-lines.txt), task #122's measurements of the cause, and local runs on an Apple M1.

Outcome

  • It was a vspipe that did not exit, not a slow graph or task #96's race. Task #122 found the cause: on Windows, Defender's real-time protection suspends vspipe's last thread in ExitProcess after vspipe has printed its final line, so the process never ends and its pipes stay open. The worker has stopped such a vspipe since task #122, 30 s after its final line. This test runs vspipe directly, with Process.run and no limit, so a suspended vspipe held it until package:test's 5 minutes ran out.
  • Fix (tests): every test that runs vspipe directly goes through runVspipe (app/test/support/vspipe_process.dart). It applies the worker's rule: after a final line, VAPOURBOX_VSPIPE_EXIT_GRACE_SECS (30 s) to exit. After that, describeHang records the stacks (cdb on Windows shows the suspend count) and the process tree is killed. The run then counts as vspipe's final line says: Output N frames with no Error: line before it passes, anything else fails, and the test log says what happened. A vspipe with no final line past its limit is a BoundedTimeout with its stacks and stderr. This is not a retry: each graph runs once, and only the wait for a finished process is bounded.
  • Both stress tests now bound and time each graph (90 s a graph, well inside the test's timeout) and print one line per graph with vspipe's own Output … in X seconds. A hang names its graph, and the nightly log has every graph's time on every platform.
  • Not yet seen on Windows with the change. The stand-in tests cannot run on Windows (see "Not tested"). The nightly after merge is the first Windows run: a stuck exit there prints stopped (on Windows, Defender suspends it in ExitProcess: task #122) with cdb's suspend count, and the test passes.

Limits: an M1 is not a 4-vCPU Windows runner. On the runners the whole task #98 test took 160–177 s for 31 graphs, so its graphs average 5–6 s there. A 90 s limit per graph is more than ten times that, so it trips only on a hang. A graph that hangs is named after 90 s (plus 20 s for stacks), inside the test's 5 minutes. The nightly's per-graph lines will give the real Windows and macOS x64 times; if any graph comes near 90 s, size the limit from them.

Checks

  • vspipe_process_test.dart (push gate): the final-line rule against the Rust (ERROR_PREFIXES in order, GRACE_ENV, DEFAULT_GRACE, the Rust test's own final_kind lines), the grace read from the environment, and runVspipe against stand-in vspipes that print a final line and then hold their pipes (exec sleep 600). A clean Output line passes after the grace, with its stdout. An Error: line before Output fails, and so does a stuck final error. No final line is a named BoundedTimeout with the stderr tail; the limit counts only until a final line, so a graph that finishes near its limit and then sticks is stopped after the grace, not reported as a hang. A vspipe that exits keeps its exit code, stdin and binary stdout. A lint fails on any Process.run/Process.start of vspipe in app/test.
  • Run on an M1: the push-gate parts of vapoursynth_integration_test, pipe_source_order_test and template_call_arguments_test (including the 11 stdin-fed _runVspipeScript calls), both stress tests and the akarin parity test (heavy), all through runVspipe, all passing.

Decisions

  • Apply the worker's rule in the tests rather than keep them red. The app stops a vspipe stuck in its exit, so a test that still waited for it would only be measuring Defender. The race the stress tests guard is an abort during the graph, and an abort prints no Output line, so it still fails.
  • A Dart twin of final_kind, listed in docs/TWINS.md and pinned to the Rust, rather than running the worker: these tests exist to run vspipe without it.
  • Every direct vspipe call, not only the stress tests: all of them can hit the hang, and the lint keeps new ones out.
  • -i runs and --version print no final line, so only their limit applies (10 minutes by default, 5 for the plugin-signature probe, 1 for --version). A hang there is named with stacks instead of running into the test's timeout.
  • No retry and no knownFailures-style allowance, and the test's 5-minute timeout is unchanged.

Not tested

  • Windows with the change. The stand-in tests are skipped on Windows, for the reason vspipe_exit_guard_test.dart gives: a batch file's child keeps the pipes after cmd.exe is killed, which is not the case under test. The first Windows runs are the PR's push gate and the next nightly. A stuck exit there is shown in the log, not inferred.
  • The kill path on Windows (taskkill /T /F of a suspended vspipe) is the worker's, which task #122 saw end a suspended vspipe on a runner. The test kill uses the same ProcessTree.killTree the app uses.
