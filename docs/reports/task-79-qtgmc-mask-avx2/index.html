QTGMC InputType 2/3: two faults in MVTools' Mask, padded around in the template

Task #79, 2026-11-21. Valgrind 3.22 memcheck on GitHub's ubuntu-24.04 runners, deps 1.18.0-rc2 linux-x64 (MVTools master built from source, havsfunc r31), through .github/workflows/repro-native-crash.yml (inputs bisect, bisect_script), runs 44764012129 and 44768793791. Row checks and the depth table on an M1 Pro, deps 1.16.0 macos-arm64 (same MVTools source and havsfunc). Source read from dubhater/vapoursynth-mvtools master and VapourSynth R78's VSHelper4.h. Follows task #69.

Outcome

  • The call. havsfunc's QTGMC runs core.mv.Mask(srchClip, bVec1, kind=1, ml=ProgSADMask) when InputType is 2 or 3 and ProgSADMask > 0, which is its default at Placebo, Very Slow, Slower, Slow and Medium (task #79's description said "from Slow"). It passes no opt, and the template can't give it one. ProgSADMask and ShutterBlur (the other route to Mask and FlowBlur) aren't exposed, so InputType and the preset decide.
  • Fault 1, heap write (x86 with AVX2). Below 4 of Analyse's block columns, the 8-bit AVX2 upsizer stores its row tail before its buffer, as task #69 found. Valgrind: 1,870–8,532 errors per cell, "Invalid write of size 4 … 1 bytes before a block of size 5". The boundary is exactly W = 4b − 3o.
  • Fault 2, wrong bottom rows (every CPU). Found while checking the first fix. Mask fills the rows under its block grid with one vsh::bitblt from the row above, inside the same frame. When a row is as wide as its stride, bitblt turns that into one memcpy over overlapping memory, and every row after the first gets whatever the rows below held. That's uninitialised memory on Linux (valgrind: the output written from it), and 12 of every 16 rows wrong on macOS arm64. It needs a width that is a multiple of the stride alignment and a height the grid doesn't reach, which real sizes can hit: 1920x1080 at BlockSize 32 / Overlap 16, 1280x720 at 32/8. havsfunc's defaults at these presets (16/8) put the grid on any height divisible by 8, so a job only reaches it with an explicit BlockSize.
  • Fix (template only, no deps release). The Deinterlace pass pads QTGMC's input through mvtools_blocks(min_cols=plugin_formats.mvtools_mask_cols(w, h, b, o)), with b/o the BlockSize and Overlap havsfunc will use (QTGMCParameters::prog_sad_mask_blocks), and only for InputType 2/3 at Placebo–Medium. The helper pads to 4 block columns, then adds 8 columns when the width is a multiple of 32 and the grid stops short of the bottom. Every other job's script is unchanged (test_263). Valgrind: all 14 guarded cells clean.
  • Found here, filed as task #89: Mask also refuses every format above 8 bits, so QTGMC with InputType 2/3 at Placebo–Medium fails on every 10-bit or deeper source, and on any source with High Precision on. That needs a havsfunc patch, out of scope here.

Fault 1: the AVX2 tail (x86)

Mask builds its mask at Analyse's own nBlkX = (W − o) / (b − o) (not grown to the edge, unlike Flow*'s nBlkXP) and upsizes it with simpleResize_uint8_t(…, smallMask, nBlkX, …). The AVX2 version's vertical pass steps 4 samples at a time and does the tail at src_width − 4: with nBlkX = 3 that is −1, a read before smallMask and a write before workp (malloc(src_width + 2)). The chroma upsizer takes the same nBlkX.

Fault 2: the bottom rows

// MVMask.cpp (master), luma; chroma does the same with nHeightBUV
upsizer->simpleResize_uint8_t(upsizer, pDst[0], nDstPitches[0], smallMask, nBlkX, 0);   // rows 0 .. nHeightB-1
if (nHeight > nHeightB)
    vsh::bitblt(pDst[0] + nHeightB * pitch, pitch, pDst[0] + (nHeightB - 1) * pitch, pitch, nWidth, nHeight - nHeightB);

// VSHelper4.h (R78)
if (src_stride == dst_stride && src_stride == (ptrdiff_t)row_size)
    memcpy(dstp, srcp, row_size * height);          // one copy; source and destination overlap
else
    for (...) memcpy(dstp8, srcp8, row_size);       // row by row: each row copies the one just written

nHeightB = nBlkY·(b − o) + o. The intent is to repeat the last grid row downwards. Row by row that works, but as one memcpy the source is rows nHeightB − 1 … nHeight − 2 as they were before the copy, so only the first filled row is right. In QTGMC the mask feeds MaskedMerge(innerClip, edi1, mask, planes=[0]), so the luma at the bottom of the picture is blended by garbage.

On Linux the same rows are uninitialised: valgrind's mask:128x96 … 32/8 cell reports write(buf) points to uninitialised byte(s), 10,432 bytes into the 12,352-byte frame mvmaskGetFrame allocated. That is row 81, the second row under the grid (data/mask.128x96.blksize_32_overlap_8.run_44768793791.excerpt.txt). The macOS count says which rows; it doesn't say what lands in them, which depends on the C library's memcpy and isn't defined.

How it was found, kept visible. The first fix padded every InputType 2/3 picture to a fixed 128 columns, the 32/0 worst case, and needed no block size. Run 44764012129 cleared fault 1 in every guarded cell, but two guarded cells, 64x96 and 96x96 at 32/8, padded to 128, showed a new finding: uninitialised values from mvmaskGetFrame's frame reaching mv.Super and the output (data/logs_44764012129/). The fixed pad had made fault 2 reachable for small pictures. That's why the pad now depends on the real block size and overlap.

The fix

def mvtools_mask_cols(width, height, blksize, overlap):
    step = blksize - overlap
    w = max(width, MVTOOLS_MIN_COLS, MVTOOLS_MASK_MIN_BLOCKS * step + overlap)   # 4 block columns
    h = max(height, MVTOOLS_MIN_ROWS)                                           # mvtools_blocks' own rows
    if (h - overlap) % step and w % MVTOOLS_MASK_STRIDE_STEP == 0:              # grid short of the bottom,
        w += 8                                                                  # and a row could fill its stride
    return w if w > max(width, MVTOOLS_MIN_COLS) else width
  • Why 32. VapourSynth aligns strides to 32 or 64 bytes depending on the build (the macOS arm64 core gave 160 for 136 columns: 32). A width that isn't a multiple of 32 is never equal to its stride under either, so bitblt copies row by row. Only luma matters: QTGMC merges luma only. The chroma bottom rows can still be wrong, but nothing reads them.
  • Which b/o. The template passes BlockSize and Overlap only when the user sets them, so the worker computes havsfunc's: BlockSize 16 at Placebo–Medium (Tuning is never passed), Overlap half the BlockSize in effect. A mirror of havsfunc's table, like effective_srch_clip_pp.
  • Who gets a node. Pictures narrower than 4 block columns (never a real source), and real sizes in fault 2's case, e.g. 1920x1080 or 1280x720 with an explicit BlockSize 32. Those were wrong at the bottom before; their output changes by the 8 columns added at the right edge. Everything else, including every InputType 0/1 job and every Fast-and-below job, generates the same script as before.
  • Rejected: a havsfunc patch passing opt= (needs a deps release, fixes only fault 1); padding the height to the grid instead (moves every row's search window more than a few columns at the right do).

The >8-bit refusal (task #89)

MVMask.cpp refuses any clip above 8 bits ("Mask: input clip must be GRAY8, YUV420P8, …"), and havsfunc hands it srchClip at the clip's own depth. scripts/mask_depths.py (macOS arm64, 128x96, data/mask_depths_macos-arm64.txt):

FormatInputType 2/3 at Slow, Mediumat Fast
YUV420P8runsruns
YUV420P10, YUV422P10, YUV420P16Mask refuses itruns

Mask's kind=1 never reads the clip's pixels, but it shifts the vectors' SAD by the clip's bitsPerSample − 8 (MaskFun.cpp), so an 8-bit stand-in clip would need ml scaled to match. That belongs in a havsfunc patch and a deps release, which task #89 covers. The format sweep never caught this because InputType isn't one of its axes.

Upstream issue (draft, not filed)

Mask: bottom-row fill copies overlapping memory when a row fills its stride; AVX2 tail below 4 blocks

1. mvmaskGetFrame fills rows nHeightB..nHeight-1 with
   vsh::bitblt(dst + nHeightB*pitch, pitch, dst + (nHeightB-1)*pitch, pitch, nWidth, nHeight-nHeightB).
   When pitch == nWidth, bitblt does one memcpy of the whole range, whose source and destination
   overlap, so rows after the first get the old contents of the rows below (uninitialised on glibc).
   Reproduce: Mask(kind=1) on 128x96 YUV420P8 with Analyse(blksize=32, overlap=8); rows 81..95
   differ from row 79. Fix: copy row nHeightB-1 into each row in a loop.
2. With nBlkX < 4, simpleResize_uint8_t_avx2's tail step starts at nBlkX - 4 < 0 and reads before
   smallMask and writes before workp (same as the int16 version below 8, reported for Flow*).
