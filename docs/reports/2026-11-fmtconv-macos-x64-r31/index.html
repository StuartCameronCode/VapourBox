macOS x64 shipped fmtconv git-18a9cecb, not r31

2026-11-14 · deps 1.16.0 · measured on an Apple M1 Pro: the published macOS x64 bundle under Rosetta 2 with each fmtconv build swapped in, and the macOS arm64 1.16.0 bundle natively

Outcome: built. download-deps-macos.sh now builds fmtconv r31 from source on both macOS architectures (same tag, same patch), instead of taking Stefan-Olt's prebuilt git-18a9cecb on x64. That makes "fmtconv is pinned to r31 on every platform" true. A pixel fingerprint for r31's chroma-placement fix is now a push-gate test on all four CI platforms. The skew changed nothing VapourBox could reach: every case the shipped pipeline uses was bit-identical between the two builds. It was a latent difference, not a live one. The fix reaches users with the next deps release; until then the new test skips on a macOS x64 bundle at 1.16.0 or older.

macOS arm64 and Linux build r31 from the GitLab tag; Windows downloads upstream's fmtconv-r31.zip. CLAUDE.md and NOTICES already said every platform shipped r31. Nothing checked it: the expected-plugins list names the file, not its version.

2. Where 18a9cecb sits upstream

From a clone of gitlab.com/EleonoreMizo/fmtconv: 18a9cecb (2024-08-02, "URL update") is 34 commits after r30 (e1b75cf, 2022-08-31) and 18 before r31 (f841f5f, 2026-04-12).

  • It already has the fixes that matter on x86: the missing AVX2 direct-conversion paths (r31's changelog: "14 to 16 bit AVX2 conversion path") and the bitblt_int_to_flt_cpp fix.
  • It lacks 3079bd6 "resample: fixed chroma placement": DV placement put its vertical offset on V (plane 2) instead of U (plane 1), MPEG-2 placement on a transposed 4:2:2 (4:4:0) clip was wrong, and vertical subsampling above 2 (4:1:0) was unhandled for DV / top-left. It also lacks r31's new matrices, transfers and primaries (IPT-C2, S-Log3 rescale, L*, LogC4, NTSC-J D93, AWG4), none of which VapourBox requests.

3. Did the skew change VapourBox's output? No

62 cases (scripts/probe.py), each hashed over every plane of every frame, run with the published x64 bundle's own Python under Rosetta, once with the shipped dylib and once with r31 built for x86_64 (section 4). A third run repeated the shipped build, to separate fmtconv differences from nondeterminism. Source: 320x240 grain, blurred and grained again, 12 frames.

Correction, kept in place. The first comparison showed QTGMC Placebo differing between the two builds, which looked like an fmtconv effect. Repeating the shipped build alone gave a different hash again, on the same three formats (which ones vary changes from run to run). So these were QTGMC's own nondeterminism with several threads, not fmtconv. To be sure, the three formats were re-run with core.num_threads = 1, twice per build: all four runs gave the same hashes.

Why the differing cases can't be reached: nothing in the templates, havsfunc or the mvsfunc functions we call passes cplace, so it is always fmtconv's default mpeg2. A 4:4:0 or 4:1:0 source never reaches fmtconv: the decoder converts both to 4:2:2 (pixel_format.rs), and Rotate restores formats with zimg.

Limits of this result. Rosetta runs the AVX2 paths, so the SSE2-only path a v2-tier CPU takes was not compared. The clips are synthetic, not real footage. The 14-bit rows of Bob, Resize and QTGMC are absent from the table because they fail on both builds (section 6).

fmtconv's AVX/AVX2 translation units have no static initializers, so the v2 tier needs no separate build and fmtconv gets no _tierFiles entry. The ARM patch is dead code on x86, where the SSE2/AVX2 scalers replace the patched function; Linux x64 has always shipped it applied. The macos-15-intel runner builds natively, so the first build-deps-macos.yml x64 run is the real proof of the CI toolchain; the composed-v2 gate checks the result.

5. A fingerprint for "is this r31?"

scripts/fingerprint.py: a 64x64 4:2:0 clip with flat luma and identical U and V planes, each a ramp rising down the picture. Split into fields (TFF), then fmtc.resample(scalev=2, interlaced=1, interlacedd=0, cplace=…). With U = V going in, any U−V coming out is chroma placement alone. 16-bit averages:

Builddv field 0 U−Vdv field 1 U−Vmpeg2 U−V
18a9cecb (published x64, Rosetta)+606.31+606.310.00
r31 x86_64 (built here, Rosetta)−606.31−606.310.00
r31 + patch (macOS arm64 1.16.0 bundle, native)−606.31−606.310.00

The sign flips exactly between versions and does not depend on the SIMD path, so the test needs no reference image. It is fmtconv version pin in app/test/vapoursynth_integration_test.dart (push gate, every platform): dv must be below −300 on both fields and mpeg2 within 1. It skips on a macOS x64 bundle whose version.json says 1.16.0 or older, the known skew, and enforces from the next deps release on. Run against the 18a9cecb build it fails with "+606.31"; against both r31 builds it passes.

6. Side finding: 14-bit sources and havsfunc (not fixed here)

fmtc.bitdepth(bits=14) is refused ("output pixel bitdepth not supported") by both builds. havsfunc's Resize and Bob convert through it, so haf.QTGMC fails at every preset on a 14-bit source, on every platform. The worker passes yuv4xxp14le through natively. Tracked separately; it is not a version skew and r31 does not change it.

Decisions

  • Build r31 on x64 rather than reword the docs to accept the skew. It builds and passes both gates, it removes one more unversioned prebuilt, and it keeps the invariant true for the day something passes cplace="dv".
  • Apply the ARM patch on x86 too, as Linux x64 does: one recipe, and the patch is dead code there.
  • Test the behaviour, not the version string. fmtconv reports no version at run time; the chroma fingerprint is what a skew would actually change.
  • Skip, don't fail, against 1.16.0 on macOS x64, so the push gate stays green until the next deps release, which turns the check on by itself.

Not tested

  • The SSE2 path (v2-tier CPUs); real footage; the macos-15-intel runner's own build (the next build-deps-macos.yml run).
  • Windows' r31 zip was not re-fingerprinted here; the push gate now does that on every run.
