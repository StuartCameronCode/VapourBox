Task #89: QTGMC InputType 2/3 at more than 8 bits (havsfunc's 8-bit-only mv.Mask)

2026-11-22 · deps 1.18.0-rc3 (also 1.16.0 in Plan) · macOS arm64 (M1 Pro) · found by task #79

Outcome

Fixed in the template, with no deps change. havsfunc's QTGMC runs core.mv.Mask(srchClip, bVec1, kind=1, ml=ProgSADMask) when InputType is 2 or 3 and ProgSADMask > 0, which it is by default at Placebo, Very Slow, Slower (the app's default), Slow and Medium. MVTools' Mask refuses any clip above 8 bits, so every 10/12/16-bit job with those settings failed, and so did every 8-bit one with High Precision (16-bit) on:

Mask: input clip must be GRAY8, YUV420P8, YUV422P8, YUV440P8, or YUV444P8, with constant dimensions.

For exactly those jobs the Deinterlace pass now rebinds _deinterlace_qtgmc through plugin_formats.havsfunc_mask_any_depth(haf, fn). While QTGMC builds its graph it points havsfunc's module-level core at a proxy whose mv.Mask is mvtools_mask_any_depth. That function hands Mask an 8-bit stand-in clip of the same size and subsampling, multiplies ml by 2bits−8 for kind 1, and puts the 0–255 mask on the clip's full scale (x·peak/255). Other jobs' scripts are byte-for-byte unchanged.

On the same picture at two depths, a 10-bit job now differs from the 8-bit one by 0.16 levels (Slow, Medium) and 0.07 (Placebo). That is less than the same comparison with the Mask switched off (0.28 and 0.12), which shows the stand-in adds no difference of its own. What remains is QTGMC rounding at the deeper depth.

Why a stand-in is exact (MVTools master ed90ee9 and v24 read the same here)

  • Kinds 0–4 never read the clip's pixels. The clip supplies only the format and size. Only kind 5 copies the source luma, and the helper passes kind 5 through unchanged.
  • The SAD shift is read from the clip. MakeSADMaskTime computes sad = vector.sad >> (bitsPerSample − 8), with bitsPerSample taken from the clip's frame. Analyse measured that SAD at the vectors' depth, which is srchClip's depth in havsfunc. Each block's mask value is ByteNorm(sad, 4 / (ml·blkX·blkY), gamma), so on an 8-bit stand-in, ml × 2bits−8 gives the same value. The one difference is that MVTools truncates sad >> k before dividing. That puts them at most one mask level apart, and the stand-in is the more precise of the two.
  • The scene-change thresholds scale by the vectors' depth (scaleThSCD reads the analysis data), so a stand-in doesn't move the scene-change decision. ysc is in 8-bit units either way.
  • The factor can't be read from the vectors without requesting a frame while the script is evaluated, which no template may do (task #65). It comes from the clip, whose depth is the vectors' depth in havsfunc.

Measurements

Source: Tests/TestResources/pal-sd-25.mov, 40 frames of 720x576 4:2:2, measured on frames 6–29. The file is an 8-bit master in a 10-bit container (its low two bits sit 0.002 levels from zero). A light blur at 10 bits gives it 0.47 levels of real sub-8-bit content. Three clips are compared: 8-bit (that blur rounded), exact-10 (the 8-bit clip ×4: the same picture at two depths) and real-10 (the blurred clip itself). Differences are luma mean / max in 8-bit levels.

Limits: one clip with synthetic low bits, on one platform. A mean says nothing about where the differences fall. The Mask-off control is what separates QTGMC's own depth rounding from the stand-in. x86 was not measured here; the contracts test and format sweep run on every CI platform.

With pel 2, Super interpolates the half-pel planes at each depth with its own rounding. On a synthetic grain texture the contracts test first used, the kind 1 mask then differed by up to 10 mask levels at 10 and at 16 bits, with identical vectors. A native deep Mask would see that same deep SAD, so this comes from MVTools' interpolation, not from the stand-in. The contracts test now checks exactness at pel 1, where SADs scale exactly. C. Formats

Through the helper, YUV420P10, YUV420P16 and YUV444P12 run, and plain havsfunc refuses each one. High Precision (8 → 16 → 8, dithered) differs from the plain 8-bit job by 0.182 / 47. Task #79's refusal table (data/mask_depths_macos-arm64_1.18.0-rc3.txt) is unchanged on rc3: every 10/16-bit InputType 2/3 Slow/Medium row refuses, while 8-bit and Fast run.

Decisions

  • Template-side, not a havsfunc patch (the user chose option C). It needs no deps release (a patch would have needed 1.18.0-rc4), works on every bundle from 1.16.0, and does not depend on havsfunc's source text: if upstream changes, the helper becomes inert rather than wrong. The cost is that it relies on havsfunc reading its module-level core at call time, which patch 7 (akarin) already relies on, and on QTGMC building no FrameEval that calls back after it returns.
  • Only the jobs that run the Mask (InputType 2/3 at Placebo–Medium, the same condition as QTGMCParameters::prog_sad_mask_blocks from #79) get the block. Every other script is unchanged (test_269).
  • Rejected: running QTGMC at 8 bits through run_within, which quantises the whole output; and forcing ProgSADMask=0 above 8 bits, which gives a different picture (1.4–2.8 levels).
  • #79's padding still holds as it stands. With the stand-in, Mask always works at 8 bits (1 byte per sample), so its 32-byte stride rule in mvtools_mask_cols stays exact for deeper clips.
  • ShutterBlur's kind 0 Mask (not exposed) goes through the same proxy and is exact for the same reason.

Tests

  • test_269 (Rust): the block is in the encode and preview scripts exactly for InputType 2/3 at Placebo–Medium (High Precision included), and absent otherwise. test_263 tolerates it.
  • plugin_format_contracts_test.dart (push gate): the stand-in's mask is exact at 10 and 16 bits (kinds 0, 1, 3, pel 1); QTGMC InputType 2 at Medium runs through the helper at YUV420P10, YUV422P10 and YUV420P16 while the bare call still refuses on Mask; 8-bit through the helper equals the plain call; havsfunc's core is restored, even after an error.
  • Probe: havsfunc.QTGMC[InputType=2] records the refusal (8-bit only, in HANDLED), and pass.QTGMC[InputType=2] (the pass as the template runs it) accepts every cell.
  • Format sweep: two variants, InputType 2 (Slower) and InputType 3 (Medium). All 138 nightly rows pass on macOS arm64 (run, depth, acts, parity).
  • Heavy parity (integration_high_bit_depth_filters_test.dart): InputType 2 Slow gives 0.68, and InputType 3 Medium with High Precision gives 0.26, against a tolerance of 3.0. Without the fix, both fail on Mask (High Precision at 8 bits too).

Not tested

  • x86 (master and v24 MVTools) and Windows were not measured; CI's contracts test and sweep cover them functionally.
  • Real 10-bit camera footage; the low bits here are synthetic.
  • An explicit BlockSize or Overlap other than the presets' defaults. Mask's arithmetic doesn't depend on them.
