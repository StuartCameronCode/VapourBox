Stabilize under-corrected horizontal shake on every 8-bit source

2026-11-15 · task #32 (overnight CI failures) · deps 1.16.0 · measured on an Apple Silicon Mac (macOS arm64 bundle). The fault is in MVTools' C++ (a sample-size comparison), not in CPU-dispatched code, and the same lines are in the MVTools master that the macOS and Linux bundles build and the v24 tag Windows and macOS x64 ship.

Outcome: fixed in the templates. The Stabilize pass's weave correction is havsfunc's Stab, which measures global motion with MVTools' DepanEstimate. On 8-bit input that estimate reads each row as 16-bit samples, so it measured horizontal motion at about half its size. A clean 2 px shift came out as 0.91–0.97 px, against 1.94 px at 10 and 16-bit. Vertical motion was measured right at every depth. The weave now measures motion on a 16-bit copy and compensates the clip itself (stabilize.weave). A 16-bit integer clip gets exactly havsfunc's Stab, and 10-bit was already right. On the heavy parity test's shaken fixture, 8-bit and 10-bit previews went from 9.66 to 0.343 levels apart (tolerance 2.0).

How it was found

Every nightly since Stabilize shipped (11-10) failed the stabilize / stabilize_black_edges cases of integration_high_bit_depth_filters_test.dart on some platform. The check that failed was "the pass produced the same frame as a passthrough". The fixture is testsrc2 with grain and MPEG-2 artefacts, and it has no global motion, so Depan was estimating noise. On some runners the estimate came out zero, and the pass returned the source. When the case passed, 8-bit and 10-bit differed by 1.48–1.82 levels, far looser than any other pass.

The same 10-bit preview also gave different pictures on different runs (2 of 15 locally). With core.num_threads = 1 it was identical every time, and of the pass's pieces only DepanEstimate varied: its dx flipped between ±0.011 px. With nothing to measure, the correlation peak is a near-tie, and which side wins depends on threading. So the test was given a fixture with known shake. That made it deterministic and exposed the depth difference below.

1. The cause

frame_data2d in src/MVDepan.cpp copies the FFT window and chooses how to read a sample like this:

if (bytes_per_sample == 8) {          // 8-bit read
    ...
} else if (bytes_per_sample == 32) {  // float read
    ...
} else {                              // 16-bit read
    const uint16_t *srcp16 = (const uint16_t *)srcp;
    ...

Its callers pass vi->format.bytesPerSample, which is 1, 2 or 4, never 8 or 32. So every format takes the 16-bit branch. That is right for 9–16-bit integer, but on 8-bit it reads two pixels as one sample, and twice the window's width, past the window. That halves the horizontal resolution of the correlation and reads unrelated bytes. A float clip is misread too, but none reaches Stabilize.

On a picture with real motion, both depths are deterministic. On a motion-free picture, the near-tie makes the result depend on threading. That was already true at 10-bit and above, and now it is true at 8-bit as well, because 8-bit is now measured the way 10-bit always was. Old 8-bit looked deterministic only because its misread landed on the same wrong answer every time. How large the difference is (plain 8-bit, weave, run 1 against two other runs):

3. Decisions

  • Measure on 16-bit, compensate the clip itself. DepanCompensate only applies the measured shift, so the picture keeps its own depth and nothing is converted back. The averages Stab compares against are rebuilt the same way at each depth.
  • In stabilize.py, not a havsfunc patch. The patches in the download-deps-* scripts would need a deps release, and they cannot touch the Windows DLL. One Python helper, imported by both templates, keeps preview and encode identical.
  • 8-bit Stabilize output changes. This is deliberate: it now removes the horizontal shake it was missing. test_212 pins the new weave block, so a pipeline saved before pitch correction still gets a fixed, known script.
  • The motion-free near-tie stays. It moves the picture by ±0.011 px, and only on frames where there is no shake to remove. Fixing it would mean replacing Depan.
  • The test uses the shaken fixture for both Stabilize cases. On the plain one, the "does the pass do anything" check rested on that near-tie.

Not tested

  • Real shaky footage, on any platform but macOS arm64. The cause is a comparison in portable C++, so the halving is the same everywhere. The nightly parity run checks the result on every platform.
  • Whether the motion-free near-tie comes from FFTW, from frame-property buffers, or from something else inside the plugin.
  • Reporting it upstream. The fix would be to compare bytes_per_sample with 1 and 4.
