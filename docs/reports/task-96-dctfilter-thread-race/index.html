DCTFilter r2 aborts under threads: an unlocked per-thread buffer map

2026-11-21 · task #96 (and #90) · found by the nightly format sweep on Windows x64 · measured on an Apple M1 Pro (macOS arm64 deps 1.16.0, and the macOS x64 deps 1.10.0 bundle under Rosetta) · every number below is in data/, produced by scripts/.

Outcome: fixed in the deps (1.18.0-rc3). DCTFilter up to r2.1 keeps one scratch buffer per worker thread in an std::unordered_map that getFrame fills with no lock. When two threads start an instance together, an insert is lost, .at() throws std::out_of_range inside a noexcept function, and vspipe aborts. On Windows an abort is a fail-fast, exit 0xC0000409, the code in both nightly failures. The Deblock pass's DCTFilter method and havsfunc's Deblock_QED (which calls DCTFilter) were exposed on Windows (the r2 release DLL) and macOS x64 (Stefan-Olt's r2.1), at any frame size. macOS arm64 and Linux built upstream HEAD, which already has the fix.

Every platform now builds tag r3.2 with Scripts/patches/dctfilter-r3.2-thread-safety.patch, upstream's own untagged commit c924a7a (a buffer per call). Its output is the same as r2's, sample for sample.

1. What the sweep saw

  • Run 44767156916 (main 9190d08d, deps 1.18.0-rc2), job windows (windows-x64-v2, sweep): deblock/deblock_qed 96x64/yuv422p12le/tff: "vspipe exited with exit code -1073740791 — fail-fast: a plugin detected memory corruption and aborted". 1 of 69 rows; every other platform and tier passed.
  • Run 44562921675 (deps 1.18.0-rc1), windows (windows-x64, sweep): deblock/dctfilter 98x64/yuv420p10le/tff and 98x64/yuv422p12le/tff, the same exit code (task #90).

The two failures had different sizes, depths and tiers, and both passed in other runs. Their common element is DCTFilter, and the only DCTFilter binaries that differ between platforms are Windows' and macOS x64's.

2. The fault, in the source

r2's DCTFilter.cpp (2017; r2.1 changes only the build files):

struct DCTFilterData {
    ...
    std::unordered_map<std::thread::id, float *> buffer;      // shared by every thread
};

static void process(...) noexcept {
    float * buffer = d->buffer.at(threadId);                 // throws if the insert was lost
    ...
}

dctfilterGetFrame(...) {                                      // fmParallel: many threads at once
    if (!d->buffer.count(threadId))                          // no lock
        d->buffer.emplace(threadId, fftwf_alloc_real(64));   // no lock
    ...
    process<T>(src, dst, d, vsapi);
}

Upstream fixed it twice. r3.0 (48ac5572) took a shared_mutex for the insert and the lookup, but r3.2 still calls count() before taking it, which is still a race. c924a7a ("Remove locks, use vsh_aligned_malloc", 2026-05-10) drops the map: each getFrame allocates a 64-byte aligned buffer and frees it. FFTW's new-array execute needs the same alignment as the planning buffer, and the commit aligns both the same way. No tag contains c924a7a yet, so the patch carries it over r3.2, and the result is byte-for-byte HEAD's source. The same class of bug was TCanny r14's (task #52).

3. Reproduction

scripts/build.sh builds r2, and r3.2 with the patch, for macOS against the bundle's FFTW, each under its own namespace so it loads beside the bundle's dctf. scripts/run.sh runs:

  • fresh_process.vpy: one DCTFilter at the failing row's per-field size (96x64 4:2:2 12-bit, TFF, split into 96x32 fields), 8 threads, a fresh vspipe each run;
  • many_instances.vpy: 1000 DCTFilter instances spliced end to end in one graph. Each instance has its own map, so each one's first frames are another chance for the race. The heavy test runs this shape.

Note, left as measured: the first fresh-process trial of r3.2 + patch failed 2 / 300, with no exception text. Both crash reports show a worker thread in vspipe's frameDoneCallback/outputFrame while the main thread was in vpy4_freeScript: vspipe R78's teardown race (task #68). The 1.16.0 bundle used here still has it; deps 1.18.0 carries the fix. A second run gave 0 / 300 for both the patched build and the bundle's (data/stress.txt). Earlier, during planning, the same scripts gave r2 2 / 200 and 1 / 300 at 16 threads, and the bundle's build 0 / 200.

So r2 aborts in about one fresh process in a hundred, whatever the frame size. Each preview is a fresh process, and the sweep runs thousands of them, which is why only the sweep saw it. Real jobs on Windows and macOS x64 had the same odds per preview and per encode.

5. FFTW_PATIENT, kept

DCTFilter plans its 8x8 DCT with FFTW_PATIENT, which times candidate plans in each process. Task #80 found that FFTW_MEASURE timing gave different FFT3DFilter pictures in different processes on x86, so a preview and its encode could differ. Switching DCTFilter to FFTW_ESTIMATE was offered and declined: this change is the thread safety only. What has been measured:

  • macOS arm64: one hash in 12 processes (bundle), and in 3 per build above.
  • macOS x64 bundle (r2.1, PATIENT) under Rosetta: one hash in 12 processes, twice (once while other jobs loaded the machine). Rosetta runs x86 code but is not an x86 CPU, so this is weaker evidence than a runner.
  • Not measured: Windows and Linux x64 on hosted runners, where task #80's FFT3DFilter differences showed. If those give more than one hash, the fix is the one task #80 made, in a follow-up task.

6. The fix and its checks

  • download-deps-windows.ps1: the r2 7z is gone. Section 4b4 builds DCTFilter.dll from r3.2 with the patch using FFT3DFilter's Zig recipe (FFTW 3.3.5's DLL through an import library, API 4 headers from R78), at the x86-64 baseline for both tiers. A DCTFilter.dll without VapourSynthPluginInit2 (r2 is API 3) is rebuilt.
  • download-deps-macos.sh: Stefan-Olt's r2.1 is gone from the x64 list. Both arches compile the one file against the bundle's lib/libfftw3f.3.dylib, as FFT3DFilter is built (x64 at its 12.0 floor; PyPI's x86_64 wheel needs 15.0). Checked locally on arm64: it builds, links @loader_path/../../lib/libfftw3f.3.dylib, exports _VapourSynthPluginInit2 and passes check-macho-refs.py.
  • download-deps-linux.sh: pinned to r3.2 with the patch. It used unpinned HEAD, which is the same code.
  • Every script fails the build if the patch stops applying.
  • Tests (vapoursynth_integration_test.dart, group dctfilter thread safety):
    • push gate: DCTFilter ≥ 3.2 (core.dctf.version; r2/r2.1 report -1), and the patch and scripts are in place;
    • heavy: 10 graphs of 1000 instances and 3 graphs of 300 Deblock_QED calls.
    The bundle checks run from deps 1.18.0-rc3. Run against a copy of the arm64 bundle with r2 swapped in, both bundle tests failed 3 runs out of 3. With the bundle's own build they passed.
  • The worker's text for 0xC0000409 was "a plugin detected memory corruption and aborted". It now says "vspipe or a plugin aborted (an uncaught C++ exception, or memory corruption it detected)".

7. Not done, and limits

  • Not yet run on Windows CI. The Windows build block can only run on Windows. The before and after evidence there is the deps build plus the nightly run (deps_run_id) of this branch.
  • A race rate is a probability: 0 aborts in N runs bounds it, it does not prove it zero. The 1000-instance shape is used because it turns a 1% event into a better-than-even one per run.
  • The sweep row is not listed in knownFailures: that list requires a listed row to fail, and this one fails only sometimes. It stays intermittent on Windows and macOS x64 until 1.18.0-rc3 is the pinned bundle.
  • The same unlocked map is in DFTTest (every bundled version, upstream HEAD included) and LGhost r1: task #98.
