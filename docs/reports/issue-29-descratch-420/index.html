DeScratch failed on interlaced 4:2:0 sources

2026-11-15 · task #29 · deps 1.16.0 · measured on an Apple Silicon Mac (macOS arm64 bundle). The failure is in zimg's arithmetic, not CPU code, so it is the same on every platform; the nightly heavy run covers the others.

Outcome: built. The DeScratch pass failed with "Resize error 1027: image dimensions must be divisible by subsampling factor" on most field-flagged 4:2:0 sources, at any bit depth. Our own conversions around the call were not the cause. The failure is inside the plugin: its constructor builds the blurred clip it analyses (and corrects with) by resizing the frame to height // (1 + blurlen) rows, rounded to even. zimg resizes a field-flagged clip one field at a time, so 4:2:0 chroma then needs a multiple of 4.

The templates now run 4:2:0 luma through DeScratch on a 4:2:2 carrier: the clip's own luma plus a blank half-width chroma plane, assembled with ShufflePlanes (no resample). They then put the source's chroma back. The plugin processes planes independently and copies chroma by default, so the carrier gives bit-identical output wherever the native call works, and it works at every height. A chroma mode, which is off by default, gets a second call on a copy without _FieldBased.

1. Where it fails

The plugin alone on field-flagged (TFF) BlankClips, 720 wide (sweep.py). Progressive clips, 4:2:2 and 4:4:4 never fail.

The encode and preview templates carry the same block, so both failed. These jobs reach DeScratch with _FieldBased set:

  • Deinterlacing off with a detected field order. The heavy test's case, and a film-on-tape capture's.
  • Soft Telecine. A bare VDecimate leaves _FieldBased=2, so an NTSC film DVD with Soft Telecine and DeScratch failed too. QTGMC, Bwdif and IVTC (VFM ± VDecimate) reset it to 0, which is why the existing encode test (QTGMC first) never caught this. Update (task #33, 2026-11-15): Soft Telecine jobs are no longer marked field-based, so DeScratch now sees their film frames as progressive; see issue-33-soft-telecine-field-based.

Correction to the plan. The plan said DeScratch also fails on NTSC DV (4:1:1), because the plugin refuses YUV411P8 ("Video must be YV12, YV16 or YV24!"). That is true of the plugin, but no job reaches it with 4:1:1. Both templates convert 4:1:1 to 4:2:2 straight after the pipe, before any pass. The 4:1:1 branch was therefore dropped while implementing.

Field-aware analysis removes the most scratch. Stripping _FieldBased (the one-line fix) makes fewer false changes but leaves more scratch, and it would change the output of every 4:2:2 interlaced job that works today. Per-field processing is worst, and it cannot split a 486-line 4:2:0 frame at all. So the fix keeps field-aware analysis and makes it work on 4:2:0.

Limits of this measure: one clip; straight, synthetic, dark scratches of constant opacity; luma only; default parameters plus three variations. Real film scratches wander and vary in contrast. Scratch 2 (1 px wide, 50%) is barely touched by any variant. This ranks the variants on one kind of scratch; it does not show how often DeScratch helps on real footage.

3. The carrier is bit-identical where the native call works

The same probe at 4:2:0 compared the native call with the carrier (exact.py). Both were run progressive, TFF and BFF, at blurlen 15, 5 and 30 and mindif 3. In every case where the native call works, 0 of 24 frames differ in Y, U or V, and the carrier keeps _FieldBased. So no job that works today changes by a single sample. The carrier also works on field-flagged 4:2:0 at every height in section 1 at blurlen 15, 30 and 50.

Why it is exact: DeScratch handles each plane independently. With modeu = modev = 0 (the default) it copies the chroma planes unchanged. The luma result depends only on the luma plane and its luma blur, and zimg computes that the same whatever the chroma subsampling.

Decisions

  • Carrier, not stripping _FieldBased: it keeps today's output where today works, and it removes more scratch (section 2).
  • Chroma modes on (advanced, default off): U and V come from a second call on a copy without _FieldBased, which accepts every 4:2:0 height. For a progressive source this is today's output. For a field-flagged one at a height that happened to work, its chroma is now analysed as frames rather than as fields.
  • One call site (_descratch() in both templates), so every path gets the same parameters, and the 8-bit guard stays around the whole block.

Tests

  • test_242_descratch_any_subsampling (Rust): both scripts carry the carrier, exactly one call site, and the chroma call only with a chroma mode on.
  • integration_high_bit_depth_filters_test.dart (heavy):
    • preview and FFV1 encode on 8- and 10-bit 4:2:0, with chroma modes off and on;
    • a 4:2:0 encode's luma equals a 4:2:2 encode's, sample for sample, and its chroma equals the source's (with 78,675 luma samples changed, so the comparison is not vacuous);
    • Soft Telecine + DeScratch on soft_telecine_dvd.mkv;
    • yuv420p14le added to the deeper-formats row, which gives every pass a field-flagged 4:2:0 source.
    All six new tests fail with error 1027 on the previous templates.

Not tested / follow-ups

  • Real scratched film. There is no such fixture in the repo; the quality ranking rests on synthetic scratches.
  • Soft Telecine leaves _FieldBased set on film frames, so every later zimg resize treats them as fields. Filed as task #33. Fixed by task #33 (2026-11-15): report.
  • DeScratch on a source deeper than 8-bit up-converts the whole 8-bit frame, so untouched pixels lose precision. Filed as task #34.
  • Blur Radius allows 200, but the plugin refuses height // (1 + blurlen) < 2 (above 119 on 480 lines). Filed as task #35.
