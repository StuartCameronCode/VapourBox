Automatic white balance compiled an expression for every frame

GitHub issue #253 (task #136), 2026-11-28. Measured on an Apple M1 (8 cores), deps 1.18.0-rc5 (macOS arm64) unless stated. The issue's own numbers are from a Windows desktop and a 48-core EPYC.

Outcome

  • The issue is right, and the cost was worse than it says. Colour Correction's automatic white balance (_auto_white) returned a new expression from a std.FrameEval on every frame, with the frame's offsets written into the expression text. The template's _expr() sends an expression to akarin wherever akarin is installed (every bundle but macOS x64), so every frame paid for an LLVM compile, inside a Python callback that holds the GIL. That is ~17 ms a frame on an M1, and no number of cores helps: the issue's 20% CPU and the EPYC running slower than the desktop.
  • Fix: with akarin, PlaneStats stamps each chroma plane's mean on the frame and one expression, compiled once, reads it (x x._AwbUAverage …). No Python runs per frame. The FrameEval stays only as the fallback where akarin is absent (macOS x64), where each frame's std.Expr is cheap (~0.35 ms).
  • Speed, the filter alone at 706x480: ~60 fps → ~8,000 fps (see below). Through the worker on this machine under heavy load the issue's whole chain did not speed up measurably (10.8 → 10.9 fps): the rest of the chain was slower than the old filter's serial limit there. On a free machine whose other passes run faster than ~60 fps, as the issue's did (47.6 fps without Colour Correction), the old filter was the limit; that case was not measured here.
  • Output: the fallback is identical everywhere, as is the akarin path at 8, 10 and 12 bits. At 16 bits, 17 of 10,800 chroma planes (0.16%) came out one 16-bit step apart (1/256 of an 8-bit level): akarin reads a frame property as a 32-bit float, and the old code wrote the offset as a 6-decimal literal. Neither is the more correct.
  • Automatic levels is left as it is. The issue suggested the same treatment, but it costs ~0.2 ms a frame (a std.Levels is a lookup table, not a compile), and the akarin version is not bit-exact: akarin compiles with fast-math, and its division lands a .5 tie on the other side of std.Levels' in 2.0% of (min, max) pairs, one level off.
  • The old code was also the pattern the IVTC fade fix forbids (an akarin node per frame inside a FrameEval; there it aborted or hung jobs). CLAUDE.md now states it as a rule for every pass.

The code

Before (worker/templates/pipeline_template.vpy, {{#CC_AUTO_WHITE}}):

su = core.std.PlaneStats(c, plane=1)
sv = core.std.PlaneStats(c, plane=2)

def _apply(n, f, clip_in):
    du = (neutral - f[0].props['PlaneStatsAverage'] * peak) * strength
    dv = (neutral - f[1].props['PlaneStatsAverage'] * peak) * strength
    return _expr(clip_in, ['', 'x {:.6f} +'.format(du), 'x {:.6f} +'.format(dv)])

return core.std.FrameEval(c, functools.partial(_apply, clip_in=c), prop_src=[su, sv])

After, where akarin is present:

st = core.std.PlaneStats(c, plane=1, prop='_AwbU')
st = core.std.PlaneStats(st, plane=2, prop='_AwbV')
out = _expr(st, ['',
    f'x {neutral} x._AwbUAverage {peak} * - {strength} * +',
    f'x {neutral} x._AwbVAverage {peak} * - {strength} * +'])
return core.std.RemoveFrameProps(out, props=[...the six _Awb* properties...])

The same arithmetic, per frame. The prefixed property names keep the stats from colliding with a later pass's PlaneStats, and they are removed afterwards. Everything before the akarin branch, and the fallback after it, is unchanged.

Speed of the filter alone

scripts/bench_isolated.py takes _auto_white verbatim from the template before (main) and after, and pulls it through frames() on a synthetic 706x480 4:2:0 clip: AddGrain noise, a chroma cast that changes every frame, and a luma contrast that drifts. No decoder or encoder. _auto_levels, unchanged, is timed alongside for scale.

The machine was never idle while this was measured: another task's heavy tests were running. Two runs are shown. Run A, 1,200 frames, came right after this task's own test suite finished, and the load was not recorded. Run B, 600 frames, was taken with a load average of 165–180 on 8 cores (data/timing_conditions.txt; output in data/bench_isolated_macos-arm64.txt). No measurable change here, and why. The old filter's cost is serial: ~17 ms a frame on this M1, a ceiling of ~60 fps for the job. Here the rest of the chain, sharing 8 cores with another task's tests, ran at ~11 fps, far below that ceiling, so the old filter's work overlapped the other passes and cost almost nothing extra. It becomes the limit when the rest of the chain runs faster than its ceiling, as on the issue's desktop (47.6 fps for SMDegrain + LSFmod, 16.8 with Colour Correction: ~38 ms a frame for the colour correction, at 20% CPU). That case, a free machine fast enough to hit the ceiling, was not measured here. The isolated numbers above are what this change is shown to remove; how much of a whole job that is depends on the machine and the rest of the chain.

Is the picture the same?

scripts/probe_exact.py runs both versions of _auto_white on the same clips: 60 frames at 706x480, every depth (8/10/12/16), every subsampling, strengths 0, 0.37, 0.8 and 1. The new function runs once with akarin and once bound to std.Expr (the fallback). data/probe_exact.txt:

scripts/probe_white_rate.py counts how often, over 600 frames per case (data/probe_white_rate.txt):

DepthChroma planes that differ (of 1,200 per case, 9 cases)Largest difference
8, 10, 12-bit0 of 10,800 at each depth0
16-bit17 of 10,800 (0.16%): 0–5 per case1 sample step

Why: the integer sample x plus the offset rounds to x + round(offset), so only the offset's rounding matters. The old code computed the offset in double precision and wrote it with 6 decimals; akarin reads the PlaneStats mean (a double in [0, 1]) as a 32-bit float, which times a 16-bit peak leaves about 0.004 of a step of error. Where the offset's fraction is that close to .5, the plane rounds the other way. At 12 bits the error is under 0.0003 of a step, and nothing differed. A Python callback stamping a double-precision offset (as the fade fix does) would remove the difference at the cost of Python on every frame again; for 1/65,535 of full range on 0.16% of planes, it is not worth it.

The heavy test app/test/integration_auto_colour_test.dart also checks, through the worker on a real clip (small_clip.mp4), that each automatic filter changes the picture and that the preview of a frame is the lossless encode's frame, sample for sample (max 0).

Why automatic levels stays a std.Levels

Automatic levels has the same shape, a std.Levels (and std.Merge below strength 1) per frame, but a std.Levels is a lookup table built in microseconds, not a compile: ~5,000 fps on its own at 706x480 before and after. Caching each (min, max) pair's node was tried and made no measurable difference on the drifting clip (5,052 → 5,432 fps at 8 bits, 4,843 → 4,118 at 10; machine load not recorded), so it was not kept.

One akarin expression reading the measured points from frame properties was tried too, written as std.Levels' own arithmetic (R78 genericfilters.cpp: clamp, (v − min_in) / (max_in − min_in), × range, + min_out, clamp, + 0.5, truncate). It is not bit-exact. akarin compiles with fast-math, so the division becomes a multiplication by a reciprocal, and where the exact result is a .5 tie the reciprocal's rounding drops it: min_in=52 max_in=162 min_out=16 max_out=235, input 107 is 55/110 × 219 + 16 = 125.5, std.Levels 126, akarin 125. scripts/probe_akarin_levels.py, data/probe_akarin_levels.txt:

Cases are seeded random (min, max) pairs at 8 bits, with three output ranges (16–235, 0–255, 40–200); a case differs if any of the 256 inputs does. With constants in place of properties, opt=1 happened to match and opt=0 did not; with properties neither does. The white balance has no division, which is why it can be one expression.

What changed

  • worker/templates/pipeline_template.vpy: _auto_white's akarin branch; a comment on _auto_levels saying why it is left alone.
  • Tests: test_271 (Rust) and color_correction: automatic colour builds no node per frame (Flutter, push gate) check that the akarin branch reads the means from properties, evaluates nothing per frame and comes before the fallback, and that automatic levels stays a std.Levels. integration_auto_colour_test.dart (heavy) is described above.
  • CLAUDE.md, "One script template": never build an akarin expression per frame, and the fast-math caveat.

Corrections made during the work

  • The plan proposed moving automatic levels into one akarin expression too, after a first check that found no difference. That check covered too few (min, max) pairs; the wider one above found 2.0% of pairs one level off, so the idea was dropped. A node cache tried next gained nothing measurable and was dropped as well.
  • The first run of the exactness probe built its white-balance clips without grain (the bundle has no noise plugin; it now uses AddGrain), and its format table made every "4:2:2" case 4:2:0. It found no difference. The run reported above has grain and real 4:2:2, and it found the two 16-bit cases.

Limits

The machine was shared with another task's heavy tests for every timing: the load average was not recorded for run A and was 165–220 for run B and the chain. Whole-job speed on a free machine was not measured. All speeds are one M1 on macOS. The issue's machine is Windows x86, where akarin's compile cost per frame will differ, but the cost was per frame and serial on every platform, and it is gone on every platform. The isolated numbers are synthetic clips through frames(), the filter's own cost; the chain's speed depends on the other passes and the encoder. The chain's source is a camera clip, not a VHS capture. macOS x64 (no akarin) keeps the fallback: it ran a std.Expr per frame before and still does, so nothing changes there; its speed was not measured on Intel hardware. The exactness probes use synthetic clips (grain plus a moving chroma cast); the 16-bit rate depends on how often a frame's offset lands within ~0.004 of a half step, which is a property of the arithmetic, not the picture.
