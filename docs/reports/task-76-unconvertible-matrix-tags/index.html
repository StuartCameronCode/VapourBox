Task #76: frames tagged with a matrix FFmpeg 9 can't convert

2026-11-21 · macOS arm64 (M1 Pro) · deps 1.18.0-rc2 (FFmpeg 9.0.2, martin-riedl build) · branch stuart/76-sources-tagged-ycgco-bt2020c-smpte2085-c

Summary

FFmpeg accepts all thirteen H.273 matrices as tags, but its scaler can convert a frame from only seven of them. A source tagged ycgco, bt2020c, smpte2085, chroma-derived-nc, chroma-derived-c or ictcp therefore failed every decode that converts its pixel format. That covered the app's before frame and thumbnails, Detect borders, an encode whose decoder or encoder converts (a 4:4:0 or 9-bit source; HuffYUV's yuv422p, AMF's nv12), and, for bt2020c with a PQ or HLG transfer, the HDR display tone map. Task #73 had fixed only the processed preview, whose pipe carries no tags.

Fixed, in two places:

  • The decode neutraliser (decode_tag_neutraliser and its app twin ColorTags.decodeNeutraliser) now replaces such a matrix with the one the preview reads it as (ColorMetadata::scaler_stand_in, derived from #73's swscale_matrix).
  • The encoder ends its -vf with setparams=colorspace=<stand-in>,scale,setparams=colorspace=<tag>. The output keeps the source's tag and stores the same samples an untagged source would.

The HDR tone map reads bt2020c as bt2020nc. Task #73's plan said HDR bt2020c was unaffected; it was not (§4).

Every number below comes from scripts/probe-unconvertible-matrices.sh. Raw output: data/probe-macos-arm64.txt.

Every YUV-to-YUV conversion is independent of the replacement: a JPEG, another subsampling, depth or packing. Those are every conversion of the source the app and the worker make: the before frame, the thumbnails, the pipe-format decoders, Detect borders' yuv444p, Noise/Halo. Descale reads the Y plane itself (task #17), and HDR goes through zscale. So the neutraliser changes no pixel of any of them. Only RGB or gray output reads the matrix, so the replacement is the preview's reading (§5). An RGB decode then matches the preview, which matters to the test harness's _frameRgb24.

Two alternatives fail. Declaring the input unknown while the output says ycgco fails the same way, because the output tag is a negotiation target the scaler can't produce. Declaring neither works, but the file loses its tag. A ycgco file that says nothing plays as BT.601.

The bridge swaps the tag for its stand-in around an explicit scale, which negotiates its output format with the encoder exactly as the inserted one would, and then puts the tag back. It doesn't need to know the target format, so it also covers conversions ffmpeg chooses on its own. When nothing converts, its scale passes the frames through unchanged. So the worker adds it for every encode whose output matrix is one of the six, and never otherwise. A Custom FFmpeg -vf replaces the chain and the bridge with it, and the job log says so.

Correction to task #73's plan, which said the HDR path "already reads bt2020c through zscale, so it is unaffected". It doesn't: an HDR source tagged bt2020c had no preview, before frame or thumbnails. display_tonemap_filter and HdrDisplay.toneMapFilter now read it as NCL, which has the same Kr/Kb and is the reading the SDR preview already uses.

5. Decision, per tag

TagConverted asWhy (task #73's reading)
rgb (gbr), bt709, fcc, bt470bg, smpte170m, smpte240m, bt2020ncnever touchedThe scaler converts them. Changing a valid matrix the scaler converts moves YUV → gray by up to 28 levels (reserved-tags report).
bt2020cbt2020ncThe same Kr/Kb.
chroma-derived-nc / -cbt709 or bt2020nc by the primaries, else unknownH.273 derives exactly those coefficients from those primaries.
ictcpbt2020ncIt exists only with BT.2100's primaries.
ycgco, smpte2085unknownNo YCbCr matrix comes close.

The rule "never clear a valid tag" was about a pixel change. It becomes "never touch a matrix the scaler converts". For the six it can't convert, the alternative is no picture.

6. Verification

  • decode_neutraliser_cases.json holds the neutraliser for 33 tag combinations, and both the Rust and Dart tests check every row. Rust also checks that every MATRICES entry, with every primaries value, is either converted as it is or stands in as a matrix the scaler converts.
  • colour_tag_ffmpeg_test.dart (push gate, on each platform's bundled ffmpeg) covers three cases. With the neutraliser, every matrix decodes to JPEG, rgb24, yuv444p and yuv420p10le. The bridge, on lossless x264 (nv12) and HuffYUV, keeps the tag and every sample for each of the six. The HDR tone map gives a picture for bt2020c with PQ and HLG.
  • integration_unconvertible_matrix_test.dart (heavy, 37 tests) runs against twins of the same picture tagged with the stand-in, for each of ycgco, bt2020c, smpte2085, ictcp and chroma-derived-nc:
    • The before frame and thumbnail fail without the fix and match the twin's with it.
    • The reports of --detect-crop, --detect-noise-halo and --detect-native equal the twin's.
    • A HuffYUV encode keeps the tag and the twin's samples.
    • A ycgco 4:4:0 encode, whose decoder converts, equals the twin's.
    • An HDR bt2020c preview and before frame equal a bt2020nc twin's.
    The encode, 4:4:0 and HDR cases fail with the worker built from the code before this change.

Limits

  • Synthetic testsrc2 and one real clip (small_clip.mp4). The probes ran on one FFmpeg build (macOS arm64); the push-gate test runs the fixes on each platform's bundle.
  • The bridge's sample identity is measured on x264, HuffYUV, FFV1 and rawvideo. NVENC, QSV and AMF can't be run here; their conversion is the same scaler negotiation.
