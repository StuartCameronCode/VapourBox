Issue #144 — KNLMeansCL fails on 10-bit sources on Windows, and is unreliable on macOS

2026-11-03 · issue #144 · measured on an M1 Pro (macOS arm64) against the deps 1.14.0 bundle · reproduced and fixed on Windows x64 (AMD Radeon 780M), see 3d

Outcome. Every platform moves to the same KNLMeansCL: Jaded Encoding Thaumaturgy's maintained fork, v1.3 (GPL-3.0). It is built from that tag on macOS and Linux, and taken from its PyPI wheel vapoursynth-knlmeanscl 1.3 on Windows. That fixes two separate bugs:
  1. Windows shipped Khanattila's v1.1.1 release (2018), which refuses every 9–15-bit clip except packed YUV444P10 / RGB30. The KNLMeans Noise Reduction method failed outright on any 10-bit 4:2:0 or 4:2:2 source, as reported. This was first read from the source. It has since been reproduced on Windows with the 1.14.0 DLL and shown fixed with v1.3 (section 3d).
  2. macOS built Khanattila's unpinned master. On Apple's OpenCL it gives a different result on a repeat run in 24 of 60 cases (by 110–255 levels), and even when repeatable it does not compute the algorithm's result at low h. v1.3 is repeatable in all 60 cases and matches a CPU reference.

1. The reported failure (Windows)

From the user's job log (Windows 11, RTX 3060), with the username path removed:

Python exception: knlm.KNLMeansCL: only YUV444P10 and RGB30 are supported!
  clip = core.knlm.KNLMeansCL(clip, d=1, a=2, s=4, h=1.20, channels="Y", device_type="gpu")

The device had already been selected ("gpu", from the worker's probe), so this is a format refusal, not a missing-OpenCL case. The message comes from v1.1.1's NLMVapoursynth.cpp, which the Windows script downloaded as a release zip:

} else if (d.vi->format->bitsPerSample == 10) {
    if (d.clip_t & NLM_CLIP_REF_YUV || d.clip_t & NLM_CLIP_REF_RGB) {
        ...CL_UNORM_INT_101010...          // packed 10-10-10 only
    } else {
        vsapi->setError(out, "knlm.KNLMeansCL: only YUV444P10 and RGB30 are supported!");
}} else if (bitsPerSample == 16) { ... } else {
        "knlm.KNLMeansCL: P8, P10, P16, Half and Single are supported!"   // 9/12/14-bit

NLM_CLIP_REF_YUV is set only for channels="YUV" on 4:4:4. Our template calls channels="Y" then channels="UV" (4:2:0 can't take "YUV"), so every 10-bit source fails, and 9/12/14-bit fail with the second message. Only 8-bit, 16-bit and float work. pinterf's 2020 commits (ad0a020, "Add 9-15 bit support for all modes") fixed this on master, but Khanattila never cut a release with them, so the only Windows binaries were v1.1.1 and pinterf's own 2020 builds.

QTGMC's knlmeanscl denoiser is affected the same way: havsfunc's KNLMeansCL wrapper makes the same channels='UV' call. The user's QTGMC jobs presumably work because those sources are 8-bit, or because QTGMC's High precision option runs it at 16-bit. That is an inference; it has not been confirmed with the user.

Why nothing caught it

  • The 2026-10-25 depth-parity measurement for the new KNLMeans method ran on a Mac, which had the master build.
  • integration_high_bit_depth_filters_test.dart did not include KNLMeans.
  • No hosted runner has an OpenCL device (lavapipe is Vulkan only), so KNLMeans has never run on Windows in CI, at any depth. The worker's device probe uses an 8-bit clip, so it passes there too.

2. The candidate: KNLMeansCL 1.3

Jaded-Encoding-Thaumaturgy/vapoursynth-knlmeanscl continues Khanattila's master (merge base ca424fa, 2023-01-05). Its OpenCL kernel (NLMKernel.cpp) is unchanged. Its 1.2 and 1.3 changes: VapourSynth API v4, wheels for every platform, Apple CL_INVALID_VALUE handling in auto device selection, and a fix for Apple's clEnqueueFillBuffer not completing when no event is requested, which is the macOS bug in section 3. Its 9–16-bit code (NLMVapoursynth.cpp:693) accepts every integer depth for every channels mode.

Source builds rather than wheels on macOS and Linux: the macOS x86_64 wheel is minos 15.0 (the Intel floor is 12.0), and the Linux wheel bundles its own libOpenCL loader; both platforms already build every other plugin from a pinned tag. v1.3's meson.build locates the VapourSynth headers through r = run_command(py, '-c', 'import vapoursynth …') with r.stdout().strip() used later. Neither script's meson patcher recognised that assigned form, so both now handle it. The patchers were checked against v1.3, BM3D r12, CAS and mvtools; the three existing forms patch exactly as before.

3. Measurements (macOS arm64)

All from scripts/run.sh. Synthetic clips (gradient, coloured blocks, grain from grain.Add) at 320×240; frame 5 of 11; d=1 a=2 s=4. Differences are mean absolute, in 8-bit levels.

3a. Does it run, and is it repeatable?

The depth matrix is 6 depths (8, 9, 10, 12, 14, 16) × 4:2:0 / 4:4:4 × channels Y / UV (and YUV on 4:4:4) × device gpu / auto = 60 cases. Each build ran it twice, each time in a fresh process.

Which cases go wrong on master changes from run to run. In one pass, 18 of 60 were garbage (more than 20 levels from v1.3) and the remaining 42 still differed by about 2.3–3.1 levels (see 3b). Under v1.1.1 on Windows, the 9–15-bit Y and UV cases are exactly the ones that would error.

3b. Is it computing the right thing?

To decide which build is right where they disagree, nlm_reference.py implements the kernel's maths on the CPU for 150 sampled pixels. The weight is exp(−P·255² / (h²(2s+1)²)), and the centre pixel's weight is wref × max(largest weight, FLT_EPSILON) (the max-weight buffer starts at CL_FLT_EPSILON). The input is a flat-ish picture with grain of variance 40 (RMS 6.3 levels).

Lower is better. About 0.25 is the floor from GPU float rounding and 8-bit output. At h=1.2 every weight here is about e−55, far below the epsilon floor, so the correct output is the input. Master denoises anyway because its max-weight buffer was never filled. The master figures are from a run where it produced no garbage; in other runs, h=2.0 and h=5.0 came out at about 125 levels.

What this means for users. The KNLMeans default (h=1.2, KNLMeansCL's own) removes little from heavy grain. It denoises noise of a couple of levels RMS, but at 6 levels every weight is below the floor. Windows and Linux have always behaved like that. macOS users saw stronger denoising, and the occasional garbage frame, because of the race. After this change macOS matches the other platforms, so a macOS user's existing KNLMeans settings will denoise less. The defaults are unchanged; whether 1.2 is the right default for the sources people use KNLMeans on is a separate question.

Not run on Windows: the real app on a real 10-bit file, the repeatability matrix from 3a, the CPU-reference comparison from 3b, and an NVIDIA GPU like the reporter's RTX 3060.

4. What wasn't tested

  • Windows: tested since, see 3d. This was untested when the report was first written. It has since run on Windows x64 with an AMD GPU: v1.1.1 reproduces the error and v1.3 fixes it, both in the Noise Reduction pass and in QTGMC's denoiser. Still untested on Windows: an NVIDIA GPU (the reporter's), and the real app on a real 10-bit file rather than the test harness.
  • macOS x64 and Linux: the scripts are changed, but nothing has been built or run there. build-deps-* CI is the build test. Neither platform can run KNLMeans in CI (no OpenCL).
  • Only one kind of input: synthetic grain on synthetic pictures. That is enough to tell right from wrong against the reference, but says nothing about the best h for real footage.
  • NVIDIA and Intel OpenCL drivers. AMD's ran the app-level tests in 3d, but not the repeatability matrix or the CPU reference, which have run only on Apple's. The fill-buffer race is described as Apple-specific (see GROMACS issue 4852, linked in v1.3's source).

5. Decisions

  • Swap the plugin rather than work around the depth in the template (for example by converting 9–15-bit to 16-bit around the call). The workaround would have fixed only the Windows error. It would have left QTGMC's havsfunc call broken on the same sources and macOS still producing garbage.
  • One version everywhere (v1.3), as the scripts already do for BM3D (tag r12 = wheel 12.0), so a job produces the same picture on every OS.
  • Leave the default h alone: the default isn't what broke, and changing it would change every platform's output.

6. Corrections made during the work

  • The first reply to the user suggested switching Color Format to 8-bit as a workaround. That would not have worked: the output colour conversion is the last step in the script, after Noise Reduction. It was withdrawn before the reply was posted.
  • The first probe loaded both builds into one process and got nonsense. I put that down to the two copies' OpenCL state colliding. Running each build in its own process showed the garbage was master's alone. The scripts still use one build per process.
  • The first two versions of the CPU reference were wrong: they left out the CL_FLT_EPSILON floor and missed that luma's 3·d² distance cancels NLM_LEGACY = 3. Those versions made master look right at h=1.2. Only the corrected version, the one in scripts/, is used in 3b.
