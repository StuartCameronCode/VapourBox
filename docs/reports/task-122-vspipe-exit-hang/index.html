vspipe that does not exit after its last line

Task #122, 2026-11-27. Measured on GitHub's windows-latest runners with deps 1.18.0-rc4, both CPU tiers (windows-x64 and windows-x64-v2 bundles), the worker's debug build, under load (every core but one running yes). Runs 45920512665 and 45927466967 of repro-vspipe-exit.yml. The original failure is task #120's: the format sweep's stabilize/pitchMode=auto row, 720x480 yuv444p16le progressive, past its 360 s budget on Windows, and 3 of 80 previews in task #120's repro (deps 1.18.0-rc3), each with vspipe's last thread in ExitProcess → NtTerminateProcess.

Outcome

  • Fix (in the worker): a vspipe that has printed its final line is given 30 s to exit, then stopped. worker/src/vspipe_exit.rs knows the lines R78's main prints just before it returns (Output N frames in …, Script evaluation failed:, the output-node and header errors). After one, the encode and the preview wait VAPOURBOX_VSPIPE_EXIT_GRACE_SECS (default 30, 0 = forever) and kill vspipe. The job log says so. After a stop the encoder's result decides when vspipe finished cleanly (vspipe flushes its output before printing Output); otherwise vspipe's error does. Output alone does not mean success: R78 prints it after Error: Failed to retrieve frame … too. A vspipe a kill cannot end fails the job and never hangs it.
  • Reproduced, and the fix seen working on a runner: run 1, v2 leg, guard arm, run 68. vspipe printed Output 1 frames in 0.75 seconds at +988 ms and did not exit. The worker stopped it 30 s later, and the preview returned its frame (32.7 s in all; data/run1-v2-guard-run68-stderr.txt).
  • Its rate depends on Defender: run 1 saw 1 hang in 3,200 pitch-auto previews across both tiers, in an arm that had Defender on by mistake; run 2, with Defender on throughout, saw 347 in 3,000. Task #120's repro saw 3 in 80.
  • Cause: Microsoft Defender real-time protection suspends vspipe's last thread while the process exits, and does not resume it. In run 2 (Defender on, guard off), 347 of 3,000 pitch-auto previews hung: 218 of 1,500 on x64 and 129 of 1,500 on v2. Every one printed Output 1 frames. In every one, cdb's non-invasive attach (which adds 1 itself) showed the one thread left at Suspend: 2, and NtResumeProcess let vspipe exit at once (0–0.02 s), after which the worker returned. 343 were in NtTerminateProcess; 4 were earlier in the exit path (atexit destructors, FLS cleanup, and once inside Defender's own MpOav.dll). Defender's DLL is loaded in the process. No WerFault was involved. With Defender off: 0 hangs in 3,200 previews of run 1's Defender-off arms. vspipe's own code does nothing wrong, so the worker-side stop is the fix. A stop terminates the suspended process (run 1's run 68 shows it).
  • Debugging aid: the preview now echoes vspipe's stderr as it arrives (vspipe: +<ms> ms …; the app leaves those lines out of a failed preview's error text). The test harness puts the stderr tail in a timed-out preview's or job's report, so a hang shows where vspipe got to.

Method

scripts/repro-vspipe-exit.ps1, run by scripts/repro-vspipe-exit.yml (copies of .github/scripts/ and .github/workflows/ as run). It runs the worker's preview of the sweep row's job (data/pitch-job.json, frame 15) directly, one run at a time, with a 60 s limit. Most arms set the guard off (grace 0), so a hang stays a hang. Each arm changes one thing and restores it afterwards. A hung run is examined before it is touched:

  1. the process tree and the worker's stderr, which carries vspipe's lines;
  2. vspipe's threads (state, wait reason);
  3. WerFault processes and Application events 1000/1001/1005;
  4. cdb's non-invasive stacks;
  5. NtResumeProcess, then TerminateProcess, each with 10 s to take effect, and whether the worker then returns.

Tests

  • vspipe_exit::tests (Rust, every platform): the final-line table, the grace from the environment, the stop against a fake process and against a real child that prints the summary line and sleeps. The outcome notes are covered too.
  • app/test/vspipe_exit_guard_test.dart (push gate; not on Windows): a wrapper runs the real vspipe and then becomes sleep 600 holding vspipe's pipes, reached through the debug-only VAPOURBOX_VSPIPE. With a 3 s grace the preview returns its frame in about 5 s and the encode writes the whole clip in about 6 s. Each says it stopped vspipe.
  • app/test/vspipe_echo_prefix_test.dart: the app's vspipeEchoPrefix is the worker's VSPIPE_ECHO_PREFIX (docs/TWINS.md), and previewErrorText drops the echo.

Limits

  • Run 1 saw one hang, with the guard on. Run 2 took stacks of 347 real hangs with the guard off.
  • Whether Defender was on in task #120's runs is not known. The script found real-time monitoring off on the hosted image, and #120's hang rate (3 in 80) lies between run 1's and run 2's. Two other differences were not tested: deps 1.18.0-rc3, whose Windows plugins partly failed to load (task #116), and the launcher (Dart's Process.start against PowerShell's Start-Process).
  • The guard bounds a hang after a final line. A vspipe stuck before printing one is still caught only by the encode's 600 s stall watchdog, or the harness's limits for a preview.
  • Hosted runners only, debug worker, one job (the sweep row). Real-time protection is on by default on users' Windows machines, so users may meet this too. No user report of it exists. Without the guard it would be a preview that never returns, or an encode that never finishes after its last frame.
