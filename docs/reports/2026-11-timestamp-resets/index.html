Task #21: MPEG-PS/TS whose timestamps reset mid-file

2026-11-14 · follows issue #169 (task #14, its report, §8) · measured on an Apple M-series Mac (macOS arm64), deps 1.16.0 (FFmpeg 9.0.2), with this branch's debug worker

Outcome: fixed by decoding a joined copy. A program or transport stream whose clock goes back (or leaps forward) mid-file is what you get from a DVD title that spans VOB IDs, a broadcast capture spliced across a programme change, and, as found here, VapourBox's own DVD import of a multi-title set. On such a file the app counted only the last segment's frames, so even an untrimmed encode stopped at the first reset. A seek past a reset was undefined, and #169's trim stopped at the reset.

The worker now scans a TS/PS's packet timestamps once. When the clock resets, it stream-copies the file into the same container without -copyts. ffmpeg's own discontinuity correction then makes the timestamps continuous, with one offset per segment shared by every stream, so sync within a segment is kept. Everything decodes that copy. A file with no reset is never copied, and every argument it gets is unchanged.

1. Definition: frame N across a reset

Frame N is the Nth slot of the source's continuous timeline, with each segment following the last exactly as ffmpeg's correction joins them (what a player shows). Frame 0 is still the video's first picture (#168), and slots are still on the constant-rate grid (#157).

A reset is what ffmpeg itself corrects in a discontinuous format when -copyts is off. Per audio or video stream, in decode order, it is a DTS more than 0.1 s behind the stream's last, or more than 10 s (dts_delta_threshold) ahead. source_continuity::resets_from_packets is the one statement of this rule, and the app reads its answer through --scan-timestamps. fixtures_probe.py checks the edges:

All 57 tests in the file pass, including #14's fixtures, which have no reset and therefore no copy.

3. Why a copy, and why this container

  • Per-segment offsets in each decoder (the task's first idea) were rejected. -ss can't reach a later segment, because its timestamps occur once per segment, so every seek would need a byte offset and its own setpts continuity. The sound paths that copy (passthrough) can't filter at all. It would have meant five or more argument builders, in both Rust and Dart, made segment-aware.
  • Dropping -copyts was rejected. It fixes neither the frame count nor a seek past a reset, and #169 showed that the relative trim is wrong on late-video TS.
  • An MKV copy was rejected. It needs +genpts (some PS packets have no PTS). It stores 1 ms timestamps, which risks the soft-telecine slot placement of #174. It moves the source out of the TS/PS seek rules of #169. A same-container copy keeps every format-specific rule byte for byte.
    Correction. At planning, an MKV remux measured quadratic in the number of resets (10 / 30 / 90 resets: 0.18 / 0.85 / 7.5 s). cost_probe.py did not reproduce that on its 4 s 720x576 AC-3 segments: 0.06 / 0.10 / 0.31 s, no faster-growing than the PS copy. The planning segments were different files (small testsrc2, MP2). The quadratic growth is therefore not established, and the rejection rests on the other reasons above.
  • Always remuxing every DVD import was rejected. A title with no reset would gain a muxer pass and nothing else.

cost_probe.py, internal SSD. The scan reads the whole file. At planning it took 0.72 s for 482 MB and 90k packets, so expect about 1–2 s per GB. The copy also needs free space equal to the source in the temp folder (Settings → General → Temporary Files). On a slow disk or a network share, both scale with read speed.

5. How often resets occur (step 1): not measured

This machine has no DVD rips or broadcast recordings, so the frequency in real material is unmeasured. reset_survey.py runs the shipped rule over any files or folders. What reading the code did establish:

VapourBox's DVD import copies the whole title set, not the title. dvd_reader::extract_title opens the title's VTS (DVD_READ_TITLE_VOBS) and copies every block of it. That means every title in the set (a TV-series disc commonly holds all its episodes in one), every angle interleaved, and the chapter range ignored. Each title usually starts its own clock, so resets in VapourBox's own DVD output are likely to be common. The import now joins them (§6), which makes such a file decode correctly from end to end. Extracting only the chosen title is a separate fix (task #27).

6. What changed

  • worker/src/source_continuity.rs: the reset rule, the scan, the copy arguments (-map 0:v -map 0:a? -map 0:s? -c copy -map_metadata 0 -f vob|mpegts, no -copyts, no -muxdelay, so the copy keeps the source's start time; if the muxer refuses a subtitle stream, it retries without subtitles), and the check before a copy is used (no reset left, every video packet present).
  • CLI: --scan-timestamps and --make-continuous … --output. DVD import extracts to .part and then renames it, or joins it into the output.
  • A hand-written encode job (continuityChecked unset) on a file with a reset gets a warning, never a silent change: its frame numbers were chosen against an unknown timeline.
  • App: analysis makes the copy (TimestampContinuityService). QueueItem.decodePath is what every probe and decode reads, while inputPath still names the output, Show in Folder and sidecars. A static test classifies every read. Video Info and the log say when a copy is used, and the copy is deleted with the item.

7. Not tested, limits

  • No real DVD or DVB material (§5). Seamless-branching and multi-angle titles are untested beyond the fact that the import copies their interleaved blocks.
  • Sync is checked on synthetic segments whose sound and picture start within 11 ms of each other. A segment whose own sound leads its picture by more keeps that lead (one offset per segment), but that is not measured here.
  • Preview and the detectors do not scan; they read whatever the app hands them. A hand-written preview job on a file with a reset is not warned about.
  • One machine (macOS arm64). The worker's rule and the copy are plain ffmpeg/ffprobe calls, the same on every platform.
