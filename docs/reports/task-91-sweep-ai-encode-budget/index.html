The format sweep's AI-model encodes: 10 frames, not 30

Task #91, 2026-11-22. Nightly format-sweep legs on GitHub's macos-15-intel runners (Intel Core i7-8700B, 4 vCPUs; both x64 CPU tiers), deps 1.18.0-rc2, the ai-runtime add-on's onnxruntime 1.23.2; the other platforms' legs of the same runs for comparison. Wall times of whole test groups and rows as the sweep logs them. No screenshots: no picture is compared here, only times.

Outcome

  • The fault: on macOS x64, the sweep's delta-only check (an FFV1 encode whose untouched samples must be bit-exact) timed out at the 300 s job budget on most Colourisation rows and one Face Restoration row, every nightly.
  • Most of it was Core ML, and task #94 (report) has removed it: Intel Macs now run the ai-runtime models on the CPU, which was faster on these runners in every comparison. That is also the user-facing fix: the minutes of Core ML start-up before an Intel Mac's first frame are gone. Nothing more is needed in the worker.
  • What was left is the test's budget: on #94's verification run (CPU), DeOldify's 30-frame encodes still timed out on all four rows of the x64 (v3) leg; every other add-on variant passed. DeOldify costs ~3.3 s a frame there (#94's measurement), and the sweep runs two rows at once on 4 vCPUs, each ONNX Runtime session wanting every core.
  • Fix (test only): a delta-only encode of an add-on (AI-model) variant covers the fixture's first 10 frames (sweepAddonEncodeFrames), as a trim from frame 0, and the comparison takes the same frames. The check needs both temporal edges (DDColor reads two frames either side, Face Restoration's landmarks two) and some full windows, not 30 frames. Every other variant still encodes all 30.
  • Rejected: forcing the CPU in the test (moot on Intel after #94; on arm64 it would stop the sweep running the Core ML path users run), a longer timeout alone (minutes of CI per row for no extra coverage, and a real slowdown hides longer). If 10 frames is ever not enough, run the add-on encodes one at a time (the budget is per process) before raising the timeout.

Arithmetic: DeOldify at its default render size runs the model once per frame (temporal radius 1, memoised): 30 runs × ~3.3 s (#94: 3.2–3.5 s a frame on these runners, single process) + ~10 s start-up ≈ 110 s alone. Two encodes sharing 4 vCPUs roughly double it, ≈ 220–250 s, and a slower runner draw passes 300 s: v2 passed at about 150–190 s a row, v3 did not. At 10 frames: ≈ 45 s alone, ≈ 100–130 s two at once, a 2.3–3× margin.

Limits

  • The x64 numbers are GitHub's Intel VMs (4 vCPUs, paravirtual GPU); runner draws differ by about 2× (DeOldify's group: 391 s on one, 668 s on the other, same code). No real Intel Mac was measured; #94's report covers what that leaves open about the provider choice.
  • Group wall time includes the comparison and the fixtures' decodes, not only the encodes; it is an upper bound on the encodes' share.
  • The 10-frame margin is an estimate from #94's per-frame times; the first nightly with this change is the measurement, and is added below when it has run.
