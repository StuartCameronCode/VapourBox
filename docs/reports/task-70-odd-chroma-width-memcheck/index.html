QTGMC's "uninitialised memory" at an odd chroma width: a memcheck false positive

Task #70, 2026-11-19. Measured on GitHub's ubuntu-24.04 runners: AMD EPYC 9V74 (run 44498405213) and Intel Xeon 6975P-C (run 44498392281), the same inputs on each (data/workflow-inputs.txt). Deps 1.16.0 linux-x64 (VapourSynth R78, MVTools master built from source, havsfunc r31), valgrind 3.22.0. macOS arm64 (deps 1.16.0) for the harness and the push-gate test. Every number comes from .github/workflows/repro-native-crash.yml with the inputs in data/, or from scripts/.

Outcome

  • QTGMC does not read uninitialised memory into its picture. Task #66 found valgrind reporting QTGMC's output as uninitialised on x86 Linux when the chroma width is odd and the depth is above 8 bits (98x96 and 722x480 4:2:0 at 10–16 bits, 4:2:2 12-bit). Three independent checks on x86 show that those bytes never reach the output:
    • Two memory fills: every flagged case run under valgrind with every allocation filled with 0x00, then 0xff, writes the same output (table 2). A deliberate padding read in the same harness writes different output.
    • Padding poison: the row padding of every frame QTGMC's filters produce, filled with a different pattern per seed, gives the same picture for seeds 1, 2 and 3 in all 32 cases: Draft, Fast, Slower and Placebo × 98x96 and 722x480 × 4:2:0 10/12/16-bit and 4:2:2 12-bit (table 3).
    • VapourSynth's C kernels: with core.std.SetMaxCPU('none'), every flagged QTGMC case is valgrind-clean (table 1).
  • The cause is valgrind's model of one instruction. QTGMC follows mv.Degrain1 with std.Merge. VapourSynth's AVX2 16-bit merge reads whole vectors, stride padding included, and multiplies with vpmaddwd. valgrind treats that instruction as one opaque operation per 64-bit half, and each half holds two adjacent columns. So at an odd plane width the last real column shares a half with a padding column, and memcheck marks it undefined. The real arithmetic never mixes the two columns (section 2). Degrain1 + std.Merge alone reproduces the report exactly, with no QTGMC.
  • Nothing to patch. No MVTools patch, no deps release, no template guard. Padding the width to 724 (the task's proposed guard) would have changed every 718- and 722-wide QTGMC job for no gain: the havsfunc.QTGMC contract in plugin_formats.py records that padding the width moves columns up to 5 levels at 854x480.
  • Kept: a push-gate test, app/test/qtgmc_stride_padding_test.dart, runs the poison harness on every CI platform (x86 included) and fails if a VapourSynth or MVTools update lets padding reach QTGMC's picture. The repro workflow gains verify (the two memory fills) and poison inputs, so the next memcheck finding can be checked at the output in one dispatch.

Correction to task #66's report: its "Found on the way" list says QTGMC reads uninitialised memory at these sizes. That is what memcheck reported. This report shows the bytes never reach the output. A dated note there links here.

1. Reproducing it without QTGMC

bare.vpy (task #66's report, scripts/bare.vpy, extended here) runs one call on a synthetic moving clip under valgrind --track-origins=yes --error-exitcode=99, writing y4m. New for this task: degrain_merge is mv.Degrain1 (QTGMC's arrangement: levels=1 super, vectors from a search super) followed by std.Merge(out, source, 0.25), as QTGMC Draft's binomial1 does. cpu=none calls core.std.SetMaxCPU('none') first, which switches VapourSynth's own kernels to C (plugins are unaffected). defined=1 makes the source write its whole buffer, padding included.

2. Why memcheck flags a column it doesn't need to

VapourSynth allocates each plane row with a 64-byte-aligned stride and initialises nothing. mv.Degrain1 writes every visible sample (the right and bottom strips that blocks don't cover are copied from the source, MVDegrains.cpp), but not the padding. At 98x96 4:2:0 16-bit storage a chroma row is 49 samples (98 bytes) in a 128-byte stride.

VapourSynth R78's 16-bit merge, vs_merge_word_avx2 (src/core/kernel/x86/merge_avx2.cpp, lines 64–100), works 16 samples at a time, so the last vector of the row includes padding. It interleaves the two inputs (_mm256_unpacklo_epi16(v1, v2), line 82) and multiplies each pair by the weights with _mm256_madd_epi16 (line 86): each 32-bit result is w1·v1[c] + w2·v2[c], one column. Column 48's result never involves column 49.

valgrind 3.22 translates vpmaddwd (VEX/priv/guest_amd64_toIR.c: math_PMADDWD_256 at line 11414 splits into two math_PMADDWD_128, line 11392) into a call to the helper amd64g_calculate_mmx_pmaddwd for each 64-bit half. memcheck can't see inside such a helper: one undefined bit in its inputs makes its whole 64-bit result undefined. That explains every row of task #66's table:

  • Odd chroma width (49 at 98 wide; 361 at 722): the last column shares a half with padding. Even widths (50, 48, 98 at 4:4:4, 360) pair real with real and padding with padding.
  • Above 8 bits: 8-bit merge (vs_merge_byte_avx2) uses vpmulhrsw, which memcheck tracks lane by lane.
  • "It takes QTGMC's arrangement": it takes a Merge after the Degrain. Degrain alone is written by vspipe row by row, visible bytes only.
  • Slower's 58,773 errors: Slower's search clip is std.Merge(Resize(…), repair0, 0.1), so the same pairing taints its last chroma column. MVTools' motion search compares blocks there with branches, so memcheck reports each branch, and every output sample that depends on a vector inherits "undefined". The vectors themselves are computed from defined data, as tables 2 and 3 show.

3. The bytes never reach the output

Two memory fills (workflow input verify): each case runs twice under valgrind, with --malloc-fill=0x00 and 0xff, which fill every new heap block. Bytes no filter wrote differ between the two runs. If they reached the output, the output would differ.

Padding poison (scripts/poison.py, workflow input poison): havsfunc's, mvsfunc's and adjust's core is replaced by a proxy. Each core.<ns>.<fn>(…) call's output passes through a std.ModifyFrame that copies the frame and fills its row padding with a pattern derived from the seed. The source is poisoned the same way. Then QTGMC's visible output (4 frames) is hashed. A positive control reads back the padding of one poisoned mv.Degrain1 frame, which must differ by seed. scripts/leak_check.py is the negative control: QTGMC followed by one deliberate padding read gives different hashes per seed.

The same harness on macOS arm64 (deps 1.16.0) gives one picture per case too, and the push-gate test now checks four of these cases on macOS arm64, macOS x64, Windows and Linux on every push.

Intel Xeon 6975P-C (run 44498392281): every row of tables 1, 2 and 3 is the same, and the output hashes are identical to the AMD runner's, case for case (data/*-intel.*). Padding poisoned per seed reaches whatever SIMD path each CPU takes, so a padding read on either would have split its own seeds.

Limits

  • Poison covers what the proxy reaches. Calls havsfunc makes as clip methods (clip.std.X(…), DitherLumaRebuild(…).mv.Super(…)) don't go through core, so their outputs keep unpoisoned padding (their inputs are poisoned). The two-fill check covers those buffers.
  • Two fills cover fresh allocations only. VapourSynth recycles frame buffers within a process. A recycled buffer holds an earlier frame's bytes, which are the same in both runs, so the check cannot see a read of those. The runs are short and the poison check covers recycled frames, because it writes the padding on every frame.
  • What is proved: QTGMC's visible output does not depend on stride padding at these sizes, on these runners and bundles. Not proved: that no other nondeterminism exists. Task #62 (FFT3DFilter) was a different cause and is fixed in deps 1.18.0.
  • Every poison row ran at the default thread count; the plan's one single-thread row was not run. Threads change which buffer a frame lands in, not what is written to its padding, which the poison sets on every frame either way.
  • arm64 has no valgrind run. It doesn't need one for this finding: the poison test runs there on every push.

Checking the next memcheck finding

A memcheck "uninitialised" report on a VapourSynth graph at more than 8 bits with an odd plane width is expected, and is not by itself a bug. Before acting on one, dispatch repro-native-crash.yml with modes: none and the case in verify (two fills) and bisect with :cpu=none. If the outputs are the same and the C kernels are clean, it is this false positive. If the outputs differ, it is real; poison and locate narrow it down.
