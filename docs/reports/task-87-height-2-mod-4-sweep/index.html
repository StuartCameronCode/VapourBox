Task #87: the 96x66 sweep rows

Four faults at a field-flagged 4:2:0 frame whose height is 2 mod 4 (720x486; the sweep's 96x66). Measured 2026-11-21 on macOS arm64 (M1 Pro), deps 1.18.0-rc2.

Summary

Every nightly format-sweep leg since the first (run 44127090331, 2026-11-17) failed the same rows on every platform: 6792 rows, 6 failed plus the bit-exact group. The 96x66 rows (task #57) merged the same day as the sweep (#47), #56 and Bifrost v4.0 (#60), so there is no earlier nightly to bisect: the rows exposed faults that are older than them. There are four causes. All four are real faults, so no tolerance or knownFailures entry was added.

A: unpadded conversions (Resize error 1027)

zimg converts a field-flagged clip per field. On a 4:2:0 frame 66 rows high the chroma has 33 rows, so a field has no whole chroma height, and zimg refuses even a pure depth change (depth.py, flagged rows):

66 16 -> 8  {0: ('0f34219a', …), 2: ('ERR Resize error 1027 …'), 'strip': ('0f34219a', …)}

Deband's 16-bit rows passed because nothing is restored there. The fix pads the frame to whole field chroma rows by repeating each field's own last row, and crops the result back (plugin_formats.pad_around, task #57). With field_based_only, a progressive frame or one that already fits takes the same path as before, so its output does not change. Error diffusion still runs per field. colorize.py's source clip is 4:4:4, so its step is given in luma rows (2 << fmt.subsampling_h). ai_runtime imports plugin_formats lazily, which leaves the runtime's self-test unchanged.

B: the unwritten last row

zfield.py: a 48x33 GRAY8 plane shifted with resize.Spline36(src_top=-0.5, src_left=1). Unflagged, the last row is computed. Flagged, it is never written:

0 shift (33, 48) rows-1.. [47, 97, 177, 101, 146, 33, 83, 163]
2 shift (33, 48) rows-1.. [0, 0, 0, 0, 0, 0, 0, 0]

Bwdif behaves the same on any plane with an odd number of rows, whether or not the clip is flagged (lastrow.py). The source's chroma lies in [peak/4, 3peak/4] over a BlankClip whose chroma is 0, so a row nobody wrote reads 0 or leftovers from another frame:

 8-bit 96x66 fb=0 bwdif field=3   before NOT WRITTEN [0, 0, 0, 0, 0, 0]
 8-bit 96x66 fb=2 bwdif field=1   before NOT WRITTEN [130, 155, 179, 74, 98, 123]   (another frame's row)
16-bit 96x66 fb=0 bwdif field=1   before NOT WRITTEN [0, 0, 0, 0, 0, 0]
                                  after  written   (every case, 8/10/16-bit, both flags)

Under MallocScribble=1 MallocPreScribble=1, LUTDeRainbow's internal luma-to-chroma resize (66 → 33 rows, field-flagged) leaves its last row at 170 (0xAA), which is the scribble pattern.

That explains the parity numbers changing from run to run (arm64 12-bit Bwdif: 5.72 on 11-17, 3.42 on 11-19) and Linux sometimes passing. A 720x486 job through Bwdif, Chroma Shift, Auto Chroma or LUTDeRainbow got a garbage bottom chroma row.

What else changes. Against the unpadded call (lastrow.py, compare()), every row agrees exactly at 96x64, at 8, 10 and 16 bits, flagged or not. At 96x66 the bottom 2–4 chroma rows differ, because the edge is now handled at the real field height:

C: run_within's depth-only conversion

depth.py: a 4:2:0 depth change (Bilinear down, Point back) gives the same md5 with _FieldBased 0, 2 or stripped, at 96x64 and 720x480, for 16→8, 10→8 and 16→10. An undithered depth change is per sample. So _change converts a copy without the flag and copies the clip's props back (the plugin still sees _FieldBased), and run_within pads only for a subsampling change. Output changes only for field-flagged 720x486 4:2:0 above DeScratch's, Dedot's or LUTDeCrawl's depth, where the plugin now sees the real 486 rows, as it does at its native depth.

D: Bifrost

bifrost_luma.py on deps 1.18.0-rc2 (v4.0): Y is unchanged at 8, 10, 12 and 16 bits, at every subsampling, with interlaced both on and off. On the sweep fixture the new UntouchedPlanes([0]) check passes the four rows that failed before (98x64 422p10 TFF, 98x64 444p12 prog, 96x64 420p16 TFF, 96x66 420p12 prog). The synthetic picture never triggers Bifrost, so luma being exact comes from the fixture rows, not from that script.
