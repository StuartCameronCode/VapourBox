pipe_source dropped a frame a late output frame still needed

Task #120, 2026-11-26. Measured on an Apple Silicon Mac (M1), macos-arm64 deps 1.16.0, the bundle's vspipe (R78), and on GitHub's Windows runners with deps 1.18.0-rc3 (repro runs 45799894961 and 45799902759). The failures are nightly run 45667413686 (main bd1ed4b2, deps 1.18.0-rc3), jobs 139393212274 (windows-x64-v2, heavy) and 139393212389 (windows-x64-v2, sweep).

Outcome

  • Symptom 1: stabilize: Stab runs end-to-end failed once, on a Zen 5 Windows runner (AMD Family 26), with pipe_source: frame 0 was asked for after it left the cache (read up to frame 70, oldest frame not yet served 71, window 42, cap 689 frames). It passed on every other run, platform and tier with the same bundle.
  • Cause: Stab's declared reach (n−8…n+9) is right. pipe_source kept a served frame for a window of 42 counted back from _low, the oldest source frame not yet served (task #58). A served frame can be asked for again: every output within the radius wants it, through several nodes (two SCDetects, Interleave, the 16-bit copy), and VapourSynth's cache drops it between their requests. vspipe R78 asks for the next output frame whenever any frame completes, with no limit on how far ahead it runs (frameDoneCallback), so while one output frame runs late the reader reads on. When that output's own requests arrive, the frame can be more than the window behind _low.
  • Not MVTools: v24's DepanEstimateStage1-3 and DepanCompensate are fmParallel and issue every request in arInitial. Not task #116 (the missing FFTW DLL): the failing job computed Depan for 70 frames, and Stab passed on the v3 tier that night with the same bundle.
  • Fix: the template's last node is pipe_source.track_output(clip): a FrameEval notes when vspipe requests output frame m (before any of m's requests reach the pipe), a ModifyFrame when it completes. The reader keeps every frame less than the window behind _low as it was when the oldest output frame still in flight was requested. Without a tracker the rule is the old one. The memory cap is unchanged: a stalled output now has the cap (689 frames in the failing job), not the 42-frame window, before a frame it needs is given up, and asking for a frame given up still raises.
  • Symptom 2, the format sweep's stabilize/pitchMode=auto row at 720x480 yuv444p16le hanging past 360 s, is a different fault, reproduced on the Windows runners with stacks: vspipe finishes and then never completes its own exit (ExitProcess → NtTerminateProcess), so its stdout pipe stays open and ffmpeg and the worker wait forever. It happened with the old reader and the new one alike. Its cause is outside this change and is task #122.

Why the window from the oldest output in flight is enough

vspipe requests output frames in order. When it requests output m, only outputs below m have asked for anything, so _low ≤ src(m−1) + R + 1. Output m reaches back to src(m) − R, which is at least _low − (2R + 1); the window is max(40, 2·total_radius + 24). No map from output to source frames is needed, so it holds through rate changes, decimation, VFR timelines and preview padding.

Measured caveat: VapourSynth runs the requests' first steps on its thread pool, so the tracker's FrameEval sees them out of order: 428 times in 360 loaded runs, up to 14 outputs late. Taking _low at that moment put an output's snapshot up to 18 frames past its own frame (the window allows 33 at R = 9). So an output reaching the tracker late takes the lowest snapshot of the outputs already in flight instead; with that, every snapshot was at most 9 past its frame, inside the in-order bound of R + 1 = 10.

The full hang report of the first "before" hang is data/windows-hang-stacks.txt; every run's preview times are in data/windows-*-summary.txt.

vspipe has done its work and is exiting, but its termination never completes, so its stdout pipe is never closed. ffmpeg (-vframes 1) cannot finish without that EOF, and the worker waits on both. The old reader hung as often as the new one, so it is not this change. The cause is outside VapourBox's code (a terminated thread held in the kernel, or something in what a pitch-auto graph leaves to tear down); task #122 takes it up, with a worker-side guard as a candidate: kill a vspipe that has reported its last frame but not exited.
