small_clip.mp4 counts 3154 instead of 3151 now and then: the tail probe comes back empty

Task #83, 2026-11-21. Measured on GitHub's windows-latest, ubuntu-24.04 and macos-15 runners with deps 1.18.0 (FFmpeg 9.0 series: BtbN on Windows/Linux, martin-riedl on macOS), through the temporary workflow .github/workflows/repro-probe-source.yml (runs 44755463322 and 44763118568). Locally: macOS arm64 with Homebrew's FFmpeg 9.0.2.

Outcome

  • Cause: the tail probe task #54 added (ffprobe -show_entries packet=pts_time,flags -read_intervals 102.119%, the last 3 s of the video packets) sometimes exits 0 with no output at all. On Windows this happened in 50 of 1,800 raw ffprobe runs (2.8%), on macOS in 5 of 1,800, and on Linux in none of 1,800. The worker read an empty listing as "no last kept picture" and counted nb_frames (3154, the edit list's three discarded pre-roll pictures included), with no retry and nothing logged. In 1,800 worker runs per platform, the old code would have counted 3154 in 41 on Windows (2.3%), 5 on macOS and none on Linux.
  • Where it goes wrong: inside ffprobe's seek. A run that comes back empty logs, at -v debug, exactly what a good run logs, the read-interval seek included, except for its last line: it read 137,094 bytes instead of 333,702. All 19 empty Windows logs are identical. Nothing is reported, so no exit status or stderr can tell it apart. The same command without the seek (every packet listed) was never empty, in 900 runs.
  • Fix (worker): the count-deciding probes now run through ffprobe_run. It keeps stderr, names the exit status (for example 0xC0000142, STATUS_DLL_INIT_FAILED), treats an empty stdout as a failure, retries up to 3 times (100 ms, 300 ms) and logs every failed attempt on --probe-source's stderr. A tail window that still fails, or keeps no picture, falls back to listing every video packet, with no seek (mov_last_kept). If an MP4/MOV's head probe or that listing still fails, --probe-source returns an error. It never returns the stored count.
  • Measured with the fix: 2,700 of 2,700 runs on each platform counted 3151. Every empty window on Windows was answered by its first retry, except one, which took the second. 30 runs of the push gate's two probing test binaries passed on every platform, in both rounds.

The CI failure

Run 44518323107, attempt 1, Windows job 135540066866 (PR #229, which does not touch this code). It failed continuity_integration_test.rs:124, a_deferred_scan_completes_to_the_same_model, with "small_clip.mp4: nothing to defer". Attempt 2 passed.

Correction to the task's description: for an MP4 the test never runs --complete-source. It compares two --probe-source runs, with and without --defer-scan. The flag changes nothing for an MP4 (continuity_deferred requires a TS/PS), so this was two runs of the same probe giving different answers.

The two models from the log differ only in video.frameCount: 3151 in one, 3154 in the other. Both have sourceGrid {2997/100, origin 0} and storedFrames 3154. Because the grid is present, the head probe (VIDEO_START_PROBE_ARGS) answered, and its first three packets are flagged D, so discards were seen. A count of 3154 with discards seen can only come from the tail closure returning no picture. That points at the tail probe, which the repro confirmed.

What the hypotheses predicted

  • H1, processes failing to start or initialise in bursts (e.g. 0xC0000142): refuted. No run exited non-zero. Serial runs failed as often as parallel ones on Windows (8 and 16 of 300), and 16 or 32 at once failed no more than 8 at once.
  • H2, ffprobe exits 0 with no output after the -read_intervals seek: confirmed. This is the one path the old code never retried.
  • H3, a sharing violation or scanner holding the file: refuted. Stderr was always empty, and the whole-stream listing reads the same file without ever failing.

Inside the empty run

Here are data/windows-tail-probe-normal.log and data/windows-tail-probe-empty.log, with pointers replaced by P. They agree line for line, edit-list processing included ("drop a frame at curr_cts: 0/100/200"), as do Processing read interval id:0 start:102.119, Seeking to read interval start point 102.119 and the decoder's SPS/PPS after the seek. Only the last line differs:

normal: [AVIOContext @ P] Statistics: 333702 bytes read, 3 seeks
empty:  [AVIOContext @ P] Statistics: 137094 bytes read, 3 seeks

So the seek succeeds and the reads that follow find no video packet to list. All 19 empty logs are identical. 1,500 runs of Homebrew's 9.0.2 on an M1 Pro were all good, so the fault varies with the build or the machine, which points at something like an uninitialised value in the MOV demuxer's seek. It was not chased into FFmpeg's source: the worker's fix does not depend on the cause, and the whole-stream listing avoids the seek altogether.

The fix

ProbeBeforeNow
Stream probe (-show_streams -show_format)one run, stderr discarded3 attempts, logged. Still an error when every attempt fails
Video-start (head) probeone run, failure → no grid, no discards3 attempts. An answer with no packets counts as a failure. For an MP4/MOV with nb_frames, failing every attempt is an error: it is the probe that sees the edit list
Tail window (MP4/MOV)one run, empty → nb_frames; a run that failed outright was tried once more3 attempts; then, if it failed or kept no picture, every packet listed (3 attempts); then an error
Tail window (Matroska)one run, failure → the duration's count3 attempts, then the duration's count as before
Untimed last picture (TS/PS)one run3 attempts, then as before (it can only raise the count)

The error reads "could not count the frames of <file>: its edit list discards pictures, and ffprobe's packet listing failed (<reason>)". A timeline 3 frames longer than the decode is worse than a failed analysis: the last trim asks for a frame past the end. For the CLI this was decided in the plan. The app currently drops a --probe-source error without showing it, which is filed as task #85.

With three empty windows needed before the listing runs, and Windows' measured rate of about 2.8% per run, the listing is reached about once in 45,000 probes, if failures are independent. The listing was never empty in 900 runs. Neither number proves the failure rate is zero.

Tests

  • ffprobe_run unit tests cover: retry stops at the first answer and logs each failure, gives up after 3 attempts with the last reason, names a Windows status, and keeps the end of stderr.
  • source_model unit tests drive the chain with a scripted ffprobe: a failure then an answer is retried and logged, an empty or discard-only window falls back to the whole listing, a chain that fails throughout is an error and never the stored count, the window's arguments, and a head answer must list packets.
  • worker/tests/source_model_integration_test.rs (push gate) runs --probe-source 24 times, 8 at once, on small_clip.mp4 (3151) and edit_list_bframes.mp4 (128). It prints any retried probe's stderr.
  • continuity_integration_test.rs now puts both runs' stderr in its "nothing to defer" message, so another flake says which probe failed and why.

Scripts

  • scripts/probe_loop.sh <worker> <file> <runs> <parallel> <out> tallies frameCount and the worker's "failed (attempt" lines.
  • scripts/ffprobe_tail_loop.sh <ffprobe> <file> <runs> <parallel> <out> [interval|none] runs the raw probe and tallies exit status and line count. With LOGLEVEL=debug it keeps each empty run's log.
  • scripts/cargo_test_loop.sh <runs> <out>, run from worker/, runs the push gate's two probing test binaries repeatedly.

All three run under Git Bash on Windows. .github/workflows/repro-probe-source.yml was removed before merge; to re-run, restore it from this task's branch history.

Not tested, and limits

  • One file (small_clip.mp4). Other MP4/MOV files were not looped, and neither was the TS/PS untimed-tail probe, which also seeks with -read_intervals and now has the same retry.
  • Hosted runners only, with one FFmpeg build per platform. Whether a user's machine sees the empty seek more or less often is unknown.
  • FFmpeg's cause was not found or reported upstream.
  • The Windows-only flakes in memory ("preview exited with 1", the rapid-seek stray process) are not explained by this: H1 was refuted here, so nothing links them.
