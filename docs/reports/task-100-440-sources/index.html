4:4:0 sources are decoded as 4:4:4, not 4:2:2

Task #100, 2026-11-22. macOS arm64 (M1 Pro), FFmpeg 9.0.2 (martin-riedl build, deps 1.17.0-rc1). Synthetic FFV1 fixtures made with the bundled ffmpeg. No screenshots: the pictures are checked by their samples, which the tables give.

Outcome

  • The fault: pixel_format.rs::classify put the subsampling code 440 in the 4:2:2 class, with the comment "4:4:0 is a superset horizontally and equal vertically". That is backwards. 4:4:0 has full horizontal chroma and half vertical; 4:2:2 has half horizontal and full vertical. So the decoder ffmpeg (-pix_fmt yuv422p…) halved a 4:4:0 source's horizontal chroma before VapourSynth saw it, against the module's own rule (never less chroma or depth than the source). yuvj440p is what some JPEG/MJPEG cameras record.
  • Fix: 440 is in the 4:4:4 class. 4:1:0 (quarter horizontal, half vertical) really fits in 4:2:2 and stays there. The app's twin, pixelFormatChromaLayout, moves with it, so the ProRes, v210, AV1 and hardware-encoder warnings describe what the worker does.
  • Guard: pipe_format_never_has_less_chroma_on_either_axis checks every planar YUV code (410, 411, 420, 422, 440, 444) × prefix × depth on both axes, so a class judged on one axis fails a test.
  • Output change: under Color Format "Match source", a 4:4:0 source now comes out 4:4:4 at its depth (it was 4:2:2). See below.

A. What the pipe delivers

A 128x96 testsrc2 frame stored as 4:4:0, decoded the way the worker's decoder does it (-pix_fmt <pipe>, ffmpeg's default scaler), read back as 4:4:4, and compared with the source rendered at 4:4:4 by the same scaler in one step, which is what a 4:4:4 pipe delivers. Chroma only; luma was identical in every row. 8-bit levels.

Correction. The planning stage listed a "testsrc2 yuvj440p" row equal to the limited-range one (1.78 / 21). That fixture was not full range: FFV1 has no yuvj formats, and ffmpeg stored -pix_fmt yuvj440p as limited-range yuv440p. The full-range row above is made with scale=out_range=pc and tagged pc. Only the MJPEG decoder reports the name yuvj440p, and ffmpeg's MJPEG encoder cannot write 4:4:0, so no fixture here carries that name; the unit tests cover it (it classifies exactly as yuv440p).

Column contrast is the mean |U(x) − U(x+1)| over the column region of frame 2, in 8-bit levels. "Right hue" counts preview pixels in that region where an odd column is red and an even one blue by more than 64 levels. The preview matched the encode (mean difference 0.000, read as the preview converts, previewFrameRgb24) in every row, before and after: both sides lost the columns together, which is why the comparison with an independent decode of the source is the one that matters.

The 127x95 row is task #97's fault reached through this one: an odd-width 4:4:0 source was off the grid only because of the 4:2:2 pipe. A 4:4:4 pipe has no grid to be off, so it now runs with or without #97.

What changes for existing jobs

  • Color Format "Match source" (the default): a 4:4:0 source comes out 4:4:4 at its own depth (yuv440p → yuv444p, yuv440p10le → yuv444p10le), where it was 4:2:2. With x264 that is High 4:4:4 Predictive instead of High 4:2:2; neither plays widely, and choosing 4:2:0 is still how to get a compatible file.
  • Any other Color Format, and AV1: the script converts from the true 4:4:4 chroma instead of from a 4:2:2 copy that had already lost half of it. Equal or better.
  • ProRes 422 / v210 / HuffYUV: still 4:2:2, resampled from the true chroma. Their warnings in the app (and HuffYUV's format note in the job log) now say the source's chroma is reduced, which has always been true of 4:4:0 → 4:2:2. ProRes 4444 no longer says it pads the source.
  • Hardware encoders (NVENC, QSV): handed 4:4:4 under "Match source", which the worker already converts to 4:2:0 for them (forced_pix_fmt); the warning names 4:4:4.
  • Cost: the pipe and every pass carry three full planes instead of two, about 1.5× the bytes, as for any 4:4:4 source.
  • Nothing changes for any other source format: every other code keeps its class.

Not tested

  • A real camera file: only synthetic fixtures. A real MJPEG 4:4:0 file is decoded by the same decoder path; ffmpeg's MJPEG encoder can't write 4:4:0, so none could be made here.
  • yuv440p12le end to end (the unit tests cover its class), and every pass on a 4:4:0 source: the passes see a 4:4:4 clip, which the format sweep already covers at every depth.
  • Other platforms: the decision is pure Rust and the conversion ffmpeg's, the same series everywhere; only macOS arm64 was run.

Decisions

  • 4:4:4, not a new 4:4:0 pipe format: VapourSynth has 4:4:0, but vspipe cannot name it in the Y4M header the encoder reads (the template already avoids it after a quarter turn of 4:2:2 for that reason), and no pass's plugins were probed at it. 4:4:4 is the smallest format already in _FORMAT_MAP and the format sweep that holds it.
  • 4:1:0 stays 4:2:2: it has at most 4:2:2's chroma on each axis.

Reproduce

python3 -I scripts/measure.py <bundle>/ffmpeg/ffmpeg          # tables A-C
cd app && flutter test --tags heavy test/integration_source_formats_test.dart --plain-name '4:4:0'
