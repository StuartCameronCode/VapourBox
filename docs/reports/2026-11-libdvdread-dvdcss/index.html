macOS arm64: libdvdread linked Homebrew's libdvdcss by absolute path

Task #36 · 2026-11-15 · deps 1.16.0 → 1.17.0 · measured on an Apple Silicon Mac (macOS 27.2, Homebrew libdvdcss 1.6.0)

Outcome: fixed in the build scripts. The deps 1.16.0 macOS arm64 bundle's lib/libdvdread.dylib was Homebrew's bottle, which carries LC_LOAD_DYLIB /opt/homebrew/opt/libdvdcss/lib/libdvdcss.2.dylib. On a Mac without Homebrew libdvdcss dyld refuses to load it, so DVD import failed. libdvdread is now built from source on both macOS architectures, without linking libdvdcss, with a small patch so that a user-installed libdvdcss is still found in /opt/homebrew/lib. A new packaging check (Scripts/check-macho-refs.py) fails any macOS bundle with a dependency or rpath outside itself; Scripts/check-elf-refs.py does the same for Linux.

1. Which bundles were affected

libdvdread read out of every published deps 1.16.0 zip (scripts/scan-published.sh):

This agrees with CI: on PR #186 (run 43661286187, before its test learned to skip) the arm64 job failed with Library not loaded: /opt/homebrew/opt/libdvdcss/lib/libdvdcss.2.dylib and the Windows, macOS x64 and Linux jobs extracted the fixture.

Why the guard missed it. The end-of-build check in download-deps-macos.sh skipped libdvdcss* on purpose, with a comment saying libdvdread "weak-links" it. The command is LC_LOAD_DYLIB, not LC_LOAD_WEAK_DYLIB. The check also looked only at plugins/ and lib/.

2. A plain runtime-loading build would lose CSS on Apple Silicon

libdvdread 6.1.3 built without --with-libdvdcss calls dlopen("libdvdcss.2.dylib"). For a bare name dyld searches its fallback path, /usr/local/lib:/usr/lib, which covers Intel Homebrew but not Apple Silicon Homebrew (/opt/homebrew/lib) or MacPorts (/opt/local/lib). The README tells macOS users to brew install libdvdcss, which on arm64 worked only through the hard link. scripts/probe.sh builds both variants and runs scripts/dlopen-harness.c under DYLD_PRINT_LIBRARIES=1 against Tests/TestResources/dvd_titles:

Alternatives rejected

  • Preload libdvdcss in the worker. With libdvdcss already loaded, dlopen("libdvdcss.2.dylib", RTLD_NOLOAD) still returns NULL (the harness's last line in every run above): dyld does not match a bare name against an image already in the process, so libdvdread's own call would still fail.
  • Set DYLD_FALLBACK_LIBRARY_PATH. Read only at process launch, so every spawner of the worker (app, tests, anything else) would need it, and it changes library search for everything in the process.
  • Bundle libdvdcss. Deliberately not done (NOTICES, README's legal note).
  • Homebrew's libdvdread 7.x. Built --with-libdvdcss; and 6.1.3 matches Windows (SMP) and the x64 build. The worker uses only the stable DVDOpen family.

3. The patch

Scripts/patches/libdvdread-6.1.3-macos-dvdcss-paths.patch (macOS only, in src/dvd_input.c): when the bare-name dlopen fails, try /opt/homebrew/lib/, /usr/local/lib/ and /opt/local/lib/ + libdvdcss.2.dylib. These are dlopen strings, not load commands, so the library depends on nothing outside the bundle; the build fails if the patch stops applying. libdvdread is GPL-2.0-or-later; NOTICES names the patch.

4. The rest of the bundle

Scripts/check-macho-refs.py run over the local 1.16.0 arm64 tree (2,605 files, 80 Mach-O):

  • One external dependency: libdvdread's libdvdcss. python's libpython3.12.dylib has an absolute /install/lib install id, which is its own LC_ID_DYLIB, not a dependency, and nothing links it by that path.
  • 13 absolute LC_RPATHs into the build machines: /opt/homebrew/Cellar/zimg/3.0.6/lib (libvapoursynth ×2, vapoursynth.abi3.so), /opt/homebrew/Cellar/fftw/3.3.11/lib (bm3d, dctfilter, mvtools), /opt/homebrew/opt/gcc/… (libfftw3f, libfftw3f_threads, ×3 each) and /nix/store/…-boost-1.89.0/lib/ (libboost_charconv). No file has an @rpath/ dependency, so they are inert today, but one would start resolving there the moment such a dependency appeared. download-deps-macos.sh now deletes them and re-signs (--strip-absolute-rpaths).

After replacing libdvdread with the patched build and stripping the rpaths, the check passes, and the push gate's VapourSynth plugin tests (every required namespace loads, fmtconv/Bob pixel checks) and dvd_extract_integration_test pass against that tree.

Scripts/check-elf-refs.py over the published linux-x64 bundle: 92 ELF files, none with a NEEDED path or an RPATH/RUNPATH outside $ORIGIN (python links $ORIGIN/../lib/libpython3.12.so.1.0, which is allowed). Windows DLL imports are leaf names, so there is no equivalent to check.

5. What was not tested

  • A Mac with no libdvdcss at all. This machine has Homebrew's; hiding it was not done. The fixed library's only dependency is libSystem, and the CI arm64 runner (no Homebrew libdvdcss) runs dvd_extract_integration_test, which now fails rather than skips when libdvdread is missing or will not load.
  • Decrypting a CSS disc. No encrypted disc is at hand and the fixture is unencrypted; the evidence that CSS still works is that libdvdcss is loaded (above).
  • MacPorts and Intel /usr/local paths: covered by the patch's list, not run.
  • The CI-built 1.17.0 bundles: built and checked by the build-deps-macos.yml run that produces them.
