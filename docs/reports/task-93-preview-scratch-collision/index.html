Concurrent previews of one job shared their script and frames

Task #93, 2026-11-21. Measured on an Apple Silicon Mac (M1 Pro), macos-arm64 deps 1.17.0-rc1, debug worker. "Before" is the worker at bbf1927c; "after" is this change. The x86 failures are nightly run 44767156916 (main 9190d08d, deps 1.18.0-rc2) and 44562921675 (deps 1.18.0-rc1); they were not re-run here.

Outcome

  • Symptom: the heavy test "IVTC preview exits cleanly, run after run" failed 3–4 of its 36 previews on windows-x64, windows-x64-v2 and macos-x64-v2 with The VapourSynth script failed: see the traceback below | (vspipe exited with exit code 1), and no traceback anywhere in the log.
  • Cause: the test runs three previews at a time of one job (one job.id), and the worker named every file a preview writes by the job id alone: $TMP/<id>_preview.vpy, $TMP/vapourbox_preview_<id>/frames.raw, $TMP/<id>_preview_pitch_factors.txt. The harness's config file was vb_pv_<id>.json too. Each preview writes its script, decodes its frames, runs vspipe and deletes both. Running together, previews deleted, rewrote and replaced each other's files. It is not in the IVTC graph, _preview_decimate_pick or pipe_source.
  • Why no traceback: a script vspipe cannot open is not a Python error. vsscript prints Script evaluation failed: / File reading exception: / [Errno 2] No such file or directory: '…'. vspipe_failure_message found no Python exception: and no Traceback, so it said "see the traceback below" and dropped the reason. Checked by running the bundle's vspipe on a missing file.
  • Worse than the failures: most previews that exited 0 showed another preview's picture (they read its frames.raw or its script). The test checked only the exit status, so this was never seen.
  • The app was never affected: PreviewGenerator gives every preview its own Uuid().v4(); so does the format sweep. Only this test reuses one job.
  • Fix: each preview writes into a directory of its own (PreviewScratch: vapourbox_preview_<id>_<uuid>, removed on drop on every exit path; ScriptGenerator::with_scratch_dir for the script and pitch factors). The job error now carries vsscript's words for a non-Python evaluation error. Child stderr is read lossily, so a non-UTF-8 line no longer ends the read. The harness names its config file per call and prints the worker's whole error. The repeat test keeps one job on purpose and requires every concurrent preview to equal that frame previewed alone.

Measurements

scripts/race.sh: the test's ProRes 422 10-bit IVTC job, 36 previews a round at frames (i·7) mod 30, three at a time, each started after a random 0–0.4 s delay; optional busy-loop cores beside them. Every PNG is compared (md5) with the same frame previewed alone. "Shared" uses one job for all previews, as the test does; "unique" one job per frame. Raw output: data/.

Limits. The rates depend entirely on timing: the start delays make collisions far likelier than the test's simultaneous starts (an earlier run during planning, starting all three at once, failed 3 of 360 idle and 48 of 720 loaded, with 252 wrong of 338 that exited 0). CI's 3–4 of 36 is that test's own timing on slower x86 runners. It is not an x86 bug: the arm64 runners were lucky. Measured on arm64 only; the worker change has no platform branch.

The strengthened test catches it. Run against the old worker under load, the new repeat test failed with frame 0: not the picture it previews alone (MAD 8.027) and others (MAD 3–9); against this change it passes (32 s on the M1).

Decisions

  • Fixed in the worker, not only in the test. A job id names a job, not a process; a preview must not depend on its caller to be unique. The test keeps sharing one job so it guards this.
  • A uuid-named directory, not the tempfile crate. tempfile is only a dev-dependency; uuid already ships. create_dir (not _all) refuses a directory that already exists.
  • The encode's <id>.vpy and other id-keyed scratch (Descale detection, audio render, the progress file) are unchanged: each belongs to one run per job, and nothing runs two at once for one id.
  • No retries.

Not tested

  • x86 itself (Windows, Intel Mac): left to the nightly run after this change.
  • No screenshot: a wrong picture here is simply another, correct-looking frame of the clip; the MAD figures above are the evidence.
