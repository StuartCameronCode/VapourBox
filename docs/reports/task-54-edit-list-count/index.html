An MP4 edit list's discarded packets are not frames

Task #54 (found in task #50). 2026-11-17. macOS arm64 (M-series), FFmpeg 9.0.2 (deps 1.16.0 for the tables, 1.17.0-rc1 for the heavy tests: the same FFmpeg build), debug worker.

The fault

The source model's frame count took nb_frames whenever the container stores it. In an MP4/MOV that is the sample table's count. An edit list that starts after the media's first sample keeps the samples from the keyframe before it, so the decoder can reach the first shown picture, and the mov demuxer marks them discard (D in ffprobe's packet=flags). No decode outputs them, but nb_frames counts them. Tests/TestResources/small_clip.mp4 stores 3154 and decodes 3151.

The app sends the model's count as totalFrames. So its timeline offered frames 3151–3153, which do not exist, and an untrimmed encode asked pipe_source for 3154 frames. pipe_source answers a frame past the end of the decode with the last one it read, so the output ended on three copies of the last picture. Pre-existing: the app counted this way before task #50.

1. "Packets not discarded" is not the count either

The task proposed counting the video packets not marked discard. A second fixture shows why that is wrong. edit_list_bframes.mp4 (Tests/TestResources/generate_edit_list_test.sh) is an x264 clip with 3 B-frames, stream-copied with -ss 2.3 -t 4.1. The cut's edit list discards 21 pre-roll packets, and the copy's -t also drops the last B pictures, so the kept pictures' timestamps have holes (4.104 → 4.238 s). The source grid (issue #174) fills each hole by repeating the slot before it, as it does for an AVI's null frames.

So the count is the rule the model already used for Matroska: the last kept picture's slot on the grid, plus one (frame_count_from_last_picture). Since issue #174 the grid decode is what every decoder produces, so it is the one count that matches them.

2. What was built

  • VIDEO_START_PROBE_ARGS (the first 64 packets, already read) asks for flags; source_decode::discards_from_probe finds a D.
  • For an MP4/MOV with a stored count, the tail probe (probe_tail: the last 3 s of video packets, with flags) runs alongside the other probes. It returns the last kept picture and whether any packet there was discarded (a demuxer can keep B pictures past an edit's end). Matroska's existing last-picture probe now skips discarded packets too; Matroska never marks video packets discard.
  • frame_count rule 2a: with a stored count and any discard, the last kept picture's slot + 1. If there is no grid or no last picture, the stored count is used, as before.
  • A job without a count takes the model's (VideoJob::apply_source_model, over its trim). There are two exceptions (counts_by_decoding): a job with no model, and a raw MPEG-PS/TS whose timestamps reset, in a job the app did not prepare. That file's model counts its last segment (seek_reset_h264.ts: 150), while the decoder plays through the reset (300). Those two still use -count_frames. Audio Restoration's drift, which read the whole source with -count_frames on every trimmed job, takes the model's count the same way.

5. DVB-T to AVI: 126 or 128?

A heavy test encoded pal-dvbt-fieldcoded-25i.ts to AVI without a count and expected 126 frames, the -count_frames answer. Its grid decode is 128 slots holding 126 distinct pictures: two slots repeat the picture before them, where the field-coded stream leaves a gap (measured with framemd5: two duplicated hashes, one of them slots 125/126). An app job has always sent the model's 128, the timeline's length. A job without a count now encodes the same 128, and the test says so.

6. Tests

  • Rust unit tests: rule 2a on both fixtures' numbers (3151, 128); the fallbacks (no grid or last picture, the stored count; no discard, the tail never asked; VFR first); the tail parser (discards skipped, CRLF); discards_from_probe; apply_source_model's count over every trim shape; counts_by_decoding.
  • Heavy, integration_source_grid_test.dart: small_clip (frames 1, 1575, 3148, 3150) and edit_list_bframes (1, 60, 125, 127, two of them in holes). It checks that the app's count is the independent timestamp placement's slots, that the untrimmed encode is every slot, and that the preview, the app's Original and a trim are the right slot at each frame. A new group encodes interlaced_test.avi and edit_list_bframes with no count and expects every slot.
  • Heavy, integration_video_start_offset_test.dart: DVB-T to AVI is 128; small_clip copied into AVI stores 3151 and ends on the source's last four pictures, not repeats.
  • integration_v210_output_test.dart compared a countless job's output with the source's -count_frames (75). It now compares with the model's 79.

Decisions

  • Trigger on a discard, not on every MP4. Where the slot count and nb_frames differ without discards (timestamp holes in a plain MP4), the slot count would also be right. But that would change counts on files with no reported fault. Every source without discards keeps its count exactly as before.
  • Keep -count_frames for a raw reset TS/PS outside the app. Dropping it would halve such a CLI encode. Making the model count through a reset is a change to task #21's rules, not to this one's.
  • No schema bump. No field's meaning changed; storedFrames stays the container's raw count.

Not covered

  • A file whose discards are only in mid-file (a multi-entry edit list, as some editors write), none in the first 64 packets or the last 3 s, still counts nb_frames. Nothing cheap detects it, and no such file was at hand.
  • One platform. The change is ffprobe-output parsing with no platform branch.
  • The app was not driven by hand. The heavy test checks what its timeline uses: the model's count, and the preview and Original at the last frames.
  • Found while checking trims at the end, filed as task #59: in/out points become frames by round(pos × N), while the scrubber uses pos × (N − 1). An out point at the last frame therefore asks for one frame past the end.
