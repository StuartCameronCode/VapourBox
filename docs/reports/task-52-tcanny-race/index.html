TCanny's per-thread buffers race: its Gaussian blur, computed without it

2026-11-16 · task #52 (nightly failure, 2026-11-15) · deps 1.16.0 / 1.17.0-rc1 · measured on an Apple Silicon Mac (macOS arm64 bundle). The race is in TCanny's source, which every platform's build shares; the crash was seen on macOS x64.

Outcome: built. The nightly's MCDegrainSharp encode on macOS x64 died with libc++abi: terminating due to uncaught exception of type std::out_of_range: unordered_map::at: key not found, in tcannyGetFrame. TCanny r14 fills four std::unordered_maps keyed by thread id on each thread's first frame, with no lock, then reads them with .at(); two VapourSynth threads starting together can corrupt a map, and the out_of_range escapes (the filter only catches std::string), so vspipe aborts. The templates used TCanny only for its Gaussian blur (mode=-1), in MCDegrainSharp, mClean and TemporalDegrain2. worker/templates/gauss_blur.py now computes that blur with std.Convolution, which keeps no per-thread state: within 1 level of TCanny at 8/10/16-bit for every sigma a caller uses (most samples identical), untouched planes bit-exact, and faster than TCanny on arm64. test_250 keeps tcanny.TCanny out of the templates.

1. The race

From TCanny/TCanny.cpp at tag r14 (HomeOfVapourSynthEvolution/VapourSynth-TCanny). macOS x64 ships Stefan-Olt's r14 build and Windows upstream's r14 DLL; macOS arm64 and Linux build master, one commit past r14 (an alignof change), so every bundle has this code:

// tcannyGetFrame, arAllFramesReady — run concurrently (fmParallel)
if (!d->blur.count(threadId)) {
    ...
    d->blur.emplace(threadId, ...);       // no lock: a rehash here races
    d->gradient.emplace(threadId, ...);   // another thread's emplace / at()
    ...
}
} catch (const std::string& error) { ... }  // std::out_of_range is not caught
d->filter(src, dst, d, vsapi);             // filter_c: d->blur.at(threadId) ...

Only a thread's first frame inserts, so the window is the first few frames of each TCanny node, and it needs two threads to arrive together: a rare, timing-dependent abort, not reproducible on demand. It showed once in the nightly history fetched for this task (the 25 most recent nightly runs' failed jobs, 43 job logs): MCDegrainSharp's luma-only / chroma-only encode on macOS x64, 2026-11-15. The same unordered_map::at abort under QTGMC's KNLMeansCL (Linux x64, October) is a different plugin and is not addressed here.

Fixing the plugin was not chosen: Windows ships the upstream r14 DLL and has no from-source path, and a patched build would be a deps release. Not calling it fixes every platform with the current bundles.

2. The replacement

gaussian_blur(clip, sigma, planes) reproduces TCanny(clip, sigma=sigma, mode=-1, planes=planes): the same normalised weights exp(-k²/2σ²) over radius max(int(σ·3 + 0.5), 1); chroma's sigma divided by the subsampling in each direction (TCanny's default for one given sigma); separable, vertical then horizontal, in 32-bit float, rounded once (an Expr of x to float and back, which copies values raw). A float clip is left unclamped, as TCanny leaves mode -1's.

Correction during the work: the edges

The first version convolved each plane directly and differed from TCanny by up to 7 levels at sigma 0.849 and 15 at sigma 2 (8-bit), all within the radius of the frame's edge (mean 0.011 / 0.075). std.Convolution mirrors with the edge sample; TCanny mirrors without it:

source               [1, 11, 21, 31, 41, 51, 61, 71]
Convolution, x-2     [11, 1, 1, 11, 21, 31, 41, 51]   x=-1 reads x=0, x=-2 reads x=1
Convolution, x+2     [21, 31, 41, 51, 61, 71, 71, 61] x=8 reads x=7
TCanny               x=-i reads x=i, x=w-1+i reads x=w-1-i

convolution_edges.py: the Convolution rows are the ramp read two samples to each side.

So each plane is now padded TCanny's way (flipped strips from one sample in) before each pass, and the padding is cropped after.

Speed

On arm64 the Expr steps run on akarin's JIT (hybrid_mv._expr); macOS x64 has no akarin and uses VapourSynth's own x86 Expr JIT. x86 speed was not measured; with std.Expr instead of akarin on arm64 (the scalar interpreter) it was still 264 / 372 fps. Either way the blur is a small part of a motion-compensated denoiser's time.

Decisions

  • Replace the calls, not the plugin. TCanny stays in the bundle (it is still a required namespace and credited); nothing VapourBox generates calls it.
  • Match TCanny rather than pick a new blur (box blurs, as mClean/TD2's no-TCanny fallbacks used): a saved MCDegrainSharp/TD2 setting keeps its picture.
  • A guard, not a probe. The race cannot be triggered on demand, so the test is static: test_250 fails on any tcanny.TCanny( call in worker/templates and on any in a generated MCDegrainSharp script.

Not tested

  • That the abort is gone: it was one failure in ~25 nightlies; the evidence is that the code that races is no longer called.
  • Other plugins with the same per-thread-map pattern (several HolyWu plugins use it); none has been seen to crash.
  • x86 speed; images other than the one frame.
