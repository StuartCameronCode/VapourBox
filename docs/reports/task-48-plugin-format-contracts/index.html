Plugin format limits, measured, and one helper for running a plugin outside them

2026-11-16 · task #48 (task #42's plan, R2b) · deps 1.17.0-rc1 bundle as installed · measured on an Apple Silicon Mac (macOS arm64 bundle). Other platforms' bundles are checked against the same table by the push gate's quick probe and the nightly full probe; a cell that differs there goes under that platform in the table.

Outcome: built. Every plugin call the script template makes is now run against the bundle at every format a pass can be handed ({4:2:0, 4:2:2, 4:4:4} × {8, 10, 12, 16} bits × {progressive, BFF, TFF}), plus a frame-size axis up to 1080 lines, and the result is committed as Tests/TestResources/plugin_format_table.json. The five plugins that refuse a depth (DeScratch, DeDot, Bifrost: 8-bit only; havsfunc's LUTDeCrawl and LUTDeRainbow: 8–10 bit) have a Contract in worker/templates/plugin_formats.py and are called through run_within(), which replaces their five hand-written guards and the template's _low_depth_change. The four 4:1:1 guards (Frame Rate, VFR placement, Cnr4, RemoveDirt) became one conversion at the top of the script.

The migration changes no output. Every migrated pass was encoded losslessly before and after the change, on every reachable format, progressive and TFF, plus 4:1:1: all identical, except RemoveDirt, whose output differs from run to run with either template (section 4). The probe also found refusals no pass handles yet: 720x486 4:2:0 in 11 calls, and MCTemporalDenoise at a width of 2 mod 4. They are listed in plugin_formats.KNOWN and filed as tasks #57 and #56.

1. Why

Each limited plugin had its own guard: convert down, run, convert back. They were written one at a time and went wrong the same ways: the whole low-depth result up-converted, quantising every sample (DeScratch, task #34; then the four Chroma Fixes filters, task #37); a field-flagged 4:2:0 frame the plugin's internal resize refuses (DeScratch, #29); depth or size limits found by a user's job (#23, #31, #35). The limits themselves lived in comments.

2. What was built

Scripts/probe-plugin-formats.py

Lists every pass-level plugin call in the template and its modules with the template's own arguments (schema defaults where it substitutes a value), and runs each on ten frames of the interlaced capture converted to every cell. A cell is ok when a frame of the output can be requested; otherwise it records the first line of the error, or the exit status if the process crashed (each call runs in its own process, and a crash re-runs the rest). The push-gate test fails on a template call the probe neither lists nor explains in NOT_PROBED (OpenCL, Vulkan, plugins bundled nowhere).

Documentation rows outside the reachable set are measured too: 4:1:1 8-bit (pipe_source reads it, the template now converts it before any pass) and 9 / 14-bit (pixel_format.rs decodes them as 10 / 16, tasks #31 and #23).

plugin_formats.run_within(clip, key, fn, label=…)

contract = CONTRACTS[key]                      # depths, subsampling, min size
target = work_format(clip.format, contract)    # smallest accepted depth ≥ the clip's (else the largest),
                                               # the nearest subsampling that loses no chroma
if target == clip.format: return fn(clip)      # accepted: no node added
work = convert(clip, target)                   # zimg, _FieldBased kept (per-field chroma)
return clip + back(fn(work)) - back(work)      # only fn's change, at full depth

A depth change alone uses Bilinear down and Point back, exactly the old helper; a subsampling change uses Bicubic both ways. A frame below the contract's minimum raises naming the pass, the plugin and both sizes. fn must keep the frame count, size and format, or it raises (delta_only=False is the escape hatch for an fn that retimes). No contract needs a subsampling or size limit today; both are there because the probe can find them.

Guards that keep it the only way

  • test_252 (Rust): every call of a contracted plugin in worker/templates/ must sit in a function that is handed to run_within with that plugin's key; the one measure-only site (VFM, which decides on an 8-bit copy and takes pixels from clip2) is listed by its line; the old helper must not return; the 4:1:1 rule must be the only one and come before the VFR placement and every pass. A bare core.dedot.Dedot(clip) planted in deflicker.py fails it, naming the line.
  • plugin_format_contracts_test.dart (push gate): the quick probe (every limited call at every reachable format, every other call at one format per depth) against the table; each contract against its measured depths and subsampling; any other refusal in the reachable set must be explained in plugin_formats.HANDLED; and run_within itself on a fixture with real low bits.
  • plugin_format_probe_test.dart (heavy, nightly): the full probe, with the size axis.

What the refusals mean for a job

  • VFM differs by platform. The macOS arm64 and Windows vivtc builds refuse anything but 8-bit; the Linux x64 and macOS x64 builds accept 10/12/16-bit (found by the first CI run of this change; recorded under platforms in the table). The template gives VFM an 8-bit copy either way.
  • Depth (DeScratch, DeDot, Bifrost, VFM: 8-bit; LUTDeCrawl, LUTDeRainbow: 8–10): the five contracts, and VFM's 8-bit decision copy. These are the only refusals inside the reachable formats at 160×120.
  • DeScratch on field-flagged 4:2:0, the plugin alone: the 4:2:2 carrier (#29) avoids it; pass.DeScratch, the pass as the template runs it, accepts every 8-bit cell at every size.
  • 720×486 4:2:0: 243 chroma rows, so a field has no whole chroma height. 11 calls refuse it field-flagged; QTGMC, Bifrost and MCTemporalDenoise refuse it progressive too. 486-line sources are normally 4:2:2 (D1, ProRes, v210), which every call accepts. Task #57.
  • MCTemporalDenoise at 718×480 (width 2 mod 4, 4:2:0 and 4:2:2): task #56 F1, found by the format sweep too.
  • Rows outside the reachable set: 4:1:1 is refused by every MVTools user, Cnr4, RemoveDirt, DeScratch and others, which is why the template converts it first; 9 and 14-bit by QTGMC and the CTMF users (tasks #23, #31).

Correction made before the table was committed: on the first full run two of the probe's own calls had the wrong arguments, so they read as broken on every format. SmoothLevels was called without the template's useDB=False (havsfunc's default needs an f3kdb namespace no bundle has), and Cnr4 with a radius of 0 and scalar sense/str, where the template passes per-plane lists. Both were re-measured with the template's arguments and accept every reachable format.

4. The migration changes no output

scripts/identity.py encodes each migrated pass alone, losslessly (FFV1, Color Format original), on 352×240 sources at every reachable format, progressive and TFF, and on 4:1:1 for the passes whose 4:1:1 guard went, with the worker reading the templates from before the change (97d6a45) and after it, and compares frame MD5s. A control encode with no pass flags a pass that changed nothing on that source.

5. Limits of this evidence

  • "Accepts" is not "reads correctly". A cell is ok when a frame can be requested. A plugin that accepts a format and misreads it (MVTools' Depan on 8-bit, task #32) or a guard that quantises (task #34) passes the probe; those are the format sweep's and the high-bit-depth parity tests' to catch.
  • One platform measured. The table is the macOS arm64 bundle's. The other bundles are held to it by CI; a real difference there belongs under platforms in the table, measured on that platform.
  • The template's arguments, not every argument. Each call runs with one set of values (the template's fixed ones and the schema defaults). A limit that depends on a value (DeScratch's Blur Radius, #35) is only seen at that value.
  • Ten frames of one capture. Enough for format and size refusals, which are raised when a filter is created or the first frame is requested; not a test of content-dependent failures.
