Linux deps: VapourSynth's zimg came from master at build time

2026-11-22 · task #103 (found by task #90) · measured in GitHub Actions on the linux-x64 (v3, v2) runners against build-deps-linux artifacts · every number below comes from scripts/ run against the run IDs given.

Outcome: fixed in the deps (1.18.0-rc3's Linux assets replaced). R78's subprojects/zimg.wrap says revision = HEAD, and the Linux build makes meson use it (it never passes PKG_CONFIG_PATH to meson setup, task #111). So every Linux build linked whatever zimg master was that day, statically, into libvapoursynth.so.4. Master moved to e2e43d09 ("Update graphengine") on 2026-11-21 01:32Z. Every rc3 Linux build after that aborted in VapourSynth's own resize (double free or corruption (!prev) at free() ← vszimg::real_get_frame), which meant 617 of 6861 sweep rows. The wrap is now pinned to 67e06032 (graphengine cb5b2ce1), which rc2's build had cloned. The rebuilt libvapoursynth.so.4 is byte-identical to rc2's, and every resize failure is gone.

Symptom

From task #90's runs of the rc3 candidate bundle (build-deps-linux 44931836464 from main 478a7397; ci-test 44940677617, nightly 44940674293). It reproduced on linux-x64 at both CPU tiers; no plugin is involved:

Where the zimg came from: a correction

The task, and its plan, blamed download-deps-linux.sh's git clone of zimg master, and the first fix pinned that clone. That build (B1) crashed exactly as before. The clone builds a standalone libzimg.so that nothing in the bundle loads (no binary names it). B1's libzimg.so was already byte-identical to rc2's. The VapourSynth build log shows where the real one comes from:

Run-time dependency zimg found: NO  (tried pkg-config and cmake)
Looking for a fallback subproject for the dependency zimg
Executing subproject zimg for machine: host

The script does set PKG_CONFIG_PATH for meson, but the line continuation before meson setup ends on a comment line. So the variables (and CC=clang-18) go to a bare env, and meson runs without them. Meson then falls back to R78's subprojects/zimg.wrap (revision = HEAD, depth = 1). Every Linux bundle since 0c805a7b was built that way, with gcc 13 and a static zimg from the day's master; task #111 owns the line. The second fix (B2) rewrites the wrap to ZIMG_COMMIT, refuses a wrap that no longer says HEAD, and checks both commits after setup.

Limits

  • The graphengine cause is inferred, not bisected (task #109).
  • linux-arm64 builds with the same pin (its log says VapourSynth links zimg 67e06032), but no CI runner tests that bundle.
  • macOS and Windows were never exposed: Windows uses the VapourSynth wheel's zimg; macOS builds against zimg releases (arm64 Homebrew's 3.0.6, x64 3.0.5 from source).
  • The pin keeps Linux on an unreleased zimg, because R78 needs ZIMG_API_VERSION 2.5. Moving to a release or a newer commit changes every resize on Linux and needs the same A/B.
