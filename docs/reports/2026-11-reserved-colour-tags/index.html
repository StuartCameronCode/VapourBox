Sources tagged with reserved colour primaries/transfer

2026-11-10 · reported on the videohelp forum (thread 419911, posts #123/#140/#150) with a ProRes capture · measured on an M1 Pro (macOS arm64) against the deps 1.16.0 bundle (FFmpeg 9.0.2)

Outcome. FFmpeg 9's scaler refuses to convert a frame tagged color_primaries=reserved / color_transfer=reserved, and fails the whole decode. That emptied the app's Original side ("No preview") and timeline and failed Detect borders, as reported. It also failed Descale's Detect, and the encode and preview of a ProRes 4444 with alpha, which nobody had reported. Every decode of the source now puts a setparams that sets only the invalid tags to unknown first in its one -vf. The fixed decodes are bit-identical to the same file untagged, and a source with usable tags decodes with exactly the arguments it always had. Built.

1. The source and the error

The clip is ProRes 422 (apcn), 720x486, yuv422p10le, BFF, 2997/100 fps, time base 1/11988, with pcm_s24le as stream 0 and video as stream 1. ffprobe reports color_space=unknown, color_primaries=reserved, color_transfer=reserved, color_range=tv. Any ffmpeg that converts its pixel format stops with:

[swscaler] Unsupported input (Operation not supported): fmt:yuv422p10le csp:unknown prim:reserved trc:reserved -> fmt:yuv422p …

Where reserved comes from

FFmpeg's ProRes decoder reads the header's colour fields as ISO 23091 codes, where 0 is reserved and "unspecified" is 2. Apple's ProRes spec uses 0 for "unknown". So a ProRes writer that marks colour as unknown the Apple way produces exactly these tags. FFmpeg's own prores_metadata bitstream filter does it too: its unknown constant writes code 0, and it refuses 2 and 3.

prores_metadata settingffprobe then reports
color_primaries=unknown:color_trc=unknownprim reserved, trc reserved (the reported clip's tags)
color_primaries=2 / =3refused ("not a valid value")
colorspace=0matrix gbr (on a YUV stream)

H.264 is not affected in the same way. Its decoder maps reserved codes to unknown itself: h264_metadata with primaries/transfer 0 or 3 probed as unknown and converted fine. The exception is matrix 15, ipt-c2 (Dolby Vision profile 5), which fails with "Impossible to convert". The fixture and the tests are therefore ProRes.

The encode is affected too, when its decoder converts

The worker's decoders write the pipe format chosen by decode_pixel_format. That is the source's own format, except when pipe_source cannot read it. ProRes 4444 with alpha decodes as yuva444p12le, which is converted to yuv444p12le. With reserved tags:

Encode-decoder conversion yuva444p12le → yuv444p12leResult
as beforeUnsupported input
with the neutraliserOK, bit-identical to the same file untagged

So the neutraliser belongs in all three source_decode builders (encode, preview, VFR timeline), and through them in every detector. It is not only for the detectors. The heavy test checks that the encode and preview of such a clip fail on the old worker and match an untagged twin on the new one.

Hence the rule:

  • Per tag, only where it is invalid, meaning not on the lists ColorMetadata::from_raw already uses. Untagged values (unknown, N/A, empty) need nothing. A blanket "set everything to unknown" would change Descale Detect's input on every tagged source, by up to 28 levels. With an unknown matrix, swscale's yuv→gray is an exact limited→full expansion; with bt709 it is something else.
  • gbr counts as valid. It is ffprobe's name for the RGB identity matrix, swscale handles it, and clearing it changed nothing. Leaving it alone keeps RGB sources' arguments unchanged.
  • ipt-c2 is cleared. swscale cannot convert it, and a Dolby Vision profile 5 picture is warned about, never blocked. With a PQ transfer, the HDR tone-map's own leading setparams overrides the matrix anyway.

4. Decisions

  • The raw tag stays in the job. The task first proposed making the app's colorTag() drop reserved. It doesn't. The decoder reads the tag from the stream whatever the job says, so the worker has to know the stream's tag is invalid in order to clear it, and the job is the only place it can learn that without its own ffprobe (which would cost every preview render). Clearing unconditionally whatever from_raw didn't keep was also rejected (section 3: it changes gray16le pixels when the job lacks a valid tag the file has). The encoder's tags still drop reserved, in from_raw.
  • One decision on each side, byte-identical. In the worker it is color_metadata::decode_tag_neutraliser (via VideoJob::decode_tag_neutraliser), placed by source_decode::decoder_filter ahead of the size guard. In the app it is ColorTags.decodeNeutraliser, placed by PreviewGenerator.beforeFrameArgs / thumbnailArgs ahead of scale and the HDR tone map. color_tags_test.dart parses the Rust lists from source and repeats the Rust case table.
  • Unchanged arguments for usable tags. No tag fix means the -vf is exactly the size guard, as before (asserted in source_decode.rs).

6. Tests

  • Fixtures (Tests/TestResources/generate_reserved_colour_tags_test.sh, stream copy only): reserved_colour_tags.mov is 15 frames of prores422_10bit_telecine.mov laid out like the reported clip (audio first, 1/11988 time base), 1.7 MB. reserved_colour_tags_4444a.mov is ProRes 4444 with alpha, 320x240, 10 frames, 0.55 MB. The script fails unless ffprobe reports reserved,reserved.
  • Heavy (integration_reserved_colour_tags_test.dart): every check compares against an untagged twin, which is the fixture stream-copied with bt709 primaries/transfer and the matrix left unknown. The checks: before frame and thumbnail fail without the fix (a guard that the fixture still reproduces the bug) and with it equal the twin's picture (MAD 0); each of the three detectors' reports equals the twin's; preview of both fixtures equals the twin's (MAD 0); the 4444a encode's frames equal the twin's (MD5).
    Run against the unfixed worker: --detect-crop, --detect-native, the preview and the encode tests fail, and --detect-noise-halo passes (no conversion, as predicted). With the fix, all 8 pass.
  • Unit: the case table and "never touches an accepted value" sweep on both sides; source_decode keeps one -vf with the fix first, and is unchanged without one; the Dart lists equal the Rust source's; argument placement with the HDR tone map and with DV5 (ipt-c2 + PQ).

7. Limits and what wasn't tested

  • Measured on macOS arm64 with FFmpeg 9.0.2 only. The scaler is shared code and FFmpeg is pinned to the 9.0 series everywhere, but the nightly heavy run is what checks Windows and Linux.
  • One real clip. Other writers that produce reserved (a MOV colr atom on another codec, for example) were not found or tested. The rule does not depend on the codec.
  • No app screenshot. Every result here is an exit code or a bit-exact comparison, and none is a visual judgement.
  • An invalid color_range (ffprobe reports only tv/pc/unknown) and tags that change mid-stream away from the probed ones are not handled.
  • Found in passing, not fixed here: --detect-native decodes gray16le through swscale, so Descale Detect's luma depends on the matrix tag (section 3: up to 28 levels between a bt709-tagged and an untagged copy of the same picture). --detect-noise-halo avoids this by decoding the source's own format and taking its luma plane. This fix does not make it worse: a valid tag is never cleared.
    Since fixed (2026-11-14), see section 8. The app's Detect jobs also turned out not to carry these tags at all, so in the app this report's fix never reached the three detectors; that is fixed in the same change.

8. Addendum (2026-11-14): Descale Detect's luma

--detect-native asked ffmpeg for gray16le, which swscale makes with the frame's matrix tag. It now decodes the pipe format (as --detect-noise-halo does) and the worker scales the Y plane itself (native_res::luma_gray16): limited range expanded to 0–65535, full range scaled. That is what an untagged source's gray16le already was, which is what Detect's thresholds were calibrated on.
