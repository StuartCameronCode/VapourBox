A source's subtitles let its sound run 38 s ahead of the picture

GitHub issue #266 (task #142), 2026-11-28. Measured on an Apple M1 with the bundled FFmpeg 9.0.2 (martin-riedl build, deps 1.17.0-rc1 macOS arm64). The behaviour is FFmpeg's scheduler and muxer, not macOS's, so every platform's bundle should behave the same; only macOS arm64 was measured.

Outcome

  • The report: on a Mac, an MKV made with Audio Passthrough had its sound "cut out completely in parts of the video". The sound was all there, and separating and re-muxing the streams with MKVToolNix fixed the file. So the packets and their times were right, and their placement in the file was wrong.
  • Cause: the encoder took the source's subtitles from the same input as its sound (-map 1:a? -map 1:s? -c:s copy). Between cues a sparse subtitle stream is the output stream furthest behind, and FFmpeg's scheduler (7.0+) only holds back inputs that don't feed that stream. So the source input was never held back, and its sound ran ahead of the picture vspipe was still making. Once the muxer's interleave queue spanned max_interleave_delta (10 s), FFmpeg wrote the sound out ahead. The MKV had long runs of sound followed by long runs of picture, up to ~38 s apart. A player that reads ahead a bounded amount runs out of sound while it reads through the picture. mkvmerge interleaves by timestamp, which is why a remux fixed it.
  • Fix (worker): subtitles come from an input of their own, a second -i of the source with input 1's own seek, added after every other input (pipeline_executor.rs, subtitle_mapping). The sound's input is then held to the picture's pace, and the subtitle input reads to its end at once (a few small packets). The source is probed first, so a source with no subtitle stream adds no input and is read once, as before. If the probe fails, Matroska keeps the old mapping from input 1 rather than lose the user's subtitles.
  • Through the worker (app/test/integration_subtitle_interleave_test.dart, a 40 s fixture with cues at 1 s and 35 s): an untrimmed encode stored the sound 22.66 s ahead in MKV and 23.3–23.4 s in MP4 before the fix, and 0.099 s in both after. The cues keep their times. Trimmed encodes were never affected (0.13 s before the fix): they end with -shortest, whose sync queue already holds the streams together.
  • Rejected: -max_interleave_delta 0 also gives a correct layout, but only by holding every sound packet in memory until the next cue arrives. The memory grows with the gap between cues and the sound's bitrate: 265 MB against 83 MB for a 7.1 PCM minute, and gigabytes for a lossless film soundtrack over a long gap with no cues.

The metric and its limits

scripts/lead.py sorts a file's packets by byte position and reports the largest amount by which an audio packet's DTS exceeds the DTS of the last video packet stored before it: how far the sound runs ahead of the picture in the order a player reads the file. Its limits:

  • It measures the layout, not playback. No player was tested here, and the reporter's player and source are unknown. A large lead explains a dropout in a player with a bounded read-ahead; how much lead a given player tolerates was not measured.
  • About 0.04–0.1 s is the floor: x264's own delay (lookahead and B-frames) holds the picture back that much in any encode.
  • The sources are synthetic (testsrc2, a sine tone, SRT cues). A real source would differ in its bitrates, not in the mechanism.

The fault needs no throttling: vspipe, or even decoding and re-encoding the picture as in the unthrottled row, is always slower than demuxing the file. Without subtitles the sound input is held to the picture's pace and the layout is right; the lead is roughly the gap to the next cue.

A trimmed encode was also checked in the first look (-ss 5 on both source inputs, -shortest): 0.04 s with the subtitles on their own input. That says nothing about the fix on its own: through the worker, a trimmed encode was already fine before it (next section).

A correction made during the work

The first version of the trimmed check expected the second cue at 30.0 s on the file's own timeline, and it read 30.968 s, on the old and the new worker alike. That isn't an error in either. A trimmed copy into MKV keeps the sound from the keyframe before the in-point, and the output stores the picture that much later (task #24, CLAUDE.md "Source Frame Size"). Here the picture starts at 0.968 s, so the check now measures the cue from the first picture.

The change

// before (one input, sound and subtitles)
-ss T -i source.mkv ... -map 1:a? -map 1:s? -c:s copy

// after (the source's subtitles from an input of their own, last)
-ss T -i source.mkv ... -ss T -i source.mkv -progress ... -map 1:a? -map N:s? -c:s copy
  • The decision is subtitle_mapping(form, embed_pending, codecs, input), a pure function that is unit-tested. It covers Matroska (copy), MP4/MOV (text codecs only, as mov_text, as before), AVI (none), no subtitle stream (no input), and a failed probe (Matroska's old 1:s?, MP4 none).
  • The subtitle input reuses the exact argument list input 1 got (source_audio_input_seek). An encoder priming changes that seek only for Convert into AVI, which takes no subtitles.
  • Chapters and global tags are unchanged: chapters still come from the first input that has them (input 1), and tags from the metadata file (input 2).

Decisions

  • Own input, not -max_interleave_delta 0: the same layout without buffering the sound (memory above).
  • Probe first, add the input only for a source with subtitles: otherwise every Matroska encode would read its source twice, which costs on a network share. The probe is the one the MP4 path already ran.
  • A failed probe keeps the old mapping for Matroska: a layout fault is better than silently dropping the user's subtitle tracks.
  • Not added to the output conformance matrix: the matrix's sources have no subtitles. A subtitle source class there would multiply its cases for one property this standalone test covers.

Not tested

  • Playback in any player (VLC, IINA, Infuse), and the reporter's own source.
  • Windows and Linux bundles (same FFmpeg 9.0 series, BtbN builds).
  • Image subtitles (PGS, VobSub) into Matroska through the worker; the mapping is the same N:s?.
  • The subtitle mux post-pass (an embedded transcript) is a stream copy of a finished file with no slow input, and was not re-measured.
