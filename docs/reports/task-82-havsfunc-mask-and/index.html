havsfunc's mask ANDs as one Expr: LUTDeCrawl and LUTDeRainbow at 10 bits

Task #82, 2026-11-20. Found by task #75. Measured on an Apple M1 (macOS arm64), deps 1.18.0-rc1 (VapourSynth R78, havsfunc r31, akarin present) with only havsfunc.py changed by patch 8. Not measured on x86.

Outcome

  • Cause: havsfunc r31's only core.std.Lut2 calls, eight of them, are LUTDeCrawl's and LUTDeRainbow's mask ANDs, Lut2(a, b, function=lambda x, y: x & y). At 10 bits VapourSynth fills a 220-entry table by calling the lambda once per entry, four tables per filter, at every script evaluation: 8.0 s per filter (0.5 s at 8 bits). The template's contract runs both at 8–10 bits, so 10-bit sources, and 12/16-bit ones converted to 10 by run_within, paid it on every preview and the encode.
  • Fix: havsfunc patch 8 in all three download-deps-* scripts routes the eight calls through _mask_and(a, b) = core.std.Expr([a, b], ['x y min']). Bit-identical in 36 of 36 cases, through akarin's Expr and through VapourSynth's own std.Expr; 0.0002 s per filter.
  • Preview through the worker (10-bit ProRes 4:2:2 fixture, Chroma Fixes with both filters on): 17.4–19.4 s → 0.33 s, the same PNG byte for byte.
  • Ships in deps 1.18.0-rc3. The patch fails the deps build if havsfunc's calls change, rather than doing nothing, because the exactness argument below is about these call sites only.

Why min is exact here

R78's std.Expr has no bitand (akarin's has, but the macOS x64 bundle has no akarin), so the AND has to be another operation. x & y == min(x, y) holds for every x whenever y is 0 or peak (all ones at the clip's depth): peak & x = x, 0 & x = 0. Checked exhaustively at 8 and 10 bits, both argument orders: true. It does not hold for two arbitrary values (5 & 3 = 1, min = 3), so it rests on how havsfunc builds the operands:

FilterCallOperands
LUTDeCrawldiffs_y = diffplus_y & diffminus_yboth Expr '… {peak} 0 ?': 0/peak
LUTDeCrawlymask & diffs_yBinarize (v0 = 0, v1 = peak) and the above
LUTDeCrawlcmask = Binarize(u) & Binarize(v)both 0/peak (then resize.Point, still 0/peak)
LUTDeCrawlthemask = ymask & cmaskboth 0/peak
LUTDeRainbowthemask = umask & vmaskboth Binarize
LUTDeRainbowumask & average_y, vmask & average_y, themask & average_yaverage_y is a 0/peak Expr resized with Bilinear to the chroma size, so on 4:2:0 and 4:2:2 it has intermediate values; the other operand is always 0/peak

Output format and frame properties: Expr takes the first clip's, as Lut2 does (its bits defaults to the first clip's). min of two integers involves no rounding, so akarin's half-tie difference from std.Expr (patch 7) cannot arise; the table below checks both.

Decisions

  • Expr over a lut= list: the list is exact by construction but still costs 1.2 s per filter per evaluation; the Expr costs nothing measurable and is exact for these call sites.
  • Rewrite the eight calls, not route core.std.Lut2 through a proxy as patch 7 routes Expr: there are only eight call sites, all the same lambda, and a proxy would have to decide which functions are safe to replace.
  • min, not bitand: R78's std.Expr has no bitwise operators and the macOS x64 bundle has no akarin, and every platform must run an identical havsfunc.
  • Fail the build on a changed havsfunc (counts 8 calls, 7 on one line, 1 split over three), unlike patches 1–7: a havsfunc that ANDed two non-binary clips would make min silently wrong.
  • Guarded in the push gate (vapoursynth_integration_test.dart, “havsfunc mask AND (patch 8)”): both filters, output and mask, 8/10-bit and every subsampling, against upstream's table built as a lut= list (byte for byte the function's table, task #75, at a fraction of its cost); it also fails if a call takes over 2 s to build. Skipped on bundles up to 1.18.0-rc2, which predate the patch.

Not tested

  • x86 (Intel Mac, Windows, Linux): no machine here. Task #75's probe saw the old tables cost several times the M1's on the Intel runners; the Expr's cost does not depend on Python's speed. The push-gate test prints the slowest build time on every CI row.
  • The Windows patch text (PowerShell) could not be run here; build-deps-windows.yml applies it, and its count check makes a mismatch a failed build, not a silent skip.
  • The encode: the change is to the script graph the encode and preview share, so the identity above covers it; no encode was timed.
