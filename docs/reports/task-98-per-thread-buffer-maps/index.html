DFTTest, LGhost, CTMF, TCanny and EEDI3m: unlocked per-thread buffer maps

2026-11-22 · task #98 (found by task #96) · measured on an Apple M1 (macOS arm64 deps 1.18.0-rc2 as published, and the macOS x64 deps 1.10.0 bundle under Rosetta) · every number below is in data/, produced by scripts/.

Outcome: fixed in the deps (1.18.0-rc3). Five bundled plugins keep scratch buffers per worker thread in std::unordered_map<std::thread::id, …> members of the filter instance and fill or check them with no lock: DFTTest, LGhost, CTMF and TCanny in every published build, and EEDI3m r10 (macOS arm64 and Linux only) in one check. Two threads starting an instance together lose an insert; the kernel's .at() throws std::out_of_range inside noexcept code and vspipe aborts (unordered_map::at: key not found; exit 0xC0000409 on Windows). This is the class of bug task #96 fixed in DCTFilter. DFTTest's is the nightly knlmeanscl denoiser never crashes flake. Each plugin is now built from a pinned commit on every platform with a patch of ours that locks the map. Nothing else changes: output is the same, sample for sample, on macOS arm64 and x64. Windows can only be checked in CI.

1. The fault

Every one of them does this, with DFTTest's four maps, LGhost's one, CTMF's two and TCanny's four:

// getFrame (arAllFramesReady), no lock:
if (!d->buffer.count(threadId))
    d->buffer.emplace(threadId, …);           // inserting can rehash the table
…
// the kernel, declared noexcept, in the C, SSE2, AVX2 and AVX-512 files:
auto buffer = d->buffer.at(threadId).get();   // no lock

Each filter is fmParallel, so VapourSynth runs frames of one instance on several threads at once. Two threads that start their first frame of an instance together insert into the same table concurrently. One insert is lost, or a lookup runs during the other thread's rehash. The lookup then fails, and .at() throws inside a noexcept function, which is std::terminate. EEDI3m r8 held one mutex across the check, insert and lookup. r9.1's 61e14ab ("Use shared_mutex for unordered_map") locks the insert and the lookup but runs the first count() outside the lock.

Upstream DFTTest issue #12 (2021) reported exactly this abort and was closed as not reproducible. No release of any of the five fixes it.

3. Reproduction and the fix, measured

scripts/many_instances.vpy splices N instances of one call end to end on a 96x64 clip at 8 threads. Each instance has its own maps, so each instance's first frames are a chance for the race. It runs in a fresh vspipe each time, against the published 1.18.0-rc2 macOS arm64 bundle ("unpatched") and against a copy of it with the five plugins rebuilt by scripts/build_task98.sh. That script runs the deps script's own build_task98_plugin code ("patched"). scripts/run.sh drives both.

macOS x64 (under Rosetta)

The x64 path of build_task98_plugin was built on the M1 through a c++ shim (-arch x86_64, minos 12.0). It was dropped into the deps 1.10.0 macOS x64 bundle, which holds Stefan-Olt's builds, and compared under Rosetta (scripts/x64_parity.sh, data/macos-x64-rosetta.txt). LGhost, CTMF and TCanny are byte-identical. DFTTest gives one of two pictures, chosen per process, with either build: 10 processes of the old build gave 4 + 6 (and one abort), the new one 2 + 8, and the two builds gave the same two pictures. Across the two parity runs the old x64 builds aborted 3 times in about 50 single-instance runs (TCanny once, DFTTest twice); the patched ones never did. That variation is DFTTest's FFTW_PATIENT planning, which times plans per process, as FFT3DFilter's FFTW_MEASURE did in task #80. It is not this change. Task #101 follows it up. Scripts/check-load-time-simd.py finds no static initialisers in any of the four x64 builds.

Windows

The Windows block (download-deps-windows.ps1, 4b5) was run step for step on the M1 with the same Zig 0.15.2. That built all four DLLs, each carrying the marker and exporting VapourSynthPluginInit (TCanny: VapourSynthPluginInit2), with no imports beyond the UCRT, KERNEL32 and (DFTTest) FFTW 3.3.5. Doing so found one fault before CI could: zig's -mcpu feature list must name evex512 beside avx512f, or the AVX-512 files fail to compile. The DLLs have not been run: the deps CI run and the push gate's marker test on Windows are that check. -ffp-contract=off is passed because MSVC, which built the published DLLs, never fuses a*b+c, and clang does in the AVX2/AVX-512 files.

4. The patch

One shape for all five, generated by scripts/make_patches.py from a clean checkout at each pin, so re-running it reproduces Scripts/patches/*-thread-safety.patch byte for byte:

  • the header gets mutable std::shared_mutex bufferMutex and threadBuffer(map), which looks the calling thread's buffer up under a shared lock;
  • getFrame checks for the thread's buffers under the shared lock and allocates and inserts them under a unique lock. Only the calling thread ever inserts its own key, so nothing can insert it between the two;
  • every kernel's d->X.at(threadId).get() becomes d->threadBuffer(d->X);
  • the plugin's name gains (VapourBox: locked per-thread buffers, task #98). The API 3 plugins report no version and TCanny's did not change, so this marker is what the deps scripts and the test check;
  • EEDI3m r10: only its first count() moves under the shared lock.

Upstream fixed DCTFilter by allocating a buffer per call. That would be wrong here: DFTTest's ebuff is a whole padded float plane, and CTMF's hFine is up to memsize (16 MB from the template) per thread, so per-frame allocation would fault in fresh pages on every call. Locking keeps allocation and reuse exactly as they were.

  • All four x86 plugins pick SSE2, AVX2 or AVX-512 at run time. The base files are compiled at the x86-64 baseline and each AVX level in its own file, so one build serves both CPU tiers and nothing is added to _tierFiles.
  • macOS compiles with hidden visibility, as meson does. A first test build without it, loaded beside the bundle's own DFTTest, crashed inside the bundle's unordered_map::find. dyld merges exported template instantiations across images.
  • Each script removes a build without the marker (from an older run, or a prebuilt) and fails if the marker is missing afterwards. A patch that stops applying fails the build.

6. What it explains in CI

Every failed nightly job from 2026-11-01 to 11-21 (33 runs, about 140 jobs) was searched for these aborts (data/ci-nightly-aborts.txt). The knlmeanscl denoiser never crashes failures on linux-x64-v2 (11-03, 11-09) are DFTTest: those jobs log that KNLMeansCL has no OpenCL device, so QTGMC's denoiser falls back to DFTTest, and QTGMC Fast reaches no other plugin with such a map. This is inferred from the graph, since there is no backtrace. The other hits are TCanny (11-15, task #52, already avoided) and DCTFilter (task #96). No CI failure names CTMF, LGhost or EEDI3m.

7. Limits

  • Abort rates are from one machine (M1, 8 threads). The race depends on scheduling; other CPUs see other rates.
  • The Windows DLLs were built but not run here (section 3).
  • Output parity on Linux is not measured: Linux builds the same code with the same meson build as before, only pinned and patched.
  • The EEDI3m race was not reproduced (section 3).
