znedi3 refuses a plane with an odd number of rows on x86

Task #81, 2026-11-21. Measured on an Apple Silicon Mac (M1 Pro) with deps 1.18.0-rc2: the macos-arm64 bundle natively, and the macos-x64 bundle with an x86_64-apple-darwin build of the worker under Rosetta 2 (x86 plugins, x86 znedi3). Linux x64 and Windows x64 numbers are the nightly runs that found it (44342418084 on main 48bca80e, 44737084373 on 1a04bfcf), not re-run after the fix. Base commit for "before": 0618c709.

Outcome

  • Cause: znedi3's constructor (vsznedi3/vsznedi3.cpp) throws "clip must have even number of scanlines" when dh is false and either the frame height or the subsampled plane height is odd. It runs when the script is built, so the job fails at evaluation, whatever _FieldBased says. A 4:2:0 frame 486 lines high (NTSC D1) has 243 chroma rows. dubhater's nnedi3, which arm64 uses (havsfunc patch 6, the template's _nnedi3()), takes it, and the probe table is written on arm64, so it said ok.
  • Who was hit: on x86 (Windows, Linux, Intel Macs), every 720x486 4:2:0 job with Deinterlace → Bwdif and "High-quality interpolation" (NNEDI3), 8 and 16-bit, with or without a field order. daa and mpeg2stinx were already padded by task #57; the probe flagged them because it calls the plugins raw.
  • Fix: _nnedi3() runs every call without dh through run_within() under a new contract, 'nnedi3.nnedi3' (height_step=CHROMA): the frame padded to 488 lines (one more chroma row, each field's own last row repeated), the call, then cropped back. daa (havsfunc's own nnedi3) moved from a bare pad_around to a contract, 'havsfunc.daa', so the probe measures both padded paths. A frame that already fits gets no node.
  • The hole it fell through: plugin_format_contracts_test read only the base table's summaries, which are one platform's. A refusal only an x86 bundle shows can only be a platforms override, and nothing required one to be handled. It now must be padded by a contract or listed in HANDLED / KNOWN, like a base-table refusal. Removing the new contract makes the test name each x86 cell.
  • Cost on arm64: the frame is padded on every platform, so both run one graph (task #57's daa precedent). There, Bwdif + NNEDI3 at 720x486 4:2:0 changes in the last 3 rows of each plane only (below).

The probe

The nightly full probe on Linux x64 (both tiers) and Windows x64 (both tiers) reported the same 16 cells: bwdif.Bwdif, nnedi3.nnedi3, havsfunc.daa and mpeg2stinx at 420p8 / 420p16, f0 / f2, 720x486, table says ok, the bundle says refused. The macOS x64 full probe never finished in nightly (task #75), so its cells were measured here under Rosetta and match.

  • The probe's Bwdif and mpeg2stinx calls now take NNEDI3 from a copy of the template's helper, padding included, so they measure what jobs run: ok on x86.
  • nnedi3.nnedi3 stays the raw plugin; its within pass measures the contract. Same for havsfunc.daa. On x86 their 720x486 4:2:0 cells are refused raw and ok through run_within(): overrides for linux-x64, windows-x64 and macos-x64.
  • VFM's 9- and 14-bit documentation rows (outside the reachable set) accept on Linux x64 and, measured here, macOS x64: overrides too. Windows refuses them, as the table says.

data/x64_probe_check_before_overrides.txt is the x64 check with the new probe and contracts before the overrides were written; data/x64_probe_check.txt after (no differences).

What padding changes on arm64

Bwdif + NNEDI3 (field=3, TFF) as the template calls it, padded, against the unpadded call nnedi3 accepted before, on 10 frames (20 out) of the same source at 720x486. Found on the way, filed

FFV1 and x265 encode it. That is why daa with a field order first failed in this table's runs, before and after alike.

Limits

  • x86 here is Rosetta 2 on Apple Silicon with the macOS x64 bundle. The refusal is a constructor check, the same in every build, and the Linux and Windows nightlies show the same cells, but the fix has not run on native Linux, Windows or Intel Mac hardware. The next nightly is that check: the full probe, and the new sweep variant deinterlace/bwdif+bwdifEdeint=true on the 96x66 rows.
  • One source clip (a VHS capture), 10–12 frames, 8 and 16-bit. 10 and 12-bit run the same graph.
