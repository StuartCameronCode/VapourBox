ProRes in MOV: no +faststart, PCM for restored audio

2026-11-14 · follow-up to the v210 work (docs/reports/2026-11-v210-field-order) · measured on an Apple M1 Pro (16 GB, internal SSD), deps 1.16.0 bundle (FFmpeg 9.0.2), app 1.7.0

Outcome: built. ProRes now follows v210, the other editing intermediate. It no longer gets -movflags +faststart. With Audio Restoration on and Output → Audio on Passthrough, the restored track is PCM instead of AAC. Both are decided by one predicate, VideoCodec::is_editing_intermediate (ProRes, v210), which already decided the field-order flag. Neither change fixes a reported bug. Both change existing ProRes output, which is why they are measured and recorded here.
Correction (2026-11-14, at review). The predicate was written as also deciding the field-order flag. Meanwhile the field-order work for the other codecs (report) gave FFV1, HuffYUV, FFVHuff and x264 their own flags through VideoCodec::field_order_signal. So is_editing_intermediate now decides only +faststart and the restored track's codec.

Why ask

A ProRes or v210 file is made to be cut in an editor, not delivered. Two of the encoder's container defaults are aimed at delivery:

  • +faststart moves the MOV's index (moov) in front of the media after the last frame is written. That helps a file played progressively over HTTP. Editors and local players read the index wherever it is.
  • A restored audio track is new audio, so Passthrough cannot copy it. It was encoded as AAC in MOV. The editor encodes the soundtrack again on delivery, which makes two lossy generations.

F1 · What +faststart costs

Source: 180 s of 1920x1080 25p ProRes HQ (testsrc2 with temporal noise, so the data rate is realistic), 191 Mbit/s, 4.30 GB. The same -c copy mux was timed without and with +faststart, so the difference is the second pass alone. Two sessions, wall-clock seconds:

runno faststart+faststartextra
A13.798.274.48
A24.049.795.75
A35.957.471.52
B11.883.651.78
B21.863.801.94
B32.136.464.33
B44.327.723.40
B52.798.816.01

The extra pass costs 1.5–6.0 s per 4.3 GB: 0.4–1.4 s/GB, median about 0.9 s/GB. An hour of ProRes HQ 1080p (~86 GB) is about 1–2 minutes on this SSD. For v210 (~500 GB an hour) it is roughly 6× that.

Limits. These runs use a fast internal NVMe SSD. The machine has 16 GB of RAM, so the 4.3 GB file is partly in the page cache, which is why the spread is wide. No USB disk or NAS was available. There the pass reads and rewrites the whole file at that device's speed, so on a ~150 MB/s hard disk an hour of HQ would take an estimated 10–20 minutes. That figure is an estimate, not a measurement.

Against a whole job: a QTGMC 1080i encode at ~15 fps takes ~300 s for these 3 minutes, so the pass adds ~1–2% on this SSD. For a straight ProRes transcode it adds more, and on slow storage much more. The pass also runs after the last frame, so the progress bar sits at 100% with nothing moving. A process killed during the pass leaves an unreadable file.

F2 · It does not need the space twice

The old comment on uses_faststart said faststart "needs the space twice". That was wrong. Polling the output directory during a +faststart mux found one file at most, and a peak of 4,210,692 KiB, which is the final file (4,300,722,657 bytes). FFmpeg logs "Starting second pass: moving the moov atom to the beginning of the file" and shifts the data in place. The comment is corrected.

F3 · PCM beside ProRes in MOV

ProRes plus pcm_s16le muxes as apch + sowt, at 768 kb/s for mono 48 kHz (1.5 Mbit/s stereo). Beside 45–300+ Mbit/s of ProRes that is under 3% of the file. sowt is the little-endian LPCM tag QuickTime and NLEs read.

Decisions

  • No +faststart for ProRes (uses_faststart is !is_editing_intermediate()). The benefit to an editing file is nil. The cost is small on an SSD, real on slow storage, and always a stall at 100%. H.264/H.265 in MP4/MOV keep it.
  • PCM for a restored track beside ProRes (restored_passthrough_codec), in every container, the same as v210. ProRes can only go in MOV today. The user can still choose any codec with Audio → Convert. Only the Passthrough default changed.
  • 16-bit PCM (pcm_s16le, the existing AudioCodec::Pcm), the same as v210. The rendered track is 32-bit float, so a 24-bit option for intermediates would keep more. That is a separate decision because it needs a new codec value. Left as a follow-up.

Verification

  • Rust: test_faststart_skipped_for_editing_intermediates sweeps VideoCodec::ALL, checks every ProRes profile in MOV has no +faststart, and checks H.264 MP4/MOV and H.265 MOV keep it. restored_passthrough_is_pcm_beside_intermediates sweeps every intermediate and container. encode_codec_args gives ProRes MOV -c:a:0 pcm_s16le with no bitrate.
  • Heavy: integration_audio_restoration_test.dart encodes ProRes and v210 MOVs with restoration on and audio copied, and checks the first audio stream is pcm_s16le.

Not tested

  • A USB disk, a NAS or Windows/Linux file systems (see the estimate in F1).
  • Timing through the worker. The remux isolates the pass; through the worker it runs after the same file is written, so the extra cost is the same pass.

Reproduce

SCRATCH=/path/to/scratch docs/reports/2026-11-prores-faststart/scripts/probe.sh   # RUNS=5 for session B

It builds the 4.3 GB source if it is missing (~8 minutes), then prints F1–F3.
