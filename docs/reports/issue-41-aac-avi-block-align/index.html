AAC in AVI: a packet over the declared block size was timed as two

2026-11-15 · macOS arm64, deps 1.16.0 (FFmpeg 9.0.2), VLC 3.0.23 · Windows readers on a GitHub windows-latest runner (Windows NT 10.0.26100, the bundle's FFmpeg 9.0) · task #41, found during the Convert-into-AVI priming fix (task #38)

Outcome: fixed. ffmpeg's AVI muxer declares an AAC stream's block size (WAVEFORMATEX.nBlockAlign) as 768 bytes per channel (riffenc: "maximum bytes per frame", the spec's 6144 bits) and stores AAC as VBR audio, one packet per chunk (strh.dwSampleSize 0). Readers time such a chunk as ceil(size / nBlockAlign) packets. ffmpeg's native AAC encoder writes packets over 768 bytes per channel at 192 kbps per channel and more: in the app, mono at High (the default) and Very High. Every such packet was timed as two, so the rest of the sound played one packet (21.3 ms at 48 kHz) later: +320 ms by the end of 12 s at 256 kbps. ffmpeg, VLC and DirectShow all did this; Media Foundation split the chunk and decoded 15 extra frames. Copying such AAC into AVI (Passthrough) did the same.

The worker now raises each AAC stream's nBlockAlign to its largest chunk after the encode (worker/src/avi_header.rs). avienc's trailer already records that size in the same header as strh.dwSuggestedBufferSize, so the fix reads the header and writes 2 bytes. Every file with no oversized packet is left byte for byte as it was. After the fix, every reader tested times every packet once, and the decoded samples are unchanged.

The overshoot follows bits per channel per frame: it starts at 192 kbps per channel at 48 kHz and lower at 32 kHz, where each frame gets more bits. 128 and 160 kbps per channel reach exactly 768 bytes on harsh content but were never seen to pass it at 48 kHz. That is an observation, not a bound. The app's stereo and 5.1 settings stay at or below 128 kbps per channel, so in practice the fault is mono at High or Very High.

3. The fix

  • Where the size comes from. avienc keeps each stream's largest packet and writes it into strh.dwSuggestedBufferSize when it finishes the file. In every file measured, that value was the largest audio packet (audio-only, FFV1 + AAC, rawvideo + AAC). On a 1.2 GB OpenDML file whose 16 oversized packets all lie in the second RIFF (AVIX), it was still 835, the true maximum, and the fix took the ffprobe gaps from 16 to 0 (scripts/odml_check.sh, data/odml.txt). No index or data is read.
  • What is changed. One rule, avi_header::aac_block_align_fixes, applied to a stream whose strh is auds with dwSampleSize 0 and whose strf says wFormatTag 0x00FF (AAC), when dwSuggestedBufferSize is above nBlockAlign (and fits in 16 bits). It walks the RIFF lists rather than searching bytes, and any malformed header yields no change. MP3 is left alone: its nBlockAlign of 1152 is a convention VBR-MP3 readers rely on, and like AC-3 (3840) it stays within that at every app setting.
  • When. After a successful encode into AVI with sound, Convert or Passthrough (checks_block_align), before the subtitle step. The subtitle mux never rewrites an AVI, since it falls back to an SRT beside it. Anything added later that rewrites an AVI must run the fix again. A failure is logged as a warning and never fails the job. The job log says when the block size was raised.

4. Tests

  • Rust: avi_header.rs unit tests on synthetic headers. They check the right offset and value; no change when packets fit; stereo; MP3, AC-3, PCM and CBR AAC left alone; only the stream that overshoots; truncated or garbage input without a panic; exactly 2 bytes written, and the file untouched (bytes and mtime) when there is nothing to fix; and the container × audio-mode gate.
  • Heavy: integration_video_start_offset_test.dart, group mono AAC over 768 bytes a packet into AVI (task #41), on Tests/TestResources/avi_aac_overshoot.mkv (generate_avi_aac_overshoot.sh). The fixture has noise bursts that overshoot at any level, kept 0.1 s clear of the beeps, decoding to ≤ 0.23 so they never read as beeps. It covers Convert at High and Very High, untrimmed and trimmed, plus a copied 256 kbps mono AAC source. Each case first requires that oversized packets were written (otherwise it proves nothing). It then checks: nBlockAlign equals the largest packet, the packet timestamps are gap-free, the beeps keep their 2 s spacing within 1 ms, and each beep falls within 1 ms of its white frame (not for the copy; see section 5). With the fix turned off, both tests fail. The other Convert-into-AVI tests are back at the default quality and check the header the same way.

5. Limits

  • One FFmpeg series (9.0: the martin-riedl macOS build, and the bundle's Windows build for the Windows fixtures, which gave the same largest packets, 833 and 777). The planning run used Homebrew's 9.0.2, whose sizes differed slightly (780 for 777). The heavy test therefore asserts that an overshoot happened, not how many.
  • Sources: two fixtures, one capture of music and speech, and synthetic noise. How often real captures overshoot was not measured. The fix does not depend on it.
  • Windows readers were run on one runner image, with the readers' default AVI components. LAV Splitter (ffmpeg's avidec, already measured), VirtualDub, Premiere and Vegas were not tested.
  • Found on the way, not fixed here (task #43): an untrimmed Passthrough of an AAC source that carries priming writes a null frame at the head of an AVI (task #38's fault on the copy path), so the copy case checks drift only.
