v210 output and interlaced field-order flagging

2026-11-10 · forum request (videohelp thread 419911, post #154) · measured on Apple Silicon (macOS arm64), deps 1.16.0 bundle (FFmpeg 9.0.2, VapourSynth R78), against the templates of app 1.7.0

Outcome: built. Uncompressed 10-bit 4:2:2 (v210) is a new output codec, in MOV (default), MKV and AVI. Probing for it found that every still-interlaced ProRes or v210 MOV was flagged progressive (fiel atom 0x0100), because vspipe's Y4M header always says Ip. The encoder is now told the field order on the pipe input with -top (fiel 0x0209 TFF / 0x020e BFF), and ProRes codes the frame as fields (-flags +ildct). The suggested -field_order output option is inert in FFmpeg 9. A second finding: FFmpeg's -pix_fmt conversion of interlaced 4:2:0 to 4:2:2 blends the two fields' chroma, so v210's 4:2:2 is made in the script, field-aware.

What was asked, and what had to be checked

Strasse asked for MOV output with v210 uncompressed: AVI plays badly on a Mac, and FFV1/HuffYUV/FFVHuff aren't usable directly in Premiere or Resolve, so users transcode to v210 anyway. The bundled FFmpeg's v210 encoder takes yuv422p10le yuv422p, so no deps change is needed. An editing intermediate is only useful if the editor treats its fields correctly, so the field-order flag was checked for v210 and the existing ProRes output.

Findings

All from scripts/probe.sh. The test clip is a 720x576 25 fps 10-bit 4:2:2 blank, marked _FieldBased=2 (TFF) in VapourSynth, piped as Y4M exactly as the worker does.

P1 · vspipe never says a clip is interlaced

YUV4MPEG2 C422p10 W720 H576 F25:1 Ip A0:0 XLENGTH=10

The header's Ip (progressive) is written whatever _FieldBased is, so FFmpeg never learns the field order from the pipe.

  • P2. Before this change every still-interlaced ProRes and v210 MOV said progressive. That's actively wrong, not just missing: an editor reading 0x0100 treats the woven frame as one picture.
  • P3. -field_order tt on the output does nothing. FFmpeg's encoder setup takes the field order from the frames' own flags and overwrites the option.
  • P4. -top 1|0 before -i - (a decoder option on the Y4M input) flags the frames. setfield in the -vf chain does the same, but a Custom FFmpeg Argument -vf replaces the whole chain and would drop it, so the input option is used. CLAUDE.md gives the same reasoning for declaring colour tags on the input. In QuickTime, fiel 9 = two interleaved fields, top first; 14 = bottom first. ffprobe's tb/bt labels are FFmpeg's names for these, and they read confusingly. The atom bytes are what an editor reads, so the tests check the bytes.
  • P5. ProRes has a field flag in its own frame header, which stays progressive unless the frame is coded as fields (+ildct). Apple codes interlaced ProRes that way. v210 has no bitstream flag; its frame-level values come from the container.

So v210 is offered in MOV (default), MKV and AVI. The README says AVI carries no field order.

P7 · FFmpeg's 4:2:0 → 4:2:2 conversion blends the fields' chroma

An interlaced 4:2:0 frame whose field 0 has chroma U = 64 and field 1 U = 192 (in a woven 4:2:0 picture, chroma row k belongs to field k mod 2). The U rows of the 4:2:2 result, 8-bit units:

Converted byU rows 2…11
FFmpeg -pix_fmt yuv422p10le (frames flagged interlaced)172, 172, 84, 84, 172, 172, 84, 84, 172, 172
VapourSynth resize with _FieldBased=264, 192, 64, 192, 64, 192, 64, 192, 64, 192

FFmpeg's auto-inserted scaler treats the woven frame as progressive, mixing the fields' colour on every moving edge. zimg honours _FieldBased and keeps each field's chroma exact. So for v210 the script always converts to YUV422P10 itself (EncodingSettings::effective_chroma_subsampling), whatever Color Format is selected. FFmpeg's -pix_fmt yuv422p10le stays only as a guard and converts nothing. This is a synthetic worst case (fully saturated, opposite colours per field). On real footage the error is confined to chroma that differs between fields: moving edges.

ProRes has the same latent problem for interlaced 4:2:0 sources. It is unchanged here, because changing it changes existing ProRes output. Left as a follow-up.

Update 2026-11-14: done. ProRes now converts in the script too, measured in ProRes chroma conversion in the script.

P8 · Data rate

FFmpeg reports 221,184 kb/s for 720x576 25p v210. That matches v210's packing (6 pixels per 16 bytes, lines padded to 48 pixels): ceil(720/48)·128 · 576 · 8 · 25 = 221,184,000 bit/s. 1080p25 is 1,105,920,000 bit/s, about 8.3 GB a minute. For the same reason, MP4/MOV's +faststart (a second full pass that rewrites the file to move its index to the front) is skipped for v210.

Decisions

  • Field order from one decision. ScriptGenerator::output_field_order starts from "deinterlacing off and a field order detected". It drops to progressive where a pass makes the frames progressive: Stabilize's pitch correction, Deblock's mpeg2stinx, and a Frame Rate conversion (a retimed woven frame is not a field pair). A test counts every SetFieldBased( in both templates, so a new pass that clears the marking fails until it is accounted for.
  • Only v210 and ProRes are flagged. FFV1/HuffYUV in MKV could take the flag as metadata, and x264/x265 would need real interlaced coding. Both are separate decisions, left as follow-ups.
  • v210's colour format is not the user's choice. Any other selection is converted to 10-bit 4:2:2 directly, and the settings dialog says so (v210ChromaPinWarning, pinned to the worker's table).
  • Restored audio beside v210 is PCM, not the container's usual lossy codec.

Verification

app/test/integration_v210_output_test.dart (heavy) encodes real jobs and checks:

  • a 10-bit 4:2:2 ProRes source comes back bit for bit in v210 (framemd5 of all 25 frames)
  • the fiel bytes and field_order for v210 MOV/MKV and ProRes MOV at TFF and BFF, plus ProRes's frame header
  • AVI stays unknown, and a deinterlaced job stays 0x0100
  • each field's chroma survives the 4:2:0 → 4:2:2 conversion on a red/blue field fixture (10-bit rows exactly 360/960)
  • PCM passthrough and conversion in MOV
  • preview = encode (meanAbsDiff 0.000)

The Rust tests cover the argument matrix (which codecs and jobs get -top and +ildct) and the script's conversion block.

Not tested

  • Windows and Linux FFmpeg builds. -top is a generic decoder option, so the nightly heavy run on all four platforms is the check there.
  • Opening the files in Premiere Pro or DaVinci Resolve. The fiel values are Apple's documented meanings, but no NLE was run.
