zimg's NEON float vertical resize reads filter coefficients past its buffer

2026-11-27 · task #115 (added by task #109) · measured on GitHub Actions ubuntu-24.04-arm (Neoverse V2, gcc 13.3, clang 18.1, glibc 2.39), runs 45994602531 and 45995908194, and locally on macOS arm64 (Apple clang) · every number below comes from scripts/; the tables are in data/.

Outcome: a zimg bug, not the harness and not a false positive. It is harmless in what we ship. resize_line_v_f32_neon<Taps, Continue> in src/zimg/resize/arm/resize_impl_neon.cpp always reads coefficients filter_data[0..7], whatever Taps is. On ARM a filter row of 4 or fewer taps is stored 4 floats apart, so on the last output row coefficients 4 to 7 come from the 16 bytes past the end of FilterContext::data. The values are never used.

  • gcc 13 with AddressSanitizer keeps the loads, and all 32 of task #109's arm64 aborts are this read: READ of size 4, 0 bytes after a vector of exactly output rows × 16 bytes, in resize_line_v_f32_neon<1, false> or <4, false>.
  • The same 32 abort with every frame plane 4096 bytes larger, so the harness's frames are not involved.
  • A one-function patch, loading only the taps the instance uses, brings it to 0 aborts. It changes no pixel (158 of 158 CRCs identical).
  • Upstream master (9806db42 / graphengine 308d3735) behaves the same: 32 aborts unpatched, 0 patched.
  • clang 18 ASan finds nothing. The build VapourSynth makes (gcc 13, -O3, no sanitizer) contains none of the extra loads, and valgrind finds no invalid read in it.
  • The shipped linux-arm64 bundle (deps-v1.18.0-rc4) is clean under valgrind on both resizes.

No VapourBox change. The read is undefined behaviour in the source, but no build we ship performs it. A draft upstream issue with the patch is in upstream-issue-draft.md. The user files it; it has not been filed.

Symptom

Task #109 ran its 158 tmp_overrun graphs under gcc 13 ASan on ubuntu-24.04-arm (docs/reports/task-109-graphengine-tmp-overrun/data/linux/44995813552/c-bisect-arm64-gcc-13). 32 aborted with a heap-buffer-overflow, at every graphengine commit, the good cb5b2ce1 included. That ruled out graphengine's f6211289 bug, but left these 32 unexplained. Nothing aborted on x64 (gcc or clang), nor under Apple clang ASan on macOS arm64, which runs the same NEON source.

The code

template <unsigned Taps, bool Continue>
void resize_line_v_f32_neon(const float * RESTRICT filter_data, ...)
{
	...
	const float32x4_t c[8] = {
		vdupq_n_f32(filter_data[0]),
		...
		vdupq_n_f32(filter_data[7]),   // always 8, whatever Taps is
	};

ResizeImplV_F32_Neon::process passes m_filter.data.data() + i * m_filter.stride. The stride is ceil_n(filter_width, AlignmentOf<float>) (resize/filter.cpp:63), and on ARM ALIGNMENT is 16 (common/align.h), so a filter of 4 or fewer taps has a stride of 4 floats. The kernel's per-pixel loop (resize_line_v_f32_neon_xiter) multiplies by c[0..Taps-1] only, so c[4..7] are dead. On x86 ALIGNMENT is 64, every stride is at least 16 floats, and the same read stays inside the vector. The 16-bit kernel is safe because stride_i16 rounds to 8. A filter wider than 8 taps runs the kernel again at offset 8 with the rest. When fewer than 8 taps remain there, the same over-read can happen, and the patch covers it too.

The controls

  • Padded frames (--pad 4096, a new tmp_overrun option): the same 32 cases abort, at the same regions and in the same function. The harness's planes and its tmp buffer (127,168 bytes at 720x480) are not the overflowed block.
  • clang 18 ASan, same runner, same source: 0 aborts. Its <1, false> loads one coefficient (ld1r {v0.4s}, [x0], data/45994602531/disasm-asan-clang-1ufalse.txt). clang drops the dead loads before ASan instruments them; gcc keeps them under ASan.
  • The build VapourSynth makes (gcc 13 -O3, no sanitizer): <1, false> loads filter_data[0] only (ld1r {v1.4s}, [x0]). <4, false> loads [x0], [x0, #4], [x0, #8] (one ldp) and [x0, #12]: taps 0 to 3, nothing past them (disasm-vs-gcc-*.txt). The patched build's two kernels are instruction for instruction the same. valgrind memcheck over all 158 cases: 0 invalid reads, patched or not (valgrind.tsv).
  • The shipped bundle: deps-v1.18.0-rc4's linux-arm64 vspipe under valgrind (bundle_check.sh, single-threaded). YUV420P8 → RGBS bicubic and RGB24 → YUV420P8 point, at 4x4, 96x64 and 720x480: every run finished, with 0 invalid reads (bundle-check.tsv).

Cause

The kernel builds c[8] from filter_data[0..7] for every Taps. With 4 or fewer taps the coefficient rows on ARM are 4 floats apart, so the last row's reads of 4 to 7 fall 0 to 15 bytes past the vector. The read is undefined behaviour in the source whether or not a compiler emits it. Whether it reaches memory depends on the compiler: gcc's ASan build keeps it; gcc's optimised build and clang's (with or without ASan) drop it, since nothing reads c[4..7].

The fix (scripts/zimg-neon-v-f32-taps.patch, one function): load Taps > k ? filter_data[k] : 0.0f. Taps is a template constant, so this folds away, and the unused c[k] are never read. Padding FilterContext::data by 8 floats would also work, but it would fix the allocation rather than the kernel.

Who is exposed

  • VapourBox: no one, today. The linux-arm64 bundle is the only shipped build that runs this kernel from source we compile. Its gcc 13 -O3 build emits no extra load, and valgrind sees none in it. macOS arm64 ships Homebrew's zimg, built with clang, which drops them as Apple clang does here. That was not disassembled. Windows and x64 builds use the x86 kernels.
  • What would change that: a compiler or flags that keep the dead loads (gcc ASan does). Even then the read is at most 16 bytes past a heap block, and the values are discarded, so pixels are unaffected. It could only fault if the vector ended exactly at an unmapped page. That needs a block glibc serves by mmap (≥ 128 KiB, so 8192 or more output rows), at which point the read lands in the mapping's page padding. In the cases measured it is invisible except to ASan.
  • A zimg bump (task #126, 9806db42): unchanged, same 32 reports. CLAUDE.md's zimg pin rule asks for task #109's ASan run before a bump; on arm64 these 32 are expected and are not the #109 overrun.

Decisions

  • No VapourBox code or bundle change: the shipped build does not perform the read. A zimg patch carried in download-deps-linux.sh would be upkeep for no change in the binary, and macOS and Windows zimg could not take it anyway.
  • Not filed upstream by this task: upstream-issue-draft.md has the issue text, the repro and the patch, and the user files it (decided at the plan stage).
  • Task #109's report keeps its numbers; it gains one dated line pointing here.

Corrections

  • The plan expected the over-read to "survive" in a normal gcc build and called the shipped exposure a page-edge fault at 8192+ rows. Measured: the shipped build has no such load at all. The page-edge reasoning applies only to a build that keeps the loads.

Limits

  • One runner type (Neoverse V2) and one gcc (13.3). Other gcc versions or flags may or may not keep the loads. The source bug does not depend on either.
  • Only cpu_type AUTO_64B (VapourSynth's default) was run. On aarch64 that is the NEON kernels.
  • The bundle check runs two conversions at three sizes, single-threaded, two frames each. That is enough for a deterministic read in a kernel that runs on every row; it is not a survey of VapourBox's passes.
  • macOS arm64's Homebrew zimg was not disassembled; Apple clang's behaviour on this source was checked locally (one coefficient load in <1, false>, with or without the patch).
