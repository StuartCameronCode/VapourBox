Task #72: the macOS x64 format-sweep SIGILL was vspipe's teardown race

2026-11-19 · GitHub-hosted x86 runners (macos-15-intel, ubuntu-24.04, windows-latest) · deps 1.17.0-rc3 against 1.18.0-rc1 · scripts in scripts/, raw counts in data/

Outcome

  • Every macOS x64 SIGILL in the push gate was task #68's race. On deps 1.17.0-rc3, 4 push-gate runs failed a random format-sweep row with vspipe exited with signal 4 (SIGILL) (5 rows). Every one left a crash report, and every report has the same faulting thread: vspipe's frameDoneCallback → condition_variable::notify_one → pthread_cond_signal → _os_unfair_lock_unowned_abort (section 1).
  • It is fixed by deps 1.18.0-rc1, which carries upstream's vspipe fix (task #68). On the same x86 runners, with only vspipe-bin swapped, R78's own vspipe crashed 71 of 32,160 one-frame runs and the patched one 0 of 32,160 (section 3).
  • No retry or quarantine was added. The sweep's native-crash class still finds real bugs (tasks #69, #70). Instead, the CI crash-report step now names this signature and says whether the bundle has the fix (section 4).

A Zig ud2 (vszip / zsmooth safety trap)ruled outSame: the trap is in _os_unfair_lock_unowned_abort, called from vspipe, with neither plugin on the stack.

Why the same race is SIGILL on macOS and SIGSEGV on Linux

R78's frameDoneCallback increments completedFrames before it writes the frame and notifies. Main can see "every frame done" in that gap and free VSPipeOutputData, its mutex and condition variable included. What the callback then does with freed memory decides the signal:

  • macOS: pthread_cond_signal takes the condition variable's internal os_unfair_lock. In freed (or reused) memory its owner field no longer matches, and libplatform aborts on purpose with ud2: EXC_BAD_INSTRUCTION, SIGILL. When the callback is still in outputFrame writing to the freed buffer, it is a SIGSEGV instead; both A/B crashes on macOS x64 (section 3) were that form.
  • Linux: glibc's condition variable has no owner check, so the fault is the write itself: SIGSEGV in outputFrame, with main in vpy4_freeScript.
  • Windows: an access violation (0xC0000005).

The fixture Tests/TestResources/crash_reports/macos-x64-vspipe-teardown-sigill.ips is one of these reports as CI printed it (paths reduced to the runner's own).

What they show on macOS is that the race fires there, under the same signature, and that the patched side did not crash in 10,720 runs.

4. What changed

  • .github/scripts/print-crash-reports.py: prints every thread of a macOS .ips (it printed the faulting thread only), classifies a report (vspipe-teardown, image:<name> or unknown), and says whether the bundle's vspipe carries the fix (its --version marker read from the binary). --classify FILE… runs it on any .ips or gdb text and never fails.
  • ci-test.yml and nightly.yml: the macOS jobs upload the raw .ips files as crash-reports-* artifacts on failure (14 days).
  • app/test/crash_report_classifier_test.dart (push gate): the macOS SIGILL and the Linux SIGSEGV fixtures both classify as the race; a plugin/driver crash is named by its image.
  • replay-vspipe.sh: runs on macOS (no env -0 or timeout there).
  • CLAUDE.md Debugging Tip 11: the macOS signature.

5. Not tested

  • The SIGILL form itself under the A/B: the loops on macOS x64 produced only the SIGSEGV form. The SIGILL form's evidence is the five CI reports' stacks, which are the same callback.
  • A larger macOS-only A/B. 10,720 runs a side gave 2 against 0; telling the two apart on macOS alone would take roughly five times as many runs.
