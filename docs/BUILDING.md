# Building VapourBox from Source

## Prerequisites

### All Platforms
- [Flutter SDK](https://flutter.dev/docs/get-started/install), stable channel — `app/pubspec.yaml` requires Dart SDK `^3.6.2`, so Flutter 3.27.4 or newer
- [Rust](https://rustup.rs/) stable (the worker is edition 2021; CI builds with `dtolnay/rust-toolchain@stable`)

### Windows
- Visual Studio Build Tools with the C++ workload
- **7-Zip**, installed at `C:\Program Files\7-Zip\7z.exe` — `download-deps-windows.ps1` needs it for the plugins that ship as `.7z` (mvtools, nnedi3cl, znedi3 and others). Without it those plugins are **skipped with a warning**, leaving an incomplete bundle.

### macOS
- Xcode Command Line Tools
- Swift (from the CLT) only if regenerating the app icon

### Linux
```bash
sudo apt-get install -y clang cmake git ninja-build pkg-config \
  libgtk-3-dev liblzma-dev libstdc++-12-dev
```

## Download Dependencies

> **Required before building or running locally.** Dependency binaries are **not**
> committed — these scripts reproduce them in full from upstream release URLs, and
> CI (`build-deps-*.yml`) is the source of truth. Run the script for your platform
> once to populate `deps/` (which is gitignored), and re-run it after the matching
> `download-deps-*` script changes.

**Windows (PowerShell):**
```powershell
.\Scripts\download-deps-windows.ps1
```

**Linux:**
```bash
./Scripts/download-deps-linux.sh
```
Builds VapourSynth R73 and the plugins from source against an embedded Python
3.12.8. Detects `x86_64` vs `aarch64` and targets `deps/linux-x64` or
`deps/linux-arm64`.

**macOS (arm64, native):**
```bash
./Scripts/download-deps-macos.sh
```

**macOS (x64):** built natively on an Intel Mac — the same script (`uname -m`
reports `x86_64`, so it targets `deps/macos-x64`). FFmpeg is sourced pre-built
from [evermeet.cx](https://evermeet.cx/ffmpeg/) (static x86_64); most plugins
come pre-built from
[Stefan-Olt/vs-plugin-build](https://github.com/Stefan-Olt/vs-plugin-build), and
`descratch`/`neo-f3kdb`/`nnedi3cl`/`vivtc` build from source.

```bash
./Scripts/download-deps-macos.sh --force
```

To build the x64 deps on Apple Silicon instead, run it under Rosetta 2 with an
Intel Homebrew prefix (`macos-13` Intel runners were retired Dec 2025):

```bash
softwareupdate --install-rosetta --agree-to-license
arch -x86_64 /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
arch -x86_64 /bin/bash -lc 'PATH=/usr/local/bin:$PATH ./Scripts/download-deps-macos.sh --force'
```

In CI, deps are produced by **Build macOS Deps** (`build-deps-macos.yml`, arm64 on
`macos-15` and x64 natively on `macos-15-intel`), **Build Linux Deps**
(`build-deps-linux.yml`, x64 + arm64) and **Build Windows Deps**
(`build-deps-windows.yml`, x64 on `windows-latest`).

`Scripts/deps-expected-plugins.json` is the contract for a complete bundle: the
`package-deps-*` scripts assert every listed plugin exists before zipping and fail
the build otherwise, so a dead upstream URL becomes a red build rather than a
silently incomplete bundle. Add new plugins there.

### How the worker finds deps

| Build | Search behaviour |
|-------|------------------|
| **Debug** (`cargo build`) | Searches upward from the executable for `deps/` — **except on Linux** |
| **Release** (`cargo build --release`) | Only known production paths |

The upward search is restricted to debug builds deliberately: in release mode a
malicious `deps/` in a parent directory could inject compromised binaries. **Use
debug worker builds during development.**

**Linux has no upward search** (`#[cfg(all(debug_assertions, not(target_os = "linux")))]`
in `dependency_locator.rs`), so the worker reads only
`~/.local/share/VapourBox/`. `download-deps-linux.sh` writes to repo-root `deps/`,
so link them for local worker runs and `cargo test` — the same thing CI does:

```bash
mkdir -p "$HOME/.local/share/VapourBox"
ln -sfn "$PWD/deps"   "$HOME/.local/share/VapourBox/deps"
ln -sfn "$PWD/addons" "$HOME/.local/share/VapourBox/addons"
```

## Development Builds

### macOS (recommended)

Use the debug script, which handles the full workflow (build worker + app, copy into bundle, remove quarantine from deps, launch):

```bash
./Scripts/run-debug-macos.sh            # Full build and launch
./Scripts/run-debug-macos.sh --skip-worker  # Rebuild app only
./Scripts/run-debug-macos.sh --skip-app     # Rebuild worker only
./Scripts/run-debug-macos.sh --run-only     # Just copy and launch
```

### Linux

```bash
./Scripts/run-debug-linux.sh            # Full build and launch
./Scripts/run-debug-linux.sh --skip-worker  # Rebuild app only
./Scripts/run-debug-linux.sh --skip-app     # Rebuild worker only
./Scripts/run-debug-linux.sh --run-only     # Just copy and launch
```

### Windows (manual)

1. Build worker: `cd worker && cargo build`
2. Copy worker: `cp worker/target/debug/vapourbox-worker.exe app/build/windows/x64/runner/Debug/`
3. Run app: `cd app && flutter run`

## Release Builds

### Build Rust Worker
```bash
cd worker
cargo build --release
```

### Build Flutter App

**Windows:**
```bash
cd app
flutter pub get
flutter build windows --release
```

**Linux:**
```bash
cd app
flutter pub get
flutter build linux --release
```

**macOS:**
```bash
cd app
flutter pub get
flutter build macos --release
```

> **Note**: The macOS Flutter build may fail with "Unable to find module dependency" errors. If so, use xcodebuild directly:
> ```bash
> cd app/macos
> rm -rf Pods Podfile.lock && pod install
> xcodebuild -workspace Runner.xcworkspace -scheme Pods-Runner -configuration Release build ONLY_ACTIVE_ARCH=NO
> xcodebuild -workspace Runner.xcworkspace -scheme Runner -configuration Release build ARCHS=arm64 ONLY_ACTIVE_ARCH=YES
> ```

> **macOS deployment targets are per-arch**: arm64 targets **15.0**, x64 targets
> **12.0** (Monterey — the x64 deps are built to match). `app/macos/Podfile` reads
> `VAPOURBOX_ARCHS` (default `arm64`) and `VAPOURBOX_DEPLOYMENT_TARGET` (default
> `12.0`); `package-macos.sh` and `build-macos.yml` set both per arch. To
> cross-compile the Intel Runner on Apple Silicon, set `VAPOURBOX_ARCHS=x86_64`
> and pass `ARCHS=x86_64` to xcodebuild.

### Generate Dart JSON Serialization

Run this after model changes:
```bash
cd app
dart run build_runner build --delete-conflicting-outputs
```

### Regenerating the App Icon

`Scripts/generate-app-icon.swift` is the vector source of truth (CoreGraphics, no
ImageMagick needed); `Scripts/generate-app-icons.sh` drives it at every size each
platform wants and packs the Windows `.ico`. macOS only, needs Swift from the CLT:

```bash
./Scripts/generate-app-icons.sh
```

The generated PNGs and `.ico` **are committed**, because Xcode's asset catalog and
the Windows resource compiler read them at build time.

## Packaging

**Important**: Never manually assemble a release build by copying binaries into the .app bundle — an incomplete bundle crashes silently on video drop. Always use the packaging scripts.

### Windows
```powershell
.\Scripts\package-windows.ps1 -Version "1.0.0" [-SkipBuild]
```
Output: `dist/VapourBox-1.0.0-windows-x64.zip`

### Linux
```bash
./Scripts/package-linux.sh --version 1.0.0 [--skip-build] [--arch x64|arm64]
```
`--arch` defaults to the host. Output: `dist/VapourBox-1.0.0-linux-<arch>.tar.gz`

### macOS
```bash
./Scripts/package-macos.sh --version 1.0.0 [--arch arm64|x64] [--skip-build] \
    [--notarize] [--no-sign] [--team-id ID] [--keychain-profile NAME]
```
`--arch` defaults to the host architecture and also fixes the deployment target
(arm64 → macOS 15, x64 → macOS 12). Output: `dist/VapourBox.app` and
`dist/VapourBox-1.0.0-macos-<arch>.dmg`.

macOS ships as **two separate per-arch DMGs, not a universal binary**. In CI the
**Build macOS** (`build-macos.yml`) workflow takes `arch: both | arm64 | x64`
(default **both**, which fans out over a matrix and emits one DMG per arch) plus a
`notarize` toggle. Signing and notarization happen there, using the Developer ID
cert from repo secrets; Windows and Linux CI builds are unsigned. Locally, use
`--no-sign` for ad-hoc test builds.

The processing dependencies are **not** bundled — the app downloads the
arch-appropriate set (`macos-arm64` or `macos-x64`) on first run per `uname`, so
both deps bundles must be published for a release.

### Testing a Packaged Build

Run from the terminal to see error output (release mode swallows exceptions silently):
```bash
# macOS
dist/VapourBox.app/Contents/MacOS/vapourbox
# Linux
dist/VapourBox-1.0.0-linux-x64/vapourbox
```

Do **not** run `app/build/macos/Build/Products/Release/vapourbox.app` directly — it lacks templates and proper bundle structure.

## Running Tests

There are three suites. Both `cargo test` and `flutter test --exclude-tags heavy`
run in the CI gate (`ci-test.yml`) on macOS arm64, macOS x64, Windows x64 and
Linux x64.

```bash
# 1. Rust worker tests — script generation, preview, subtitles
cd worker && cargo test

# 2. Flutter suite, minus the encode-heavy tests — what the push gate runs
cd app && flutter test --exclude-tags heavy

# 3. Everything, including the full-encode integration tests (slow)
cd app && flutter test
```

- `worker/tests/filter_integration_test.rs` **only generates and inspects the
  `.vpy` script** — it does not run `vspipe | ffmpeg`, so it cannot catch runtime
  or plugin-behaviour bugs. Those need the Dart integration tests.
- `app/test/integration_*_test.dart` spawn the worker end-to-end via
  `app/test/support/worker_harness.dart`. The encode-heavy ones are
  `@Tags(['heavy'])` and run in `nightly.yml` (`flutter test --tags heavy`), not
  the push gate.
- The harness honours `$VAPOURBOX_DEPS_DIR`, else repo-root `deps/<platform>`,
  else **downloads the deps release pinned in `app/assets/deps-version.json`**
  (opt out with `$VAPOURBOX_SKIP_DEPS_DOWNLOAD=1`). Call
  `await WorkerHarness.ensureReady()` in `setUpAll`.
- Subtitle tests need the whisper add-on and skip when it's absent.

Every filter or parameter change must add tests to **both** suites — see the
checklist in [CLAUDE.md](../CLAUDE.md).

```bash
# Run the worker standalone, outside any harness
cd worker && cargo run -- --config test_job.json
```

## Releases

Releases are built in CI, not locally. `Scripts/release.sh` orchestrates the whole
flow; `Scripts/ci-build-and-release.sh --version X.Y.Z` triggers the three platform
Build workflows, waits, downloads the artifacts and uploads them to an existing
draft release. `Scripts/update-version.sh` bumps the version across pubspec,
`Cargo.toml`, `Runner.rc` and `Info.plist`. Full step-by-step instructions,
including the required signing secrets, are in [CLAUDE.md](../CLAUDE.md).

App and deps use separate release tags (`vX.Y.Z` and `deps-vX.Y.Z`) so unchanged
deps aren't re-uploaded every release. Check with
`./Scripts/check-deps-changed.sh` before bumping deps.

## Dependencies

VapourBox bundles all runtime dependencies. No external installations are required at runtime.

| Component | Version | Purpose |
|-----------|---------|---------|
| Python | 3.8 (Windows) / 3.12.8 (macOS, Linux) | VapourSynth runtime |
| VapourSynth | R73 | Video processing framework |
| FFmpeg | Latest | Video encoding/decoding |
| havsfunc | r31 + patches | QTGMC implementation |
| pipe_source.py | — | Raw frame reader for VapourSynth |
| mvtools | v24 | Motion estimation |
| znedi3 / nnedi3 / nnedi3cl | Latest | Neural network interpolation (CL = OpenCL) |
| EEDI3m | r8 | Edge-directed interpolation |
| fmtconv | **r31** (pinned, from GitLab) | Format conversion |
| neo_f3kdb | Latest | Debanding |
| DFTTest / KNLMeansCL / TTempSmooth | Latest | Denoising |
| zsmooth | 0.19.0 | CCD chroma denoise, Cnr4, RemoveGrain/TemporalMedian family |
| DeScratch / tmedian | Latest | Scratch and spot removal |
| VIVTC | Latest | Inverse telecine (VFM + VDecimate) |
| whisper.cpp | Latest | Speech-to-text for subtitles |
| libdvdread | Latest | DVD reading and navigation |

The full per-platform plugin contract is `Scripts/deps-expected-plugins.json`.
fmtconv is **pinned to r31 on every platform** and carries a local patch
(`Scripts/patches/fmtconv-r31-arm-int-scaler.patch`) that fixes black output from
its non-SIMD integer scaler on arm64; havsfunc carries five compatibility patches.
Both are explained in [CLAUDE.md](../CLAUDE.md) — keep the versions in step across
platforms, or the same job produces different output per OS.
